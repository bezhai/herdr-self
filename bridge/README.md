# Herdr Bridge

经每台机器上的 Bridge 客户端连接那台机器上的 Herdr，把飞书聊天路由到 Herdr 中的 Agent：每个飞书话题对应 Herdr 里一个 tab 中的 Agent 会话，它在所属项目的工作目录里工作（有仓库的项目默认是话题自己的 worktree）。网页提供机器、飞书应用、会话绑定、话题和 skill 的管理。

## 启动

Bridge 和每台机器上的客户端都需要 Node.js 24+。运行 Agent 的机器需要安装 Herdr，以及绑定所选 Agent 的命令行工具（Claude Code、Codex 或 Antigravity CLI `agy`）。项目带仓库时，那台机器还需要 Git 2.31+ 和拉取仓库的权限；起分支名和在私聊里挑项目还需要在那台机器上已登录的 Claude Code CLI（见下面「话题」）。

每台机器上的 Bridge 客户端必须与那台机器的 Herdr server 使用同一用户和相同的 `HOME`、`XDG_CONFIG_HOME`：`herdr --session <name>` 按 `$XDG_CONFIG_HOME/herdr/sessions/<name>/herdr.sock` 查找 server，未设置 `XDG_CONFIG_HOME` 时使用 `$HOME/.config/herdr/sessions/<name>/herdr.sock`。客户端运行 Herdr 用的是用户的 shell 作为登录 shell 设置的环境（见下面「机器上的客户端」），所以 `XDG_CONFIG_HOME` 要么不设置，要么设置在登录 shell 会读的配置里，例如 zsh 的 `~/.zshenv` 或 `~/.zprofile`、bash 的 `~/.profile`。

```bash
cd bridge
npm ci
npm start
```

`npm start` 先用 Vite 构建管理台（输出到 `web/dist/`），构建失败则不会启动。只支持安装完整依赖的源码部署：使用 `npm ci`，不要加 `--omit=dev`，构建工具在开发依赖中。Bridge 目录需要可写。前端未构建时 `/` 与 `/connect` 返回 503。

打开 `http://localhost:8080`。首次启动生成 `state/access-key`，使用该文件中的访问密钥登录。状态目录包含应用凭证和会话配置，不应提交到 Git。

| 环境变量 | 默认值 | 用途 |
| --- | --- | --- |
| `PORT` | `8080` | HTTP 端口 |
| `BIND` | `0.0.0.0` | 监听地址 |
| `BRIDGE_HOSTS` | 空 | 允许访问的额外域名或 IP，逗号分隔，不含端口 |
| `BRIDGE_STATE` | `bridge/state` | 状态目录 |
| `BRIDGE_URL` | 空 | 管理台对外地址，例如 `http://host:8080`，生成客户端配置时作为控制面地址。只能是 http(s) 地址，不带路径、查询参数和 `#`，末尾的 `/` 会去掉；格式不对时 Bridge 不会启动 |

**模型服务**：Bridge 用一个便宜的模型做几件小事：给话题的分支起名、私聊话题挑项目（和起分支名是同一次调用）、在绑定卡片上猜群的项目、从项目仓库的 README 写一句项目描述。它们由控制面直接调用一个 OpenAI 兼容的服务，所有机器用同一个，和机器上的 Claude 配置无关。服务由控制面进程的三个环境变量配置：

| 环境变量 | 用途 |
| --- | --- |
| `BRIDGE_MODEL_BASE_URL` | 服务的地址，到 `/chat/completions` 之前，例如 `http://127.0.0.1:18080/v1` |
| `BRIDGE_MODEL_API_KEY` | 密钥，作为 `Authorization: Bearer` 发送 |
| `BRIDGE_MODEL_NAME` | 请求里的 `model` |

请求是 `POST <地址>/chat/completions`，请求体 `{model, messages:[{role:'user',content:提示词}]}`，回答取 `choices[0].message.content`（`reasoning_content` 忽略），20 秒超时，用 Node.js 自带的 `fetch`。三项缺一项、请求失败、超时、返回非 2xx 或没有文字，都当作这次调用失败，调用方各自退回：分支用随机名，私聊话题在一个空目录里开始，绑定卡片不预选项目，项目描述留空；原因记在日志里，日志、错误信息、状态文件和 `/api/state` 里都没有密钥。

部署时把三项写进状态目录里的 `state/model.env`（权限 600，不提交到 Git），每行一项：

```
BRIDGE_MODEL_BASE_URL=http://127.0.0.1:18080/v1
BRIDGE_MODEL_API_KEY=<密钥>
BRIDGE_MODEL_NAME=<模型名>
```

再在控制面的 systemd 用户服务（`herdr-bridge`）的 `[Service]` 里加一行 `EnvironmentFile=-%h/apps/herdr-bridge/state/model.env`（路径按实际部署目录写；开头的 `-` 让文件不存在时服务照常启动，只是没有模型服务），然后 `systemctl --user daemon-reload` 并重启服务。改了这个文件也要重启服务。

默认允许 localhost、127.0.0.1 和当前主机名。通过其他地址访问时配置 `BRIDGE_HOSTS`；`BRIDGE_URL` 中的主机名也需要在允许范围内。当前管理台采用单用户密钥登录；公网部署需要 HTTPS 反向代理。

**机器上的客户端**：每台运行 Agent 的机器（包括 Bridge 所在的这台）运行一个 Bridge 客户端 `bin/bridge-client.ts`。客户端用这台机器自己的 token 主动连接 Bridge 的 HTTP 端口（WebSocket，路径 `/api/client`），保持一条长连接，断开后自己重连。客户端只用 Node.js 自带的模块，机器上有 Node.js 24 就能运行，不需要 `npm install`，也不需要构建管理台：把 Bridge 目录复制过去即可，不用带 `node_modules` 和 `state/`。Bridge 在机器上做的每件事（调用 Herdr CLI、建目录、写入和删除附件、准备和删除话题的工作目录、准备 Agent 的启动、起分支名和挑项目、放置 skill）都经这条连接交给客户端，由客户端在本机完成（见下面「实现」的「机器上的操作」）；Bridge 自己不执行 ssh，也不在本机直接操作机器，所以 Bridge 所在的这台机器同样要装客户端。客户端还在本机打开一个 Unix socket，把这台机器上 `bridge-schedule` 和 `bridge-skill` 的请求经这条连接转给 Bridge（见下面「定时任务」和「Skill」）。安装步骤：

1. 在管理台的「机器连接」页点机器卡片上的「生成 token」，确认后对话框显示这台机器的客户端配置：

   ```json
   {
     "url": "ws://<Bridge 的地址>:8080/api/client",
     "token": "<token>"
   }
   ```

   配置只显示这一次，Bridge 只保存 token 的 SHA-256 摘要。`url` 取 `BRIDGE_URL`，没有配置时取浏览器打开管理台用的地址，https 对应 `wss://`。这台机器访问 Bridge 要用别的地址时（例如只能用 IP），把 `url` 改成那个地址；它的主机名或 IP 要在 Bridge 允许的 Host 范围内（见上面的 `BRIDGE_HOSTS`），否则 Bridge 以「不允许的 Host」拒绝连接。配置丢了就点「重新生成 token」：旧 token 立即失效，正在用它连接的客户端被断开。
2. 在那台机器上把配置保存为 `~/.config/herdr-bridge/client.json`，权限 600（`chmod 600`）。文件里有 token，其他用户能读到它时客户端拒绝启动。位置可以用环境变量 `BRIDGE_CLIENT_CONFIG` 另外指定；设置了 `XDG_CONFIG_HOME` 时默认位置在它下面。客户端默认运行 `~/.local/bin/herdr`；这台机器的 Herdr 装在别处时，在配置里加一项 `"herdr": "<Herdr 的路径>"`，写绝对路径或 `~/` 开头的路径（`~/` 是这台机器的 home 目录）。
3. 用 systemd 用户服务运行客户端，例如保存为 `~/.config/systemd/user/herdr-bridge-client.service`：

   ```ini
   [Unit]
   Description=Herdr Bridge client
   After=network-online.target

   [Service]
   ExecStart=%h/.local/share/fnm/node-versions/v24.13.0/installation/bin/node %h/<Bridge 目录相对 home 的路径>/bin/bridge-client.ts
   Restart=on-failure
   RestartSec=10

   [Install]
   WantedBy=default.target
   ```

   systemd 不读 shell 的配置，用 fnm 安装的 Node.js 不在服务的 PATH 上，所以 `ExecStart` 写 Node.js 的绝对路径（`%h` 是 home 目录），版本号换成这台机器上装的 24.x。`fnm exec --using=24 -- node -e 'console.log(process.execPath)'` 可以查到这个路径；不要用 `fnm env` 设置的 `fnm_multishells` 下的路径，那是某一次 shell 会话的临时链接。然后执行 `systemctl --user daemon-reload && systemctl --user enable --now herdr-bridge-client`；退出登录后也要运行时，执行一次 `loginctl enable-linger`。日志在 `journalctl --user -u herdr-bridge-client`。

**客户端运行命令的环境**：systemd 不读 shell 的配置，服务的 PATH 里通常没有 `~/.local/bin`，也没有 fnm、nvm 这类工具加的目录，按服务自己的 PATH 有时找不到 `git`。客户端启动时用用户的 shell（`$SHELL`，没有时取 passwd 里登记的 shell）作为登录 shell、不带终端运行一次 Node.js，参数固定（`<shell> -l -c 'exec "$@"' sh <node> -e <打印环境的代码>`，不拼接命令字符串），取得这个 shell 设置好的环境；之后 Herdr 和 git 都在这份环境里直接运行，不经过 shell，参数原样传递。zsh 读 `~/.zshenv` 和 `~/.zprofile`，bash 读 `~/.bash_profile` 或 `~/.profile`，所以 unit 文件里不写 PATH，`git` 要在这些文件设置的 PATH 上。用登录方式，是因为 bash 不以登录方式运行时一个启动文件都不读：以前 Bridge 经 SSH 执行命令时，sshd 用的是非登录的 `<shell> -c`，zsh 读 `~/.zshenv` 就够了；登录 shell 是 bash 的机器，`git` 以前只能靠 Bridge 服务自己的 PATH 找到，现在从 `~/.profile` 取。这份环境去掉所有 `HERDR_*` 变量（否则 Herdr 和 Agent 的 hook 会把状态报到启动客户端的那个 pane 上），也去掉 shell 给自己设置的 `PWD`、`OLDPWD`、`SHLVL` 和 `_`。shell 的启动文件打印的内容不影响结果：Node.js 在一个 NUL 字符之后才输出环境，客户端只读这之后的部分。环境只在客户端启动时取一次，改了 `~/.zshenv` 之后要重启客户端（`systemctl --user restart herdr-bridge-client`）。shell 运行失败或者 10 秒内没有结束时，客户端在日志里记一行原因，命令改用客户端自己的环境（同样去掉 `HERDR_*`）运行：配置里的 Herdr 按路径照样能找到，只在 shell 的 PATH 上才有的程序（例如 `git`）找不到，clone 和 worktree 会失败。比较过的做法：每条命令都经 `<shell> -c` 执行，环境总是最新的，但每 5 秒一次的轮询要多启动两次 shell，shell 启动文件打印的内容还会混进 Herdr 输出的 JSON；在 unit 文件里写死 PATH，每台机器要单独维护一份，而且会和 shell 的配置不一致；不用登录方式，登录 shell 是 bash 的机器拿不到任何 PATH。

客户端直接连接 `url` 里的地址，不经过 `http_proxy`、`https_proxy` 这类变量设置的代理：Node.js 24 自带的 WebSocket 默认不读这些变量。设置了 `NODE_USE_ENV_PROXY=1` 或者 `--use-env-proxy`（让 Node.js 使用这些变量）时，客户端拒绝启动。读不到配置文件、配置文件权限不对或者内容无效时，客户端以状态 1 退出，systemd 隔 10 秒再启动它。同一台机器的另一个客户端连上 Bridge 时，旧的那个以状态 0 退出，`Restart=on-failure` 不会再拉起它（见下面「实现」的客户端连接）。客户端和 Bridge 要用同一版本的代码，协议版本不同时 Bridge 拒绝连接，管理台的机器卡片显示「客户端被拒绝」和原因；客户端会一直按间隔重试，所以先升级客户端、再升级 Bridge 时，Bridge 升级后客户端自己就能连上。token 不对、Host 不在允许范围内时 Bridge 不知道是哪台机器，原因只出现在客户端的日志里。

**升级到有项目和 Agent 配置的版本**：控制面和所有机器的客户端一起升级（协议版本 6，见下面「实现」的客户端连接）。控制面第一次启动时迁移状态文件（见下面「接入」的「旧版本升级」）；旧版本读不了迁移后的文件，所以迁移前的状态文件先原样复制到状态目录里的 `state.json.before-projects`（已经有这个文件时不覆盖），要退回旧版本时用它换回 `state.json`，同时也要把各机器的客户端退回去；之后每台机器的客户端连上时再把它上面接管了目录的项目转换成仓库项目；迁移后项目的名称、描述和仓库列表在管理台调整。Bridge 在一台机器上第一次用到一个仓库时 clone 它，所以那台机器要能拉取这个仓库（例如有对应主机的 SSH 访问）；仓库放在 `~/.local/share/herdr-bridge` 下（见下面「实现」的「项目的目录和 Agent 的启动准备」），迁移来的项目沿用原来的目录。进行中的话题继续用它们原来的目录。部署后 `/wt` 不再存在，也会从应用的斜杠命令面板里消失（见上面「斜杠命令」）。

**部署管家**（管家话题只能执行 `butler`，用到上面升级时迁移出来的绑定）：
1. 在能连上管理台的机器上设置 `BRIDGE_URL` 和 `BRIDGE_ACCESS_KEY`（见 `bridge-skill --help`），运行 `bridge-skill import <butler 目录>` 导入 `butler` skill；目录里是 `SKILL.md`，由 `~/butler-desk/CLAUDE.md` 整理而来，命令的用法让 Agent 自己看 `butler --help`。不要把它设为默认加载，否则其他项目的话题也会拿到它。
2. 管理台「Agent 配置」页新建一个配置：机器选 Agent 要运行的那台（这台机器上要能运行 `butler` 命令，管家服务在别的机器上时放一个转发过去的 `butler` 脚本），Agent 类型选 Claude，「只允许执行的命令」填 `butler`。Codex 和 Antigravity 不能设置这一项。
3. 「项目」页新建项目「管家」：仓库留空，话题目录选「每个话题独立」，Skills 选 `butler`。
4. 「会话绑定」页把管家的绑定改到新的项目和配置：群聊绑定的「默认项目」选「管家」；私聊绑定没有默认项目，由模型按任务挑，挑的不是「管家」时在话题的第一张卡片上换项目。改完后升级时从 `~/butler-desk` 迁移出来的那个项目没有绑定在用，可以在「项目」页删除；`~/butler-desk` 目录不要删，确认管家正常以后再由主人决定。
5. 在管家的聊天里发一条消息，确认 `butler --help` 能运行，让它写文件或运行别的命令时被拒绝、而且终端里没有弹出确认。

## 接入

1. **机器连接**：在「机器连接」页添加机器，只填名称和 Herdr session；保存后直接进入生成 token 的对话框，按上面「机器上的客户端」把配置装到那台机器上。机器是否在线就是它的客户端是否连着：卡片下方显示「客户端在线」和客户端所在的主机名，没有连着时显示「客户端离线」，协议版本不一致时显示「客户端被拒绝」和原因。客户端在线时，Bridge 每 5 秒经它读取一次 Herdr 的终端和 Agent，卡片上显示 Herdr 的状态（已连接，或者连接失败和原因）、终端和 Agent 的数量以及 Agent 列表；客户端不在线时 Herdr 状态显示「离线」。「断开」让 Bridge 停止使用这台机器：不再轮询，不再在上面开话题、发消息、接管 Agent 或者接受 `bridge-schedule` 的请求，客户端照样连着，Herdr 里的 Agent 继续运行；「连接」恢复。保留这个开关，是为了不用登录那台机器、停掉客户端，就能在管理台让 Bridge 暂时不碰它。编辑和移除需要先断开，生成和重新生成 token 不需要。机器离线时，往它的绑定发消息，话题里会提示「机器 <名称> 离线：它的 Bridge 客户端没有连上」：新话题不启动，之后重发消息会再试；进行中的话题这条消息不发给 Agent，Agent 在 Herdr 里继续运行，客户端重新连上后的下一次轮询照常取回它的回复（Herdr 为每个 Agent 保留最近 8 条）。

   从机器还分本机和 SSH 的旧版本升级时，Bridge 启动时去掉机器的连接方式、地址、端口和 Herdr 路径，只保存一次状态文件并记一条日志；机器的 ID、名称、session、是否启用，以及绑定和话题都不变。迁移后的机器在客户端连上之前显示离线，在机器页为它们生成 token、装好客户端即可。旧机器的 Herdr 路径不是默认的 `~/.local/bin/herdr` 时，日志里写明是哪台机器、路径是什么，要把它写进那台机器客户端配置的 `herdr`。旧版本首次启动时自动添加的「本机」机器不再添加，Bridge 所在的机器和其他机器一样在机器页添加。
2. **平台连接**：点击添加飞书，在官方页面新建或选择已有应用。确认后自动保存凭证并建立长连接。新应用创建者自动加入允许名单；也支持手动填写已有应用凭证。连接成功和验证凭证后，应用名称和头像以飞书机器人为准。
3. **项目、Agent 配置和会话绑定**：一个聊天的消息要送到哪里，由三种记录决定。**Agent 配置**是一台机器上的 Agent：类型（Claude / Codex / Antigravity）、可选的模型，Claude 还有权限模式（default：需要确认的操作发卡片到飞书，没有时按 default；auto：由 Claude 自动决定，很少需要确认）和可选的「只允许执行的命令」（程序名的列表，Codex 和 Antigravity 不能设置）；机器只由 Agent 配置决定，所以选配置就是选模型环境。配置名称默认是「机器 · 类型 · 模型」，例如「cpu1 · Claude · Seed」，可以改，不能重名。**项目**是零到多个 git 仓库（只接受 http、https、ssh、git 地址和 `user@host:path`，不接受本地路径和 git 会当成选项或传输助手的值）、一句描述、一组平台上的 skill 的名称和话题目录的用法：每个话题独立（默认）或所有话题共用。项目不属于哪台机器，机器上的仓库和目录放在哪由客户端决定，管理台不填路径。保存带仓库、描述为空的项目时，Bridge 在后台让一台在线机器用便宜的模型从仓库的 README 生成一句描述，期间被人改过描述或仓库就不覆盖，失败只记日志。**会话绑定**是一个聊天的默认设置：聊天、应用、聊天类型（群聊或私聊）、名称（取飞书的群名，私聊叫「私聊」，只读；应用每次连接时和收到群改名的事件时更新，读不到群名时保持原名）、是否需要 @机器人、是否启用、默认 Agent 配置，群聊还有默认项目，私聊没有（每个话题自己选项目）。管理台只修改已有的绑定：「会话绑定」页每行的「编辑」改默认项目（群聊；私聊显示「按任务自动选择」）、默认 Agent 配置和「需要 @ 机器人」（只对群聊有效，私聊总是触发），名称只读，改动只影响之后新开的话题；管理台不创建绑定，接口还能改是否启用，管理台没有这个开关。侧栏的「工作配置」分组有「项目」和「Agent 配置」两页：每页一个列表，「+ 新建项目」「+ 新建 Agent 配置」在弹窗里填字段（项目：项目名称、描述、仓库（每行一个地址）、话题目录（每个话题独立 / 所有话题共用）、Skills（只列按需读取的 skill，默认加载的不用选）；Agent 配置：配置名称（默认按「机器 · 类型 · 模型」填，改过名称之后不再跟着变）、机器、Agent 类型、模型，选 Claude 时还有权限模式和只允许执行的命令），卡片上有「编辑」和「删除」，不能删除时按服务器的说明提示。绑定在飞书里做：应用允许名单里的人在一个没有绑定的聊天里发消息（私聊的任何消息，群聊要 @机器人），机器人在这条消息的话题里回一张没有标题的卡片，写着「这个聊天还没有绑定 Bridge。」，下面是「项目」（私聊没有）和「Agent 配置」两个下拉框和「绑定」按钮。群聊的项目由便宜的模型（控制面调用模型服务，见上面「模型服务」，最多等 20 秒）根据群名和各项目的名称、描述猜，只有一个项目时直接选它；猜不出来或模型不可用时不选，不影响发卡片。Agent 配置是上一次新建绑定时选的那个，没有就选第一个。点「绑定」建好绑定（名称取群名，要求 @机器人），卡片改成「已绑定：项目 genvi，Agent 配置 cpu2 · Claude。」（私聊没有项目，只写 Agent 配置），刚才那条消息随即经和已绑定聊天的根消息相同的入口（`Topics.handle`）作为第一个任务开始；改卡片失败时同样的话回复在话题里。只有应用允许名单里的人发的消息会得到卡片、点的卡片有效，其他人点击只收到提示。没有项目（群聊）或没有 Agent 配置时，回复一句请先到管理台创建，不发卡片。同一聊天 30 分钟内只发一张卡片，卡片 30 分钟后失效；卡片只记在内存里，Bridge 重启后点旧卡片收到「已失效」，重新发一条消息即可。项目和配置被绑定设为默认，或被进行中（启动中、运行中）的话题使用时不能删除；机器上还有 Agent 配置或接管了目录的项目时不能移除机器。每个应用下一个聊天只能有一条绑定。话题的记录里有它启动时的项目、Agent 配置和目录（有仓库的独立项目还有分支），话题所在的 Herdr workspace 按机器记在绑定的 `workspaces` 里（它只是一个按标签核对的缓存，丢了只多开一个 workspace，不给管理台）。**旧版本升级**：控制面加载状态文件时，把每个带 `cwd`、`kind` 的旧绑定迁移一次：同一台机器的同一个目录成为一个所有话题共用的项目，它接管这个目录（内部记录，管理台不显示路径），项目名取目录的最后一段，重名加数字，不用飞书的占位名称；机器、类型和权限模式相同的绑定共用一个 Agent 配置，同一台机器和类型的配置只差权限模式时，名称末尾加上权限模式；绑定保留原来的 ID、名称和聊天，群聊以这个项目为默认项目，私聊没有默认项目，但它的目录同样成为项目；话题和定时任务继续指向原来的绑定，话题记下项目、配置和原来的目录，在结束前继续用这个目录。旧文件不记聊天类型：要求 @机器人的绑定是群聊，不要求的按名字判断，名字里有「私聊」的是私聊，其余是群聊。之后每台机器的客户端连上时，Bridge 对这台机器上接管了目录的项目各问一次它的目录是不是 git 仓库的根且有 origin：是的话，项目变成只有这个仓库、每个话题独立的项目，不再接管目录，名字还是迁移时起的就改成仓库名；已经有只含这个仓库的独立项目时并入它，绑定和话题跟着过去。不是仓库的目录只问一次；问不到（客户端出错）的下次连上再问。已迁移的状态文件再加载什么也不做。
4. **话题**：聊天里的一条顶层消息开启一个话题；定时任务到点时也会开话题，根消息是机器人发的运行卡片（见下面「定时任务」）。根消息就是任务本身，不写命令，Bridge 直接开始，不等确认：先决定项目、分支和 Agent 配置（见下面「开话题」），再让 Agent 配置所在的机器准备好话题的工作目录，在 Herdr 的工作区「飞书 · 绑定名称」中为话题新开一个 tab，启动 Agent，把消息发给它。工作目录由那台机器的客户端准备，准备失败（例如拉不到仓库）按启动失败处理。启动 Agent 之前，Bridge 在工作目录里放好默认加载的 skill 和项目自己的 skill，并移走它以前放的、现在已经不需要的 skill（见下面「Skill」和「实现」的「放置 skill」）；放不好只记一条日志，话题照常开。话题内的后续消息发给同一个 Agent。绑定要求 @机器人 时（群聊勾选了「仅 @机器人时触发」），群里的每条消息都要 @机器人 才会处理：开启话题的消息、话题内的后续消息，以及 `/adopt`、`/stop`、`/release` 这些命令都一样；没有 @机器人 的消息被忽略，不记录、不贴表情、不发给 Agent，也不回复。私聊和没有勾选这一项的群聊不需要 @机器人。Bridge 收下话题里的每条消息后，立即给这条消息贴上 `OneSecond` 表情；消息发给 Agent 后，话题里没有进行中的 COT 时，Bridge 在这条消息下创建一条 COT 消息（见下面「执行过程」），COT 创建成功就取消这条消息的表情，创建失败则保留表情；其他消息的表情在 Agent 处理完这条消息的那一轮后取消；消息没有发给 Agent 时（启动失败、Agent 等待确认、发送出错、会话已结束）也会取消。Agent 每轮结束时的最终回复以不带标题的卡片回复到话题里（markdown 渲染，卡片占满宽度），包括在 Herdr 中直接对这个 Agent 说话产生的回复。Agent 首次在某个目录启动时可能停在确认界面（例如 Claude 的目录信任提示），这时 Bridge 会在话题里提示，需要到 Herdr 中处理后重发消息。Agent 退出或换成别的 Agent 后，话题结束，Bridge 在下一次轮询或下一条消息时在话题里提示「该话题的会话已结束，在话题里回复即可接着做」（被接管的话题和升级前开的话题提示的是「请发起新话题」）。

   **开话题**：每个根消息（定时任务到点开话题时是机器人发的运行卡片，任务文字就是根消息）经同一条路径开始，一个根消息最多调用一次便宜的模型（见下面「实现」的「开话题」）：
   - **项目**：群聊用绑定的默认项目。私聊没有默认项目，由模型从全部项目里按名称和描述挑一个，同一次调用里还起分支名；没有挑出来（模型回答 NONE 或不存在的名称、调用失败、任务只有图片或文件、一个项目都没有）时用一个空目录，话题的第一张卡片写明「没有找到对应的项目，在一个空目录里开始。」，不单独发消息。便宜的模型是控制面调用的模型服务（见上面「模型服务」，所有机器用同一个，20 秒超时；没有配置、调用失败或没有返回文字都算调用失败），提示词是去掉附件的任务文字，起分支名的规则与 worktree-task 插件相同（同一份代码 `worktree-branch.mjs`），分支必须是 `feat|fix|refactor|docs|test|chore|perf|style/` 加小写 kebab-case，最长 64 个字符。
   - **分支**：项目带仓库、话题目录为「每个话题独立」时，话题有自己的分支，取模型起的名字；调用失败、超时或输出不合格时改用 `topic/<形容词>-<名词>-<4 位十六进制>` 形式的随机名，不中断话题，原因记在日志里。名字和别的话题的分支重名时（包括工作目录已经清理、分支留着的话题）在后面加 `-2`、`-3`……，因为 Git 不允许两个 worktree 检出同一个分支。没有仓库或所有话题共用目录的项目没有分支，群聊里也就不调用模型。
   - **工作目录**：话题所在机器的客户端按项目准备（`prepareWorkspace`）：项目在这台机器上接管了一个目录（升级迁移来的项目）时就在那个目录里工作；共用的项目是固定目录，仓库 checkout 在里面，缺就 clone；独立的项目是话题自己的目录，里面是每个仓库的 worktree，先从 origin 拉取，分支存在就检出，不存在就从默认分支新建；没有仓库的项目是空目录。路径全由客户端决定，Bridge 只记下客户端返回的目录。clone 和拉取可能很慢，这个请求的超时是 10 分钟。
   - **启动**：客户端再按 Agent 配置准备启动（`prepareLaunch`，超时 60 秒）：目录信任、Claude 的只允许执行的命令，并返回 `herdr agent start` 在 `--` 之后的全部参数（权限模式、模型、信任；Codex 另有每个话题都加的 `--no-daemon`、沙箱联网和跳过 hooks 审查），Bridge 原样放在 `--` 之后，自己不加任何参数。
   - **第一张卡片**：话题的第一张卡片（没有标题）写明「项目 · 分支 <分支> · Agent 配置」，例如「genvi · 分支 feat/fix-login · cpu2 · Claude」，没有分支时不写分支，下面有两个下拉框「换项目」「换 Agent 配置」，各列出其他所有项目和 Agent 配置（没有别的可选时不显示）。启动失败时这张卡片也在，可以换一个设置再试。
   - **换设置**：选了另一个项目或 Agent 配置之后，Bridge 在这个话题的队列里结束当前的 Agent（关闭它的 pane），让客户端删除话题的工作目录（`removeWorkspace`：分支上有自己的提交就保留，没有就一起删除；没有提交的改动随目录一起删掉），然后用新的设置把根消息当作任务重新开始：分支沿用话题已有的名字，不再调用模型；第一张卡片原地改成新的设置，话题里回复「已换成项目 promoter，话题重新开始。」（换 Agent 配置时是「已换成 Agent 配置 cpu1 · Codex，话题重新开始。」）。当前的 Agent 关不掉时话题保持原样并提示，目录删不掉只记日志。下拉框只对应用允许名单里的人生效，其他人点击只收到提示。
   - **继续做**：话题记着自己的项目、分支、Agent 配置和启动时所在的目录。话题结束后（Agent 退出、pane 关闭）在话题里再回复，Bridge 用话题记着的设置重新准备工作目录（目录被清理过就从分支恢复）、启动新的 Agent 并把这条消息发给它；`/stop`、`/release` 不会重新启动话题。被接管的话题和升级前开的话题不会重新启动。
   - **清理**：控制面每天（启动 5 分钟后第一次）扫一遍，结束或启动失败超过 7 天的话题让客户端删除工作目录，规则同上；只对 Bridge 准备过的话题做，删除成功就记下，不再重复；机器离线等原因失败时记日志，下一次再试；项目已被删除的话题没有办法按仓库清理，记日志并算作已清理。解除绑定时话题记录随绑定删除，之后没有记录能再驱动清理，所以已经结束或启动失败的话题的工作目录在这时删除（失败只记日志，不再重试）；Agent 还在运行的话题保留目录，因为 Agent 仍在里面工作，需要时在机器上手动清理。

   **图片和文件**：话题里可以发图片（图片消息，或富文本里插入的图片）和文件（文件消息，或富文本里的附件和视频）。Bridge 先从飞书下载，写到 Agent 所在机器上、Agent 工作目录下的 `.herdr-bridge/<话题 ID>/<消息 ID>-<序号>.<扩展名>`（Bridge 新开的话题用它启动时的工作目录，接管来的话题用 Herdr 报告的 Agent 工作目录），全部写好之后才把消息发给 Agent。发给 Agent 的文字里，图片和文件原来的位置换成 `[图片 N：<绝对路径>]` 或 `[文件 N：<原文件名>，<绝对路径>]`（N 按图片和文件分别编号），由 Agent 自己调用读文件或看图的工具。放在工作目录下，是因为 Claude（default 模式）和 Antigravity 读工作目录外的文件会弹确认，飞书里处理不了。`.herdr-bridge/` 下有一个内容为 `*` 的 `.gitignore`，`git status` 不显示它；目录权限 0700，文件 0600。图片最大 10 MB，文件最大 30 MB；超过上限、下载失败（例如飞书的数据防泄漏拦截）或写入失败时，话题里回复一条说明，例如「未能把附件交给 Agent：图片 1 超过 10 MB」，消息的文字照常发给 Agent，占位写成 `[图片 N：下载失败]` 或 `[文件 N：下载失败]`。话题结束（Agent 退出、`/release`）和解除绑定时，Bridge 删除这个话题的目录，删除失败只记日志（解除绑定时再试一次）；每次写入时，顺带删除同一个 `.herdr-bridge/` 下超过 7 天没有变化的其他话题目录。表情包、合并转发、卡片、语音、视频消息等 Bridge 拿不到内容的类型不发给 Agent，Bridge 在这条消息下回复「暂不支持这类消息，目前只能转发文字、图片和文件」，不开启话题。绑定要求 @机器人 时，这条提示也只回复 @ 了机器人的消息；图片消息和文件消息本身带不了 @，单独发送会按规则忽略，所以要把图片和 @机器人 放在同一条消息里发（在输入框里 @机器人 后粘贴或插入图片，发出的是一条富文本消息）；文件同理，需要放进同一条富文本消息，或者在不要求 @ 的聊天里发送。

   **执行过程（COT）**：从飞书消息开始的一轮在这条消息下有一条 COT 消息，显示「运行中」，Agent 每调用一个工具多一个步骤（标题取 Herdr 记录的工具调用标题，没有时用工具名；按工具名配图标：Bash、shell 等为命令，Read 为读文件，Edit、Write、apply_patch 为写文件，Grep、Glob、WebSearch 等为搜索，其他为默认图标），工具结束后步骤标为「完成」或「失败」，不显示工具的输出。Agent 等待确认（审批或提问卡片，或下面的「等待终端里的操作」提示）时状态行显示「等待确认」，继续运行后显示「继续运行」。这一轮结束（判断方式同表情）时 COT 标为完成，最终回复照常以不带标题的卡片单独发到话题里。一个话题同时最多一条进行中的 COT，期间发来的消息只贴表情。从终端发起的一轮没有 COT。话题结束（Agent 退出、`/release`、解除绑定）时进行中的 COT 标为出错。COT 的任何一步失败只记录日志，消息投递、表情、回复和卡片照常进行。工具步骤需要支持 `agent tool-calls` 的 Herdr 并重装集成；旧版 Herdr 的 Agent 没有 `tool_call_seq`，COT 只显示状态，不显示步骤。COT 需要较新的飞书客户端（停止按钮 PC 7.71 起、移动端 7.73 起），旧客户端上显示为普通文字。
5. **审批与提问**：Claude 或 Codex 在话题里请求权限（执行命令、改文件等）或 Claude 用 AskUserQuestion 提问时，话题里出现一张卡片。权限卡片列出工具名、说明和命令或参数预览，按钮为允许 / 总是允许 / 拒绝（只有 Claude 给出了规则建议时才有「总是允许」，Codex 只有允许 / 拒绝）；提问卡片把每个问题列成单选或多选，另有一个「其他」输入框，填了「其他」就以它为答案，有问题没答时提示且不提交。只有应用允许名单里的人能点，其他人点击会收到提示。点击后卡片改为结果和点击人，例如「已允许 · @张三」，按钮去掉。拒绝时 Claude 中断本轮，之后在话题里发新消息继续；Codex 拒绝这次调用并继续本轮。请求在飞书之外结束时（超时、本轮结束、Agent 退出、Herdr 重启），卡片改为「已失效（超时、已在终端处理或本轮已结束）」。Claude 的终端确认框在此期间照常可用；Codex 的请求最多等 10 分钟，之后卡片失效，终端里显示审批框。Agent 停在飞书回答不了的交互上（Codex 提问、MCP 表单、Claude 的计划确认、Antigravity 的命令审批和 `ask_question`、目录信任确认等）时，话题里提示一次「Agent 正在等待终端里的操作，请到 Herdr 中处理」；Antigravity 不发卡片，它的审批和提问都要到终端处理。

   审批和提问是否等待飞书的回答，由 Herdr 中这个 pane 的外部回答设置决定（见下面「实现」），不再由环境变量决定。需要支持 `herdr pane remote-answers` 的 Herdr，并在每台运行 Agent 的机器上重装集成（`herdr integration install claude` / `codex`）：旧版 hook 只在有 `HERDR_REMOTE_ANSWERS` 环境变量时等待答案，而 Bridge 已不再注入这个变量，不重装的话卡片不会出现。已经在运行的 Agent 是否加载新 hook 取决于 Agent 自己（Claude Code 会重新读取 settings 里的 hook，Codex 需要重启）。从注入环境变量的旧版 Bridge 升级后，之前开的话题的 Agent 没有打开这个设置，Bridge 第一次轮询时就会结束这些话题；这些 Agent 仍在原来的 tab 里运行，需要的话用 `/adopt` 重新接上。外部回答设置打开期间，Herdr 不为这个 pane 发 Agent 完成和需要处理的通知（系统通知、终端通知、herdr 卡片和提示音），话题的回复和审批已经转到飞书；`/release` 关闭这个设置后通知照常。
6. **接管正在运行的 Agent**：在任意已绑定的聊天里发一条只有 `/adopt` 的根消息（绑定要求 @机器人 时需要 @机器人），机器人在这条消息的话题里回一张卡片：一个下拉框列出 Bridge 已连接的所有机器上正在运行的 Agent，不受这个绑定的机器限制，每项写作「机器 · 名称 · 类型 · 状态」，例如「cpu2 · 赤尾重构 · Claude · 空闲」，下面是「接管」按钮。名称是用户在 Herdr 里起的名字：pane 的名称，没有时用 tab 的名称（Herdr 给没命名的 tab 显示的序号不算），再没有时用 workspace 的名称，都没有时才用 pane ID；同一台机器上可选的 Agent 名称相同时，名称后面加上 pane ID 区分。已经关联到话题的 pane（任意绑定，包括正在启动的话题）不列出；读取失败的机器在下拉框下面显示「机器 · 连接失败」；已断开桥接的机器不列出。选好后点「接管」，Bridge 再读一次那台机器的状态，确认这个 pane 里仍是卡片上的那个 Agent、也没有被别的话题关联，然后打开这个 pane 的外部回答设置，把这个话题关联到它（话题标题为「接管 · 名称」），在话题里发一条说明（机器、类型和名称、工作目录），有回复时接着发最近一条回复的全文，并把卡片改为「已接管 · @点击人」，之后卡片不再接受选择。没选就点「接管」时提示先选择并重画卡片；Agent 已退出或已变化、设置打不开、或者已被别的话题接管时，不关联，卡片改为原因和最新的列表，可以重新选择。选择之前，话题里的消息只会收到「请先在上面的卡片中选择要接管的 Agent」（绑定要求 @机器人 时，没有 @机器人 的消息照样被忽略），管理台里这个话题显示为「待选择」。

   接管后的话题和 Bridge 新开的话题一样：话题里的消息发给这个 Agent，回复转回话题（包括在终端里直接对它说话产生的回复），审批和提问发卡片，飞书回答不了的阻塞发提示，表情随一轮结束而取消；说明里已经发过的那条回复不会再转发；绑定要求 @机器人 时，话题里的消息同样要 @机器人。话题里发 `/release`（绑定要求 @机器人 的群里是「@机器人 /release」），Bridge 关闭这个 pane 的外部回答设置并结束话题，在话题里说明 Agent 仍在终端的 pane 里运行，之后话题里的消息不再发给它；设置关不掉时话题保持关联并提示稍后重试（Agent 已经不在时直接结束）。pane 关闭、Agent 退出或换成别的 Agent 时，话题同样结束，并提示「被接管的 Agent 已退出、已更换或所在 pane 已关闭，话题已结束接管」。

   接管不重启 Agent，也不移动 pane：pane 留在原来的 workspace 和 tab 里，不进入绑定的工作区，正在进行的一轮不受影响，终端里照常可以继续使用；Bridge 不会关闭、重启或移动被接管的 pane。用户在终端里输入的内容不会同步到飞书。没有向 Herdr 上报会话的 Agent（例如手动启动、连着后台 app-server 的 Codex）的回复可能无法转回飞书，说明里会提示；这是 Herdr 对 Codex 的既有限制。`/adopt` 只在根消息上识别，`/release` 只在接管来的话题里识别，其他位置的同名文字照常作为消息发给 Agent；这两条命令本身不贴表情。早期版本的中文命令 `/接管`、`/结束接管` 不再识别，会作为普通消息处理。卡片只有应用允许名单里的人能点。一个 pane 同时最多关联一个话题。
7. **停止当前一轮**：在已就绪的话题里发一条只有 `/stop` 的消息（绑定要求 @机器人 的群里是「@机器人 /stop」，没有 @机器人 的 `/stop` 被忽略；点 COT 的停止按钮也会发送它），Bridge 执行 `agent send-keys <pane> esc`，相当于在终端里按 Esc（Claude、Codex 和 Antigravity 都用 Esc 中断当前一轮），进行中的 COT 标为已中断；没有 COT 时在话题里回复「已停止 Agent 当前这一轮」。Agent 不在运行（不是 `working` 或 `blocked`）时不发按键，只回复「Agent 当前没有在运行的一轮」，因为对空闲的 Agent 按 Esc 可能打开它的菜单（例如 Claude 连按两次 Esc 打开回退）。按键发送失败时回复「未能停止 Agent，请稍后重试」。私聊里 COT 的停止按钮会把 `/stop` 作为根消息发到聊天里：这时如果这个聊天恰好有一个话题的 COT 在进行中，就停止那个话题；没有或有多个时，回复「请在要停止的话题里发送 /stop」。根消息 `/stop` 从不开启新话题。`/stop` 本身不贴表情，也不发给 Agent。
8. **斜杠命令**：应用每次连接成功后，Bridge 把 `/adopt`（接管正在运行的 Agent）、`/release`（结束接管）、`/stop`（停止 Agent 当前这一轮）注册为应用的斜杠命令，用户在输入框输入 `/` 时可以从面板里选（PC 7.70、移动端 7.71 起）。飞书只接受 `^[a-z][a-z0-9_-]{0,31}$` 格式的命令名，所以命令是英文。Bridge 创建缺少的命令、更新描述不一致的命令，并删除它自己注册过、现在不再有的命令（目前只有 `wt`），其余命令都不动：应用里可能有别人注册的命令，所以只有名称是 `wt`、描述还是 Bridge 当时写的「在新的 Git worktree 里开一个话题」的才删，描述不同的是应用自己的。应用缺少权限或飞书拒绝时，每次连接只记一条日志，命令照常可以手动输入。

9. **定时任务**：定时任务挂在一个绑定上，到点由 Bridge 开一个新话题，或者把任务发进一个话题，不依赖 Agent 自己的循环能力，所以 Claude、Codex 和 Antigravity 的绑定都能用。每个定时任务有时间（5 个字段的 cron 表达式加 IANA 时区，例如 `30 9 * * 1-5` 加 `Asia/Shanghai` 是每个工作日 9:30）、任务文字和模式：

    - **每次开新话题**（`new`）：到点时机器人在绑定的聊天里发一条根消息，是不带标题的纯文本卡片，写明定时任务 ID 的前 8 位、第几次运行、计划时间和任务文字（超过 300 个字符截断），然后在它下面开一个新话题：和用户开的话题一样，按绑定的机器、工作目录、Agent 类型和权限模式开 tab、启动 Agent，把任务文字作为第一条消息发给它，话题标题取任务文字的前 24 个字符。没有用户消息，所以不贴表情，这一轮的 COT 回复在这张卡片下。之后的回复、COT、审批卡片和用户在话题里的追问都和普通话题一样。上一次运行的话题还在启动 Agent，或者它的 Agent 在工作（`working`）或等待确认（`blocked`）时，这一次跳过，记为「上次还没结束，跳过」。绑定被移除后，到点时跳过并暂停。
    - **只保留最近 3 次运行的话题**：每次运行开出新话题后，更早运行的话题如果还在进行，Bridge 结束它，在话题里说明「这个话题来自定时任务 …，定时任务只保留最近 3 次运行的话题，Agent 已关闭」，并关闭它的 Agent 所在的 pane；pane 是 tab 里唯一的 pane 时 tab 随之关闭，tab 是工作区里最后一个 tab 时工作区也关闭（下一个话题会重建工作区）。最近 24 小时内有人在话题里发过消息的不关，下一次运行时再看。已经结束的话题（例如 Agent 自己退出了）不关它的 pane：Agent 不在以后，Bridge 无法确认 Herdr 没有把这个 pane ID 给了别的 pane。这是 Bridge 唯一主动关闭 pane 的地方，用户开的话题从不关闭。
    - **发进话题**（`into`）：到点时排进这个话题的队列（排在用户已经发来的消息之后），读一次 `agent list`：Agent 在工作或等待确认时跳过，记为「上次还没结束，跳过」；否则机器人在话题里回复一张同样的运行卡片，再把任务文字发给这个 Agent，就像用户在话题里发了一条消息，不贴表情，这一轮的 COT 回复在运行卡片下。话题已经结束（Agent 退出或被替换、`/release`、启动失败、解除绑定）时，这次跳过，定时任务自动暂停，并在话题里说明「定时任务 … 已暂停：这个话题的会话已结束，定时任务不会在这里另起一个 Agent」；解除绑定后话题记录已经删除，不再发说明。Bridge 不在同一个话题里另起一个 Agent：换了 Agent，就不记得之前几次做了什么。

    Bridge 停机期间错过的运行：恢复后只补跑最近错过的那一次，并且只在它比计划时间晚不超过 2 小时时补跑；更早的记为「Bridge 停机，错过」，合成一条记录，写明第一次和最后一次错过的时间。这样短暂重启不影响每天的任务，停了很久也不会恢复后连着跑。暂停期间的时间不补：恢复后从恢复的时刻算起；修改时间或任务文字后同样从修改的时刻算起。

    每个定时任务保留最近 20 次运行的记录：计划时间、处理时间、结果（开始、跳过、错过、失败）、开出或发进的话题、第几次运行和原因。发不出运行卡片、Agent 启动失败、任务没有发给 Agent 时记为失败，原因不带细节，细节只在日志里。

    **在对话里建立和管理定时任务**：用户在话题里用自己的话跟 Agent 说，Agent 调用 `bridge-schedule` 命令提交、查看、修改、暂停、恢复和删除定时任务，不需要斜杠命令，也不在网页上操作。

    ```text
    bridge-schedule add --cron <cron 表达式> --mode new|into --task <任务文字> [--tz <IANA 时区>]
    bridge-schedule list
    bridge-schedule runs <ID>
    bridge-schedule update <ID> [--cron <cron 表达式>] [--tz <IANA 时区>] [--task <任务文字>]
    bridge-schedule pause <ID>
    bridge-schedule resume <ID>
    bridge-schedule remove <ID>
    ```

    - **认出调用的 Agent**：命令只连本机的 Bridge 客户端，由客户端经它和 Bridge 的连接转发请求（见下面「安装」和「实现」的 bridge-schedule 的请求）。机器就是转发请求的客户端所属的机器，Bridge 从客户端的连接得知，而客户端是凭这台机器自己的 token 连上的；命令没有指定机器的参数，请求里写的任何机器都不算。命令带上 Agent 所在的 pane（Herdr 放在 pane 环境里的 `HERDR_PANE_ID`，也可以用 `--pane` 指定）和 Herdr session（Herdr 在非 default session 的 pane 里设置的 `HERDR_SESSION`，也可以用 `--session` 指定，都没有时为 `default`）。session 和 Bridge 为这台机器设置的不一样时拒绝，因为不同 session 里的 pane ID 会重复；这台机器在管理台里断开了桥接时也拒绝。Bridge 找出这台机器上这个 pane 里已就绪的话题，再在话题队列里读一次 `agent list`，确认 Agent 仍然关联着这个话题（见下面「实现」的话题存活；不再关联时话题随之结束）；找不到时拒绝，提示「这个 pane 里的 Agent 不属于任何进行中的飞书话题」。Agent 只能管理这个话题所在绑定的定时任务，其他绑定的定时任务对它来说不存在。ID 可以只写开头几位，例如卡片上的前 8 位；有多个定时任务以它开头时要求写完整。
    - **立即生效的操作**：`list`（这个绑定的定时任务：时间的文字描述、时区和表达式、模式（`into` 的写明是不是当前话题，不是时写出那个话题的标题）、是否暂停、下一次运行时间、任务文字的开头）、`runs`（最近 20 次运行：计划时间，开始的写第几次、晚了一分钟以上时写补跑时间，跳过、错过、失败的写原因）、`pause`、`resume`、`remove`。输出是给 Agent 读的中文，加 `--json` 时是 Bridge 返回的 JSON。暂停、恢复和删除只会让定时任务少跑，不需要确认。
    - **要确认的操作**：`add` 和 `update` 先按「定时任务的存储」里的规则检查模式、表达式、时区和任务文字，然后在调用的话题里发一张确认卡片，命令输出「已在这个话题里发了确认卡片……主人在卡片上点「确认」后才生效；到 … 还没有确认就作废」。`--mode into` 发进的就是调用的这个话题。`update` 只改时间、时区和任务文字，模式和话题不变。`--tz` 默认取运行命令的这台机器的系统时区。
    - **确认卡片**（带标题的蓝色卡片「确认定时任务」或「确认修改定时任务 · <ID>」）依次写：这个话题里的 Agent 提交了一个定时任务（或对哪个定时任务的修改），核对无误后点「确认」才会生效；时间的文字描述（例如「每周一至周五 09:30」）、时区和 cron 表达式，改了时间时另起一行写原来的时间；接下来 5 次运行（时区里的墙上时间，带星期，例如「2026-11-09 周一 09:30」）；任务文字（纯文本，改了时标明「已修改」）；模式（每次开新话题，或者发进这个话题，以及各自的含义）；绑定（名称、机器、工作目录和 Agent 类型）；有效期；「确认」和「取消」两个按钮。任务文字长到卡片放不下（请求体超过 30 KB，算法同 Agent 的回复）时拒绝提交，要求缩短。
    - **点击**：只有应用允许名单里的人点击有效，其他人点击只收到提示，和审批卡片一样。「确认」按卡片上的内容添加或修改定时任务，创建者记为提交的话题和点击人，运行时间从点击的时刻算起；卡片改为「定时任务已生效 · <ID>」（或「定时任务已修改 · <ID>」），列出重新算出的接下来 5 次运行，末尾是「已确认 · @点击人」，不再有按钮。这时绑定已被移除、要修改的定时任务已被删除、`into` 模式的话题已经结束，或者时间不再会运行时，不生效，卡片改为红色，写明原因。「取消」什么都不改，卡片改为「已取消 · @点击人」。
    - **有效期 30 分钟**：没点的卡片到期后改为灰色的「已过期」，不再生效；Bridge 每 30 秒检查一次，到期后、检查之前的点击同样按过期处理。30 分钟够主人看完卡片，或者离开一会儿再回来点；更长的话，卡片上列出的运行时间可能已经过去，一张没人理的卡片会一直挡住这个话题的下一次提交，被诱导的 Agent 提交的卡片也会一直可点。
    - **一个话题最多一张待确认的卡片**：有卡片在等时，新的 `add` 或 `update` 被拒绝，命令告诉 Agent 那张卡片几点过期、请主人先在卡片上确认或取消；已过期的卡片在下一次提交时先改为「已过期」。不同话题各有各的卡片。待确认的卡片记在话题上（`proposal`），Bridge 重启后照样可以点。卡片发不出去时提交失败，不留下记录。
    - **为什么用卡片按钮确认**：Agent 会读网页、文件和群消息，可能被其中的文字诱导去建立定时任务，也可能把时间理解错。对话里的「确认」是 Agent 读到、由 Agent 转述的，被诱导的 Agent 也能替主人「确认」；卡片按钮的点击由飞书直接送到 Bridge，不经过 Agent。Bridge 不给 Agent 发密钥：冒用别的 pane 的进程可以读取、暂停、恢复和删除那个话题所在绑定的定时任务，它提交的卡片会发到那个话题里，但生效仍然要有权限的人点「确认」。Agent 和这台机器的 Bridge 客户端以同一个用户运行，本来就能读到客户端配置里的 token（Bridge 所在的机器上还能读到 Bridge 的状态目录），密钥挡不住有意绕过的程序，只会增加把密钥交给三种 Agent 的复杂度。客户端的 token 保证的是机器：一台机器上的 Agent 碰不到别的机器上的话题。

    **安装**（每台运行绑定 Agent 的机器都要装命令和客户端；给 Agent 的说明是平台上的 skill，见下面「Agent 的说明」）：

    - **客户端**：`bridge-schedule` 只连本机的 Bridge 客户端，所以这台机器要运行客户端（见上面「机器上的客户端」），包括 Bridge 所在的机器。客户端在 `~/.local/state/herdr-bridge/client.sock` 上接收请求；Bridge 不再自己打开 socket，也不再需要 ssh。
    - **命令**：在 Agent 的 PATH 上放一个 `bridge-schedule`，用 Node.js 24 运行 Bridge 目录里的 `bin/bridge-schedule.ts`，例如保存为 `~/.local/bin/bridge-schedule` 并 `chmod +x`：

      ```sh
      #!/bin/sh
      exec "$HOME/.local/share/fnm/node-versions/v24.13.0/installation/bin/node" "$HOME/<Bridge 目录相对 home 的路径>/bin/bridge-schedule.ts" "$@"
      ```

      Node.js 的路径和客户端的 systemd 服务用同一个（见上面「机器上的客户端」），不依赖 Agent 所在 shell 的 PATH 里有没有 Node.js、有的是哪个版本。和客户端一样，这个命令只用 Node.js 自带的模块，Bridge 目录不需要 `node_modules`。脚本里没有哪台机器自己的值：每台机器把 Bridge 目录和 Node.js 放在 home 下的同一个位置（例如都是 `~/apps/herdr-bridge`）时，所有机器用同一个文件。命令和客户端都从 home 目录找 socket，不看 `XDG_RUNTIME_DIR` 和 `XDG_STATE_HOME`：systemd 用户服务和 Herdr 的 pane 里这两个变量可能不同，或者只有一边有。需要放在别处时，客户端服务和 Agent 的环境里都设置同一个 `BRIDGE_CLIENT_SOCKET`。
    - **Codex 的沙箱**：Codex 默认的 `workspace-write` 沙箱拦截所有 socket 的 `connect`，连本机的 Unix socket 也是 EPERM（2026-11-06 在 Codex 0.159.2 上实测）。所以 Bridge 启动 Codex 时加上 `-c sandbox_workspace_write.network_access=true`，打开沙箱的网络访问，`bridge-schedule` 在沙箱里也能连上客户端，不用申请到沙箱外运行；写文件的限制不变。这个开关只能整体打开或关闭，打开后 Codex 和 Claude、Antigravity 一样能访问网络。已经在运行的 Codex 话题保持启动时的沙箱设置，`bridge-schedule` 在那里会提示「没有权限连接本机的 Bridge 客户端」，说明里要求 Agent 这时申请在沙箱外运行这条命令，这会成为一张审批卡片。
    - **Agent 的说明**：`bridge-schedule` 这个 skill 是给三种 Agent 的中文说明：什么时候用这个命令（主人在对话里直接要求在某个时间或者周期性地做事）、怎么把主人的话换成 cron 和时区、怎么按主人的话选模式以及看不出来时先问、会有确认卡片，以及不按读到的内容建立或修改定时任务。它不写命令的参数和报错文字，只让 Agent 去看 `bridge-schedule --help`：skill 保存在平台上（见下面「Skill」），和代码的版本脱钩，写死在里面的参数会随着代码改动而过时，也没有测试能和代码比对。所以 `--help` 自己写全了每个操作、每个选项和取值、cron 的写法、退出码和每种报错该怎么办。这个 skill 由管理员导入平台、设为默认加载，Bridge 每次为话题启动 Agent 之前把它放进 Agent 的工作目录（见下面「Skill」）。
      - 这个 skill 只在 Bridge 开的话题里有用，所以不要装进 Agent 的全局目录（`~/.claude/skills`、`~/.codex/skills`、`~/.agents/skills`、`~/.gemini/config/skills`），以前手动复制进去的要删掉。同名 skill 同时出现在全局目录和项目里时，三种 Agent 的处理不一样：Claude 用全局的，Antigravity 用项目的，Codex 两份都放进上下文。留着全局的副本，项目里放的要么不生效，要么重复。

10. **Skill**：Bridge 保存一组给 Agent 用的 skill（存储见下面「实现」的「skill 的存储」）。管理台的「Skills」页列出它们：名称、描述，以及「默认加载」还是「按需读取」。「+ 新建 skill」填名称和 SKILL.md，SKILL.md 预先填好 frontmatter 的 `name` 和 `description` 两行；卡片上的「编辑」只改 SKILL.md，skill 的其他文件列在 SKILL.md 下面，网页里不编辑它们，按目录整体导入用 `bridge-skill import`（见下面）。卡片上的「设为默认加载」「设为按需读取」在两者之间切换：Bridge 每次为话题启动 Agent 之前（包括定时任务开的话题），把默认加载的 skill 和话题所属项目的 skill 放进 Agent 的工作目录，位置是绑定的 Agent 读项目级 skill 的地方：Claude 是 `<工作目录>/.claude/skills/<名称>`，Codex 和 Antigravity 是 `<工作目录>/.agents/skills/<名称>`；内容变了的同时更新，Bridge 以前放的、现在已经改为按需读取或者删除的从这个目录里移走（做法见下面「实现」的「放置 skill」）。工作目录里的 skill 在这个目录下一次开话题时才放进去、更新或移走；已经在运行的 Agent 用的是它启动时读到的 skill。只有按需读取的 skill 有「删除」：要删除默认加载的 skill，先把它设为按需读取，这样一次误点不会让所有话题都失去它。skill 没有版本历史，覆盖和删除都不能撤销。

    - **`bridge-skill` 命令**：Agent 查找和阅读平台上的 skill、主人在命令行管理 skill，都用这个命令；`bridge-skill --help` 写全了每个操作、需要的环境变量、退出码和每种报错该怎么办。读（`list`、`search <词>...`、`read <名称>`，加 `--json` 输出 Bridge 返回的 JSON）和 `bridge-schedule` 一样只连本机的 Bridge 客户端，由客户端经它的连接转给 Bridge，不需要密钥。`search` 找名称、描述或 SKILL.md 正文里包含所有这些词的 skill，不分大小写，名称或描述里包含的排在前面。`read` 输出 SKILL.md 全文；skill 带有其他文件时，客户端先把整个 skill 放进这台机器的存放目录 `~/.local/share/herdr-bridge/skills/<名称>`（和放置 skill 用同一个，见下面「放置 skill」），命令在正文前写出这个目录和文件列表，SKILL.md 里的相对路径都相对它。管理（`import <目录>`、`export <名称> [<目录>]`、`preload <名称> on|off`、`remove <名称>`）直接调用管理台的接口，要设置 `BRIDGE_URL`（管理台的地址，例如 `http://<控制面>:8080`）和 `BRIDGE_ACCESS_KEY`（状态目录里 `access-key` 的内容），在哪台能访问管理台的机器上运行都可以，不经过客户端。`import` 以目录名为名称，导入目录里的全部普通文件，有软链接或其他特殊文件时拒绝，已有同名 skill 时整个替换它的文件、是否默认加载不变；`export` 写到 `<目录>/<名称>`（不给目录时是当前目录），已经存在时拒绝，不覆盖。
    - **为什么只有管理员能修改 skill**：客户端的 socket 这台机器上的任何 Agent 都能连，包括被网页、文件或群消息里的文字诱导的 Agent；而平台上的 skill 会放进之后所有 Agent 的工作目录或被它们读到。所以 Bridge 对经客户端来的 skill 请求只回答 `list`、`search` 和 `read`，其他操作一律拒绝（「未知的操作」），Bridge 已断开的机器连读也不回答；写 skill 只能用登录后的管理台或访问密钥，和其他管理接口一样。
    - **安装**：在 Agent 的 PATH 上放一个 `bridge-skill`，用 Node.js 24 运行 Bridge 目录里的 `bin/bridge-skill.ts`，例如保存为 `~/.local/bin/bridge-skill` 并 `chmod +x`：

      ```sh
      #!/bin/sh
      exec "$HOME/.local/share/fnm/node-versions/v24.13.0/installation/bin/node" "$HOME/<Bridge 目录相对 home 的路径>/bin/bridge-skill.ts" "$@"
      ```

      和 `bridge-schedule` 的一样：Node.js 的路径和客户端的 systemd 服务用同一个，只用 Node.js 自带的模块，读操作要这台机器运行客户端。Codex 的沙箱已经打开网络访问（见上面定时任务的「安装」），`bridge-skill` 在沙箱里也能连上客户端；`read` 放进存放目录的文件由客户端写，不受 Agent 沙箱的限制。
    - **给 Agent 的入口**：平台上的 `bridge-skill` 这个 skill 告诉 Agent 平台上还有按需读取的 skill、什么时候该查、怎么用 `bridge-skill` 找和读，参数和报错只让 Agent 看 `bridge-skill --help`。它和 `bridge-schedule` 一样由管理员导入、设为默认加载，Agent 一启动就能看到它。

手动添加飞书应用时，需要配置机器人收发消息的权限、下载消息里图片和文件的权限（`im:message:readonly`，已有 `im:message` 或 `im:message.history:readonly` 也可以）、发送和删除消息表情回复的权限（`im:message.reactions:write_only`）、斜杠命令的读写权限（`application:app_slash_command:read`、`application:app_slash_command:write`）、读取群名称的权限（`im:chat:readonly`），以及消息事件 `im.message.receive_v1` 和群信息变更事件 `im.chat.updated_v1`（群改名后绑定跟着改名），通过长连接接收事件；审批与提问卡片还需要订阅卡片回调 `card.action.trigger`（在开放平台「事件与回调」的回调配置中选择长连接接收），然后发布应用。发送和更新卡片使用发消息的权限（`im:message:send_as_bot`），不需要另加权限。COT 接口的文档没有写所需权限，Bridge 按发消息的权限使用；如果实测需要别的权限，COT 创建会失败并退回表情，日志里有飞书返回的错误码。官方接入流程已订阅卡片回调和群信息变更事件，并申请斜杠命令的读写权限、`im:message:readonly` 和 `im:chat:readonly`；已有应用需要在开发者后台开通这些权限、订阅事件并发布新版本，缺少 `im:message:readonly` 时图片和文件下载失败，话题里会提示；缺少 `im:chat:readonly` 时读不到群名，绑定保持原名（建绑定卡片上的群聊叫「群聊」），连接日志里有一条说明。

## 实现

- 后端是 TypeScript，Node.js 24 直接运行 `.ts` 文件（只去掉类型注解，没有构建步骤），`tsc` 只做类型检查；`worktree-branch.mjs` 仍是 JavaScript，因为 worktree-task 插件按这个文件名导入它，它的类型写在 JSDoc 里。状态文件各集合的结构定义在 `state.ts`，控制面和客户端之间的请求定义在 `link.ts`，管理台读的 `/api/state` 定义在 `console-state.ts`，两端都从这里导入。管理台为 React + Vite（`web/`），构建产物为同源 JS/CSS，满足服务端 CSP（不允许内联脚本、内联样式与外部资源）。
- 主题：管理台默认跟随系统的浅色或深色，顶栏的主题按钮在跟随系统、浅色、深色之间切换，选择保存在浏览器的 localStorage，存储不可用时跟随系统。选择浅色或深色时写到 `<html data-theme>`，样式表中这个属性优先于系统设置。`web/public/theme.js` 是同源的经典脚本（CSP 不允许内联脚本），在两个页面的 `<head>` 中先于样式和应用同步运行，首次绘制前就应用保存的选择，并通过 `window.bridgeTheme` 供主题按钮读取和修改；构建时原样复制为 `dist/theme.js`，服务端以 `/theme.js` 提供（`no-cache`）。
- `@larksuite/channel` 负责应用注册、连接、消息规范化和话题内回复；各应用使用独立 Channel 和缓存。
- 连接成功和验证凭证后，Bridge 通过 `/open-apis/bot/v3/info` 读取机器人名称、open_id 和头像地址。头像只接受 https、1 MB 以内、类型为 `image/png`、`image/jpeg`、`image/gif` 或 `image/webp` 的响应（不接受 SVG，因为 SVG 可以携带脚本，而头像与控制台同源），保存在状态目录的 `avatars/` 下，由需要登录的 `/api/apps/avatar` 提供；下载失败只记录日志，保留旧头像，不影响连接。删除应用时一并删除头像。
- 机器上的操作：Bridge 在机器上做的事都经那台机器的客户端完成，客户端的方法是固定的几种（`machine.ts`），没有「执行任意命令」这种方法，运行哪个程序由方法本身决定，Bridge 只给参数（这让 Bridge 能要求的事情有明确的范围，但不是防范控制面被攻破的边界：Herdr 能往 pane 里输入命令，git 的参数（例如 `-c`）也能让 git 执行命令，客户端信任它连上的控制面）：`herdr`（用配置里的 Herdr 和机器的 session 运行 Herdr CLI）、`storeFile` 和 `removeDirectory`（写入和删除附件，见下面「图片和文件」）、`inspectDirectory`（路径是不是 git 仓库的根，是的话返回它的 origin 地址，升级迁移用）、`prepareWorkspace`、`removeWorkspace`、`prepareLaunch` 和 `describeRepos`（项目的话题目录、Agent 的启动准备和仓库描述，每个方法的参数和语义写在 `link.ts`，实现见下面「项目的目录和 Agent 的启动准备」；开话题、换设置、继续做和清理调用前三个，见上面「开话题」）、`placeSkills`（放置 skill，见下面「放置 skill」）和 `stockSkill`（把 Agent 用 `bridge-skill read` 读的 skill 放进存放目录，见上面「Skill」）。Bridge 给的路径是绝对路径或 `~/` 开头，`~/` 由客户端按它所在机器的 home 展开。运行命令的方法返回原始结果（退出码、标准输出和标准错误的最后 2000 个字符），解析 Herdr 的 JSON 和错误码（`agent_blocked`、`agent_not_ready`、`dirty_worktree_requires_force` 等）、决定什么时候做什么，都只在 Bridge 里（`core.ts` 的 `operations`、`topics.ts`、`routing.ts`）。Bridge 用到的 Herdr CLI 命令：`agent list`、`pane list` 读取机器上的终端与 Agent；`workspace list/create`、`tab create`、`agent start`、`agent prompt` 为话题开 tab、启动 Agent 并发送消息，`agent start` 末尾总是带 `--` 和 `prepareLaunch` 返回的参数（权限模式、模型、目录信任等），由 Herdr 传给 Agent；Codex 的参数里固定有 `--no-daemon -c sandbox_workspace_write.network_access=true --dangerously-bypass-hook-trust`：`--no-daemon` 让 Codex 在话题 pane 里运行，而不是连到共享的后台服务（后台服务里的 hook 带的是启动它的那个 pane 的 Herdr 环境变量，session、回复和审批都会报到错误的 pane），`-c` 打开沙箱的网络访问，让 `bridge-schedule` 能连上本机的客户端（见上面定时任务的「安装」），`--dangerously-bypass-hook-trust` 让 Codex 不经确认就运行 `~/.codex/hooks.json` 里启用的 hook（hooks.json 里有新增或改动的 hook 时，例如 Herdr 更新了它的集成之后，Codex 启动时停在「Hooks need review」界面等人确认，飞书话题回答不了这个界面，话题就一直不能就绪；在 Codex 0.159.2 上实测；这些 hook 是主人自己的）；Herdr 原样传递只含字母、数字和 `@%_+=:,./-` 的参数，这些参数不需要加引号；`agent replies` 取回 Agent 的回复；`agent requests`、`agent answer` 读取并回答 Agent 等待中的审批和提问；`agent tool-calls` 取回 Agent 的工具调用记录（COT 的步骤）；`agent send-keys <pane> esc` 执行 `/stop`；`pane remote-answers <pane> on|off` 打开和关闭 pane 的外部回答设置（Bridge 只看命令成功与否）；`pane close <pane>` 关闭定时任务较早运行的话题里 Agent 的 pane（见下面「定时任务」），也用于换设置时结束当前的 Agent。Herdr 遇到不存在的 `--cwd` 会退回 home 目录，所以话题的工作目录一定是 `prepareWorkspace` 返回的、已经存在的目录；保存绑定时不创建目录。
- 项目的目录和 Agent 的启动准备（`workspace.ts`、`launch.ts`、`command-guard.ts`，都只用 Node.js 自带的模块；客户端为了得到仓库地址的 `repoKey`，还加载 `projects.ts` 和它用到的 `core.ts`）：客户端运行 git 时带 `GIT_TERMINAL_PROMPT=0` 和 `LC_ALL=C`，不会停下来要密码，输出是英文；路径只由客户端决定，Bridge 的目录都在 `~/.local/share/herdr-bridge` 下（skill 的存放目录也在这里）。`repos/<主机>__<路径>` 是每台机器上每个仓库唯一的 clone（ssh 和 https 地址指向同一个仓库时共用），每个话题独立的项目在它上面建 worktree；`topics/<话题 id>/<仓库名>` 是话题的 worktree（只有一个仓库时 Agent 就在这个 worktree 里启动，有几个仓库时在 `topics/<话题 id>` 里启动，仓库重名时后面的加 `-2`、`-3`），没有仓库的项目这个目录是空的；`projects/<项目 id>` 是所有话题共用的项目的目录，仓库直接 clone 在里面（只有一个仓库时 Agent 在这个 checkout 里启动），不在 Git 里的文件一直留着，已有的 checkout 只 fetch、不改动。迁移来的项目接管的目录（`adoptedDir`）就是项目的目录，原样使用，缺的仓库 clone 进去。`prepareWorkspace` 对每个仓库先 fetch，再在话题目录里建 worktree：分支在这个 clone 里已有就检出，只有 origin 有就建跟踪它的本地分支，都没有就从 origin 的默认分支建新分支（不跟踪它）；worktree 被清理后再调用，会从分支恢复，已有的 worktree 原样保留。`removeWorkspace` 删除话题的目录和 worktree（没有提交的改动随目录一起删掉），每个仓库里分支没有自己的提交（相对 origin 的默认分支）就删分支，否则保留，只要有一个仓库保留了分支就回答 `branchKept`；工作区已经不存在也算成功。同一个仓库或同一个项目目录上的步骤依次执行，同时开的话题不会重复 clone。clone 先到旁边的临时目录，完整后再改名，中途被终止不会留下半个 clone。`describeRepos` 返回各仓库 clone 里的 README（每个最多 4000 个字符；clone 不下来或没有 README 的仓库不在结果里，一个都没有时失败），由控制面把它们放进提示词，让便宜的模型（见上面「模型服务」）写一句中文描述（最多 50 个字，取回答的第一行）；机器只提供 README，不运行模型。`prepareLaunch` 返回 `herdr agent start` 在 `--` 之后要追加的参数（不含 `--`）并做机器上的准备：Claude 带 `--permission-mode`，有模型时再带 `--model` 和只有这个模型可用的 `availableModels` 设置；Claude 没有跳过目录信任确认的参数，所以启动前在 `~/.claude.json`（设置了 `CLAUDE_CONFIG_DIR` 时在它下面）的 `projects` 里登记目录所在仓库的主 checkout（worktree 沿用主仓库的信任；不在 Git 里的目录沿用祖先目录的信任，没有祖先被信任时才登记它自己），读出、修改、原子替换一次完成，其他字段原样保留，已经登记时不写文件；Codex 带 `--no-daemon`、`-c sandbox_workspace_write.network_access=true`、`--dangerously-bypass-hook-trust`、有模型时 `-m`，以及 `-c 'projects={"<目录的真实路径>"={trust_level="trusted"}}'`（点号形式的键不起作用）；Antigravity 带 `--model` 和 `--settings '{"trustedWorkspaces":["<目录>"]}'`，这里用传入的路径、不解析链接，因为它拿路径和 `$PWD` 比较（这些参数在 Claude Code 2.1.311、Codex、Antigravity 上实测，2026-11-09）。Claude 配置了「只允许执行的命令」时再加 `--tools Bash,Skill,Read --allowedTools "Bash(<命令> *)" --strict-mcp-config`（不带 `--disable-slash-commands`：它会连 Skill 工具和所有 skill 一起去掉，限制了命令的 Agent 就拿不到分配给它的 skill；2.1.311 实测），以及一个 PreToolUse hook：客户端把 `command-guard.ts` 安装到 `~/.local/share/herdr-bridge/hooks/`，hook 只放行恰好是允许的命令、后面可以跟参数的 Bash 调用（参数里不能有 `; & | \` $ < > ( ) \` 和换行，命令和参数之间只能是空格或制表符），其余一律拒绝，不弹确认，任何权限模式下都有效；hook 命令末尾是 `|| exit 2`，hook 运行不起来（程序被删、Node.js 换了位置）时工具调用被阻止，而不是当作没有 hook 放行。几项设置合并成一个 `--settings` 的 JSON。Codex 和 Antigravity 不能限制命令，带 `allowedCommands` 的请求会被拒绝。
- 放置 skill：`Topics.open` 在准备好工作目录、开好 tab 之后、`agent start` 之前，调用 `Skills.place` 向那台机器的客户端发一次 `placeSkills` 请求，每次开话题一次，内容没变时也是这一次。请求里是此刻默认加载的每个 skill 和话题所属项目的 skill（项目里写着、平台上已经没有的名称跳过）的名称、摘要和全部文件（「相对路径 → base64 内容」），连同存放目录、这种 Agent 读 skill 的位置和放法（链接或复制）；这些由 Bridge 决定，放置本身由客户端用 Node.js 的 `fs` 完成（`machine.ts`）。同一台机器上的放置依次执行，因为它们共用一个存放目录。
  - 存放目录：每台机器一份，在 `~/.local/share/herdr-bridge/skills/<名称>`，一个 skill 一个目录。它不能放在任何 Agent 当作全局目录读的位置，例如 Codex 会读 `~/.agents/skills`，放在那里就又成了全局 skill。每个 skill 的目录里有一个 `.herdr-bridge-skill`，记着它的摘要；和请求里的摘要不同时，客户端才把这个 skill 的文件写到存放目录里的一个临时目录（以 `.` 开头）、最后写入摘要，再替换这个 skill 的目录；相同时什么都不写。所以软链接看到的总是一个完整的 skill。存放目录不清理：改为按需读取或者删除的 skill 的目录留在那里，只是不再有 Bridge 放的链接指向它。
  - 工作目录里：Claude 和 Codex 跟随软链接，所以 `<名称>` 是指向存放目录里这个 skill 的软链接，存放目录更新后，这台机器上所有链接看到的就是新内容，用户在这些目录手动开的 Claude 和 Codex 也一样。Antigravity（`agy`）不跟随任何软链接（2026-11-06 实测：单个 skill、整个 skills 目录、`skills.json` 指向的目录都不行），所以放一份内容相同的真实目录，从存放目录复制，目录里的 `.herdr-bridge-skill` 记着复制时这个 skill 的摘要，摘要变了才重写。同一个目录同时绑定了 Codex 和 Antigravity 时，Antigravity 的话题把 Bridge 放的软链接换成真实目录，Codex 的话题之后保留这个目录、在内容变了时更新它，两种 Agent 读的是同一份。默认加载的 skill 一个都没有、工作目录里也没有这种 Agent 读 skill 的目录时，不建这个目录。
  - 移走：放好之后，客户端看一遍这个 skills 目录，Bridge 放的、但不在请求里的 skill（改为按需读取，或者已经删除）被移走：指向存放目录的软链接删掉，带 `.herdr-bridge-skill` 的目录整个删掉。
  - 不覆盖别人的 skill：只有指向存放目录的软链接和带 `.herdr-bridge-skill` 的目录算 Bridge 放的。同名的其他东西（指向别处的软链接、没有这个文件的目录或者文件）保持原样，Bridge 记一条日志写明它的路径；移走时也不碰它们。
  - 以前的版本放的：以前 Bridge 自带 `bridge-schedule`，随代码发布，存放目录在同一个位置，但整个替换，摘要算的是全部 skill，记在存放目录顶层的 `.digest` 里，存放目录里的 skill 没有标记。工作目录里的软链接指向的同样是 `<存放目录>/<名称>`，复制的目录同样带 `.herdr-bridge-skill`（记的是整体的摘要），所以都算 Bridge 放的：平台上的同名 skill 默认加载时，存放目录里这个 skill 没有标记，客户端按平台的内容重写它，链接不变，副本的摘要对不上，也重写；改为按需读取时，它们和其他 Bridge 放的 skill 一样被移走。顶层的 `.digest` 留在存放目录里，不再使用。
  - git 仓库：客户端先用 `realpath` 解析出 skills 目录的真实位置，在那里运行 `git rev-parse --show-toplevel` 和 `git rev-parse --git-path info/exclude`，把放进去的 skill 相对仓库顶层的路径（例如 `/.agents/skills/bridge-schedule`，结尾不带 `/`，这样也能匹配软链接）追加到 `info/exclude`；已经有这一行时不写，文件末尾没有换行时先补一个。`.claude/skills` 本身是指向 `../.agents/skills` 的软链接时（例如 genvi），写进去的是 git 实际看到的 `/.agents/skills/<名称>`。linked worktree 的 `info/exclude` 就是主仓库的那一份，所有 worktree 共用，所以移走 skill 时不删这一行：同一个仓库的另一个 worktree 里可能还放着它。`.gitignore` 是仓库的内容，不改它。工作目录不在 git 仓库里，或者机器上没有 git 时，跳过这一步。
  - 失败：任何一步失败时客户端带回那一步的错误，Bridge 记一条错误日志，话题照常启动，Agent 只是没有这些 skill。
- 图片和文件：`Platforms.download` 通过 Channel 原始客户端的 `im.v1.messageResource.get`（`GET /open-apis/im/v1/messages/<消息 ID>/resources/<file_key>?type=image|file`，视频按 `file` 下载）取回资源。先看响应头的 `content-length`，超过上限时不读响应体；没有长度或长度不对时边读边计数，超过上限就中止。飞书的错误响应体是 JSON，Bridge 读出其中的错误码记入日志（例如 234003 资源不属于这条消息、234038 被数据防泄漏拦截、234043 合并转发或卡片里的资源、234009 外部群）。文件名是消息 ID（只保留字母、数字、`_`、`-`）加序号；图片的扩展名按 `content-type`（未知时为 `jpg`），文件按原文件名，原文件名没有扩展名时按 `content-type`（未知时为 `bin`）。文件由那台机器的客户端写入（`storeFile`，内容以 base64 随请求发过去，最多 60 秒）：根目录必须是 `.herdr-bridge` 目录，解析软链接之后也是，否则拒绝；客户端以权限 0700 创建目录，没有 `.gitignore` 时写入 `*`，顺带删除根目录下除这个话题以外超过 7 天没有变化的目录（失败不影响写入），再以 0600 写入文件，返回文件的绝对路径。话题记录的附件目录取自这个路径，之后由客户端的 `removeDirectory` 删除。`removeDirectory` 只删除直接位于某个 `.herdr-bridge` 目录下的目录，同样按解析软链接后的路径判断；别的路径（工作目录本身、`.herdr-bridge` 本身、更深一层的目录、文件）一律拒绝，所以 Bridge 不能经它删除别处的东西；目录已经不在时算成功。Claude Code 粘贴文字时，会把以图片扩展名结尾、指向已有文件的片段（按换行和空格后的 `/` 切分）自动转成附件，这个读取是异步的，可能晚于 Herdr 粘贴后 300ms 的回车；占位在路径前用全角冒号或全角逗号、路径后用 `]`，路径不会单独成为这样的片段，三种 Agent 都由模型自己读文件。
- 消息表情：Bridge 收下消息后立即贴 `OneSecond` 表情，不在话题队列里排队，并在话题上记录表情 ID。`agent prompt` 成功后记下返回的 Agent `state_change_seq`（Agent 状态每变化一次就增加）；这条消息随后有了 COT 时取消表情（表情先贴上，是为了在话题还在启动 Agent 或排在前一条消息之后时也能立即标记收到）；之后某次轮询中，同一 Agent 为 `idle` 或 `done` 且 `state_change_seq` 大于记下的值时，这一轮结束，取消表情，排在同一话题队列里，同一次轮询有新回复时先发回复。消息没有发给 Agent 时立即取消这条消息的表情；投递前发现 Agent 已不存在、话题结束时，取消该话题全部表情。贴表情失败只记录日志，消息照常投递；取消失败只记录日志，记录照样删除，不重试。
- 回复转发：机器每次轮询（5 秒）拿到 `agent list` 后，对该机器上 `ready` 的话题按 pane 找到它关联的 Agent（见下面的话题存活）；Agent 的 `reply_seq`（最新一条回复的序号）与话题记录的序号不同时，用 `agent replies <pane> --after <序号>` 取回新回复，按序号顺序在话题内回复。每条回复是不带标题的卡片（JSON 2.0）：正文放在 markdown 组件里，卡片占满宽度（`width_mode: fill`，回复里常有代码和表格），摘要（`config.summary`，会话列表和推送通知里显示，Bridge 发的每张不带标题的卡片都有）取正文开头，空白折叠成一个空格，最多 100 个字符。飞书拒绝请求体超过 30 KB 的卡片消息，而卡片 JSON 在请求体里还要作为字符串再序列化一次（引号和反斜杠各占 4 字节，中文字符 3 字节），所以 Bridge 按两次序列化后的 UTF-8 字节数计算，每张卡片在请求体里不超过 28000 字节。放不进一张卡片的回复（Herdr 每条最多保留 64 KiB）拆成多张卡片按顺序发出：在行尾拆分；代码块被拆开时，前一张卡片末尾闭合它，后一张开头用同一个围栏行（含语言标记）重新打开；单独一行就放不下时按字符拆开。被 Herdr 截断的回复在最后一张卡片的正文之后以纯文本提示到 Herdr 查看完整内容。一条回复的某张卡片发送失败时，这条回复后面的卡片不再发送（不在中间留下缺口），日志记录已经发出几张；序号在发送前已经落盘，不会重发。取回与发送和同一话题的消息投递排在同一队列里。Herdr 重启或 handoff 后序号从 1 重新计数，这时取回全部保留的回复，只发送序号不超过 `reply_seq` 的部分。回复由 Agent 的 Stop hook 上报给 Herdr，需要支持 `agent replies` 的 Herdr（本仓库的 fork 版本），并重装集成（`herdr integration install claude` / `codex` / `antigravity-cli`）；旧版 Herdr 的 Agent 没有 `reply_seq`，Bridge 不转发。Antigravity 的回复由 antigravity-cli 集成的 Stop hook 上报，需要装上带 Stop 回复上报的集成（`herdr integration install antigravity-cli`）；旧版集成只上报会话 ID，agy 话题收不到回复。重装集成后，已经在运行的 agy 要重新启动才会加载新的 hook。Herdr 每个 Agent 只保留最近 8 条回复，两次轮询之间更早的回复会丢失。
- COT：COT 的三个接口不在飞书 SDK 里，Bridge 通过 Channel 的原始客户端（`rawClient.request`）调用；响应 `code` 不为 0 或 HTTP 状态出错时按失败处理，日志带飞书的错误码。`agent prompt` 成功且话题没有进行中的 COT 时，`POST /open-apis/im/v1/message_cot?receive_id_type=chat_id`（`receive_id` 为聊天 ID，`origin_message_id` 为这条消息，定时任务的运行为它的运行卡片，`reply_in_thread: true`）创建 COT，记录在话题上后取消这条消息的表情，再用 `PUT /open-apis/im/v1/message_cot` 发 `RUN_STARTED`（`threadId` 为话题根消息，`runId` 为这条消息）。之后的轮询排在话题队列里、在回复、表情、卡片和阻塞提示之后处理 COT：Agent 的 `tool_call_seq`（最新一条工具调用记录的序号）与 COT 记录的序号不同时，用 `agent tool-calls <pane> --after <序号>` 取回新记录，每条「开始」记录变成 `TOOL_CALL_START`（`toolCallId`、`toolCallName`、`title` 最多 200 个字符、`icon`）和 `TOOL_CALL_END`，每条「结束」记录变成 `TOOL_CALL_RESULT`（内容为「完成」或「失败」，`isError`）；Herdr 重启或 handoff 后序号从 1 重新计数，这时取回全部保留的记录，只显示序号不超过 `tool_call_seq` 的部分；取回失败下一次轮询重试。Agent 为 `blocked` 或有等待中的请求时追加一段文字「等待确认」（`TEXT_MESSAGE_START/CONTENT/END`），在引起等待的步骤之后；恢复运行时追加「继续运行」，在之后的步骤之前。一轮结束时追加 `RUN_FINISHED`（`status: done`）并调用 `POST /open-apis/im/v1/message_cot/complete/<cot_id>?message_id=…&reason=done`；`/stop` 追加 `RUN_FINISHED`（`status: interrupted`）后以 `reason=error` 完成（飞书推荐的中断流程）；话题结束时追加 `RUN_ERROR`（「话题已结束」）后以 `reason=error` 完成。每次更新最多 50 个事件，超出时按顺序分多次发送；事件时间戳为毫秒并逐个递增。COT 至多更新一次：序号在发送前落盘，更新失败只记录日志，不重发；完成前先删除记录，更新失败也照样调用完成接口。Bridge 重启后，话题记录里进行中的 COT 在第一次轮询时照常处理，这一轮在重启期间已经结束的，在这次轮询里补上完成。
- `/stop` 和斜杠命令：`/stop` 排在话题队列里，先读一次 `agent list`（Agent 不再关联时按会话结束处理），Agent 为 `working` 或 `blocked` 时才执行 `agent send-keys <pane> esc`。斜杠命令在 `Platforms.start` 连接成功、读取机器人信息之后同步：`GET /open-apis/application/v7/app_slash_commands` 列出应用的命令，缺少的用 `POST` 创建，描述（`description.default_value` 与 `description.i18n.zh_cn`）不一致的用 `PATCH …/<command_id>` 更新，不再有的（`wt`，描述必须和当时注册的一致）用 `DELETE …/<command_id>` 删除，注册和删除各记一条日志；没有变化时不记日志。权限不足（错误码 99991672、99991640）时日志提示开通 `application:app_slash_command:read / write`，其他错误记录飞书的错误码和说明；第一个失败就停止本次同步。命令名和描述只在 `commands.ts` 定义一次，话题的命令识别、接管说明和斜杠命令注册都从这里取。
- 权限模式：Claude 在 auto 模式下由分类器直接放行或拒绝大多数操作，仍然弹出的确认框（例如读工作目录外的文件）带 `personOnly` 标记，不交给 `PermissionRequest` hook，所以话题里几乎不出现审批卡片；有的机器上 Claude Code 默认就是 auto（例如 2.1.285），所以 Bridge 启动 Claude 时总是明确传入 Agent 配置的权限模式。Agent 配置只支持 default 和 auto，没有这个字段的 Claude 配置按 default 处理。权限模式是 Agent 配置的字段，用 `POST /api/agent-configs/save` 修改，不影响已经在运行的 Agent。
- 审批与提问卡片：Claude 和 Codex 的 `PermissionRequest` hook 总是把请求交给 Herdr；pane 当前的 Agent 打开了外部回答设置时 Herdr 让 hook 等待答案，否则立即结束请求，终端照常弹出确认框。Bridge 为新开的话题在 `agent start` 之后（包括 `agent_not_ready`）、话题就绪之前执行 `pane remote-answers <pane> on`，打开失败按启动失败处理；接管时同样先打开再关联。这个设置属于 pane 当前的 Agent，Agent 退出、被释放或换成别的 Agent 时 Herdr 自动清除，live handoff 后保留。Antigravity 没有能等待答案的审批 hook，这个设置对它不起作用：它的命令审批和 `ask_question` 由 Herdr 的屏幕检测报为 `blocked`，话题里只出现下面的阻塞提示。需要支持 `agent requests` 的 Herdr（本仓库的 fork 版本）并重装集成；旧版 Herdr 的 Agent 没有 `request_ids`，Bridge 不发卡片。
  - 发现：每次轮询时，`ready` 话题的 Agent 的 `request_ids` 与话题记录的卡片不一致，就在话题队列里处理：`agent requests <pane>` 取回请求，给这次 `request_ids` 里还没有卡片的请求在话题内发卡片（JSON 2.0 卡片），成功后记下请求 ID、卡片消息 ID 和卡片标题；记录里有、`request_ids` 里已经没有的请求，卡片改为「已失效」并删除记录。卡片至少发送一次：发送失败只记录日志，下一次轮询重试，所以网络异常时可能出现重复卡片。Bridge 重启后，第一次轮询给还没有卡片记录的请求补发卡片。
  - 点击：卡片点击走 Channel 独立的卡片队列（`chatQueue.cardActions: 'separate'`），也不排在话题队列里，所以不会被同一聊天、同一话题里的消息处理挡住。不在应用允许名单里的人点击时只收到提示。允许的点击立即以提示回应飞书（飞书只等几秒），然后在后台用 `agent requests` 确认请求还在、内容与卡片一致，再调用 `agent answer <pane> <请求 ID> --decision allow|allow_always|deny`（拒绝时带 `--message 用户在飞书中拒绝了这次操作`）或 `--answers <问题文本 → 答案列表的 JSON>`，完成后把卡片改为结果。请求已不存在或 Herdr 报 `request_not_found` 时卡片改为「已失效」；其他失败时卡片改为「提交失败」并删除记录，Agent 仍在等待时下一次轮询发一张新卡片。正在由飞书回答的请求不会被轮询改成「已失效」，同一张卡片的第二次点击等第一次处理完。卡片只记标题，所以「已失效」的卡片只显示标题。
  - Channel 会丢弃同一张卡片上同一个人、同一按钮值的重复点击（12 小时内），所以提问没答全时 Bridge 重画这张卡片（保留已选的答案），每次画卡片时按钮值带新的编号，才能再次提交。卡片按钮值里带请求内容的摘要：Herdr 重启或 handoff 后请求 ID 从 1 重新计数，点击时摘要不一致就按「已失效」处理，不会回答到另一个请求上。
  - 阻塞提示：Agent 为 `blocked`、没有等待中的请求，并且连续两次轮询的 `state_change_seq` 相同时，在话题里提示一次「Agent 正在等待终端里的操作，请到 Herdr 中处理」。同一次阻塞（同一个 `state_change_seq`）只提示一次；发消息时已经因为 `agent_blocked` 提示过的，Bridge 再读一次 `agent list` 记下这次阻塞，不再重复。
- 开话题的统一入口：`Topics.begin` 在一个绑定上、以给定的根消息开一个话题，把一段文字交给 Agent，可以带上写进话题记录的字段；话题记录在任何等待之前落盘，记下根消息的 ID 用于去重。用户的根消息（包括待绑定聊天的首条消息）和定时任务的运行都走它：`handle` 先处理 @ 规则、去重、`/adopt`、`/stop`，再调用它，并给用户的消息贴表情；定时任务的运行不贴表情。话题记录同时记下这条根消息（`task`），换设置时用它重新开始。已有话题里的消息走 `Topics.deliver`，它和 `begin` 都在话题队列里用 `Topics.prompt` 投递：必要时开 tab 并启动 Agent、写附件、`agent prompt`、开 COT。
- 开话题：`Topics.open` 在话题队列里依次做 `route`（决定项目和分支，只做一次：话题记录的 `routed` 为真就不再决定，启动失败后的重试沿用；`routing.ts` 的 `nameTask` 是挑项目和起分支名的那一次模型调用，结果的解析只认完全匹配的项目名称）、`workspace`（`prepareWorkspace`，记下 `cwd`；升级前开的话题没有 `routed`、已有 `cwd`，沿用它）、`openTab`（工作区按绑定在每台机器上各一个，记在绑定的 `workspaces` 里，用标签核对）、`place`（放置 skill）、`launchArguments`（`prepareLaunch`）、`agent start`，之后话题就绪。`showCard` 在 `route` 之后画第一张卡片（`topic-cards.ts`），之后每次启动更新同一张。`Topics.change` 处理下拉框的点击（回调值的 `restart` 是 `project` 或 `agentConfig`，选中的项目或配置的 ID 在 `action.option` 里），`Topics.restart` 在话题队列里换设置，`Topics.sweep` 清理，`workspaces.ts` 放着这些共用的纯函数（`workspaceOf` 把项目转成客户端要的形状，没有项目时是 ID 为 `none` 的空项目；`sweepable` 是清理的判断）。话题记录新增 `task`、`routed`、`startCard`、`endedAt`（结束或启动失败的时间）和 `swept`。
- 根消息：`Platforms.send` 调用 Channel 的 `send` 而不带 `replyTo`，SDK 因此调用 `im.v1.message.create` 在聊天里发一条独立的消息并返回消息 ID，使用已有的 `im:message:send_as_bot` 权限。
- 定时任务的存储：状态文件的 `schedules` 集合，每个定时任务记录 ID、绑定 ID、模式（`new` 或 `into`，`into` 另记话题 ID）、cron 表达式、时区、任务文字、是否暂停、创建者（`createdBy`：提出的话题 ID 和确认人的 open_id，都可以省略）、创建时间、`handledUntil`（这个时刻及以前的运行时间都已处理）、已开始的运行次数 `count`，以及最近 20 次运行 `runs`：`due` 计划时间、`at` 处理时间、`outcome` 为 `started`、`skipped`、`missed` 或 `failed`，开始的运行有 `n`（第几次）和 `topicId`，跳过、错过和失败有 `reason`，错过多次时 `last` 为最后一次错过的计划时间。`Schedules` 提供 `add`、`list`（不带运行记录，带下一次运行时间 `next`，暂停时为 `null`）、`runs`、`update`（只改时间、时区和任务文字）、`pause`、`resume` 和 `remove`，返回的都是副本；`add` 和 `update` 检查表达式、时区（必须是 `Intl` 认识的 IANA 时区，保存为规范写法，例如 `asia/shanghai` 存为 `Asia/Shanghai`）、任务文字（去掉首尾空白后不为空，最多 16000 个字符，与能发给 Agent 的消息相同）以及之后还有运行时间，`into` 的话题必须属于这个绑定。删除定时任务不删除它开过的话题。
- cron 表达式：`cron.ts` 自己解析，没有引入依赖：依赖里没有 cron 库，需要的只是 5 个字段加时区换算，几十行代码加测试就能覆盖。支持 Vixie cron 的 5 个字段（分、时、日、月、星期），每个字段是逗号分隔的 `*`、数字或范围 `a-b`，都可以带步长 `/n`，`n/步长` 表示从 n 到这个字段的最大值；月份和星期也接受英文三字母缩写（不区分大小写），星期的 7 和 0 都是星期日；日和星期都不以 `*` 开头时满足其一即可，有一个以 `*` 开头时两个都要满足，与 cron 相同。不支持秒、`@daily` 这类宏和 `? L W #`。运行时间是时区里墙上时间的整分钟，换算用 Node 自带的 `Intl.DateTimeFormat`：一天前和两天后时区偏移相同的日子直接按偏移换算，其他日子逐个时间换算；夏令时跳过的时间那天不运行，重复的时间只在第一次出现时运行。最远找 8 年（2 月 29 日恰逢星期一这类表达式要隔好几年），找不到就算不会再运行。
- 定时任务的定时器：独立于机器轮询的 `setInterval`，每 10 秒检查一次（运行时间精确到分钟，最多晚 10 秒），第一次检查在启动 10 秒后，给飞书连接留出时间；收到 SIGTERM 时停止。每次检查对没有暂停的定时任务找出 `handledUntil` 之后的第一个运行时间，已经到了就找出不晚于现在的最近一个运行时间：它比计划晚不超过 2 小时就运行，否则也记为错过；在它之前到期的都记为错过。`handledUntil` 改为这个最近的运行时间，它和错过的记录在任何等待之前落盘，所以每个运行时间至多处理一次，运行到一半 Bridge 重启的不会重跑。每个定时任务的运行在自己的队列里依次进行，排队期间被暂停或删除的不再运行。时间无法计算的定时任务（例如状态文件里的时区被改坏）暂停并记一条错误日志，不影响其他定时任务。日志只记添加、修改、暂停、恢复、删除、自动暂停和失败，不记每次正常的运行，运行情况看运行记录。
- 定时任务的运行：`new` 模式先看这个定时任务开过的话题里运行序号最大的那个：还在启动，或者在它的话题队列里读到的 `agent list` 中 Agent 为 `working` 或 `blocked` 时跳过（读列表时发现 Agent 已不在，按话题存活的规则结束那个话题，这次照常运行）；然后发运行卡片，用 `Topics.begin` 以卡片为根消息开话题，话题记录带 `scheduled`（定时任务 ID 和运行序号），运行记为开始；Agent 启动失败或任务没发出去时改为失败。开话题的同时清理旧运行：按运行序号保留最近 3 个话题，更早的、仍在进行、`scheduled.messageAt`（话题里最近一条用户消息的时间，`handle` 收下消息时写入）不在 24 小时内的，交给 `Topics.retire`。`into` 模式在话题队列里依次读 `agent list`、发运行卡片、用 `Topics.prompt` 投递，所以和用户消息、轮询的回复转发都不会交错。
- 关闭 pane：`Topics.retire` 在话题队列里先读 `agent list`，话题的 Agent 仍然关联（见下面的话题存活）时才执行 `pane close <pane>`，成功后按话题结束处理（说明、COT 以 error 完成、表情和卡片失效、删除附件目录）；Agent 已不关联时只结束话题，不关闭任何东西；关闭失败时只记日志，话题保持原样，下一次运行再试。用 `pane close` 而不是 `tab close`：用户在这个 tab 里分出了别的 pane 或者把 Agent 的 pane 移走时，只关闭 Agent 的 pane；正常情况下话题的 tab 里只有这一个 pane，Herdr 在 tab 的最后一个 pane 关闭时关闭 tab。
- bridge-schedule 的请求：每台机器的客户端在 `~/.local/state/herdr-bridge/client.sock` 上接收 `bridge-schedule` 和 `bridge-skill` 的请求（环境变量 `BRIDGE_CLIENT_SOCKET` 可以另外指定；所在目录不存在时以权限 0700 创建，socket 的权限是 0600；启动时先删除之前的客户端留下的文件；打不开时，例如路径超过 socket 路径的长度上限，客户端只在日志里记一行，照常连接 Bridge，只是这台机器上的 `bridge-schedule` 和 `bridge-skill` 用不了）。接口是 `POST /schedules/<操作>` 和 `POST /skills/<操作>`，请求和响应都是 JSON。客户端不看请求的内容，把 `{op, body}` 作为 `schedules` 或 `skills` 请求经它和 Bridge 的连接转发（见下面「客户端连接」），Bridge 按这条连接所属的机器调用 `AgentSchedules` 或 `Skills.answer`（只回答读，见上面「Skill」）；客户端回答 200 和结果，Bridge 拒绝时回答 400 和 `{error}`。客户端没有连上 Bridge 时立即回答 503 和「本机的 Bridge 客户端没有连上控制面」。客户端等 Bridge 回答最多 60 秒，超时回答「控制面 60 秒内没有回答」；命令等客户端最多 65 秒，多出的 5 秒是留给客户端的超时回答的，所以 Agent 看到的等待时间和以前直接连 Bridge 时一样是 60 秒。socket 不存在或者没有进程在听时，命令提示「连不上本机的 Bridge 客户端」；没有权限连接时提示可能是 Agent 的沙箱不允许连接。用 Unix socket：只有和客户端同一用户的进程能连，它不在网络上，浏览器也发不了请求，所以不需要另发密钥，机器的身份由客户端的 token 保证。客户端被同一台机器的新客户端替换时，用 `process.exit` 直接退出，不关闭这个 socket：关闭会按路径删除 socket 文件，而新客户端可能在同一台机器上、已经在这个路径上打开了自己的 socket。比较过的做法：在网络上开放接口，不发密钥的话网络上的任何人都能列出任务文字、暂停和删除定时任务、往话题里发卡片，发密钥又要解决怎么交给三种 Agent；让 Agent 把请求写进 Herdr 的 pane 信息、由 5 秒一次的轮询读取，命令拿不到同步的结果，还要 Herdr 新增功能；以前的做法是 Bridge 在状态目录里打开 `agent.sock`，别的机器上的 Agent 经 ssh 到 Bridge 主机上调用，机器名由调用方用 `--machine` 自己填，没有保证，还依赖从数据面机器 ssh 回控制面的凭据。
- 定时任务的命令行和确认：`schedule-command.ts` 是命令行（`bin/bridge-schedule.ts` 运行它），`agent-schedules.ts` 的 `AgentSchedules` 处理 Agent 的请求、确认卡片的点击和过期，卡片在 `schedule-cards.ts`。卡片点击和其他卡片走同一个 Channel 回调：按钮值带 `schedule`（`confirm` 或 `cancel`）的交给 `AgentSchedules`，其余交给 `Topics`；按钮值还带这次提交的 ID，每张卡片不同，Channel 按卡片、点击人和按钮值去重不会误伤。点击立即以提示回应飞书，记录在任何等待之前删除（至多处理一次），之后用 `updateCard` 把卡片改成结果，失败只记日志。时间的文字描述由 `cron.ts` 的 `phrase` 给出：一天最多 6 个时刻时逐个列出；`*/n`、`m/n` 这类均匀跨过整点的步长写成「每 n 分钟」「每 n 小时」；连续的小时写成「HH:MM 至 HH:MM 每 n 分钟」或「每小时一次」；其他按小时和分钟列出。日期按每天、每周几（从周一排起）、每月几日写，限定了月份时前面加「每年 … 月的」；日和星期都受限、且都不以 `*` 开头时写成「每月 1 日和每周一」，有一个以 `*` 开头时写成「每月 1、11 日中的周一」，与 cron 的规则一致。
- 话题存活：`ready` 的话题（新开的和接管来的一样）只在话题机器的 `agent list` 里，它的 pane 上的 Agent 报告 `remote_answers: true` 时算作还关联着这个 Agent，与 Agent 名称和会话无关。Herdr 在 Agent 退出、被释放或换成别的 Agent 时清除这个设置，所以它同时回答了「pane 还在吗」和「还是不是那个 Agent」。接管来的 Agent 名称不由 Bridge 决定，而会话 ID 会在 `/clear` 之类的操作后变化，也可能根本没有（连着后台 app-server 的 Codex），按名称或会话都认不准。另一个好处是话题不会处在「还关联着、但审批卡片已经失效」的状态。发消息前读一次 `agent list`，Agent 不再关联时结束话题并提示；轮询拿到的列表里没有关联的 Agent 时，在话题队列里再读一次 `agent list` 确认后才结束，因为这份列表可能是在话题打开设置之前读的。新开话题和接管都在话题变成 `ready` 之前打开设置。
- 接管：`/adopt` 的话题记录在发卡片之前创建（状态 `choosing`，消息 ID 落盘去重），卡片的消息 ID 记在 `adopted.picker`。卡片内容来自每台启用机器的一次 `api snapshot`：它在同一时刻给出 `agent list` 的全部条目，以及 pane、tab 和 workspace 的列表，名称就从这三者的 `label` 里取（`agent list` 的条目不带 pane 的名称），每台机器只调用一次 Herdr；只列有 Agent 类型的条目。卡片是一个表单：下拉框（`select_static`）的每个选项的值是一段 JSON，带机器、pane、Agent 类型，以及卡片上看到的 Herdr 名称和会话 ID；「接管」按钮提交表单，按钮值只标明这是接管卡片和这次画卡片的编号。提交时用那台机器新的 `api snapshot` 核对这几项，并检查 pane 没有被话题占用（正在启动或已就绪的话题，以及正在进行中的另一次接管，后者只记在内存里）；没有选项或选项值无效时按没选处理。核对通过后依次执行 `pane remote-answers <pane> on`、取回最近一条回复、把话题记为 `ready`（机器、workspace、tab、pane 取自所选 Agent，`replySeq` 为说明里那条回复的序号，`adopted` 加上 Agent 类型和会话 ID），再发说明和更新卡片。选中在话题队列里处理，和话题里的消息排在一起。卡片点击和请求卡片一样走 Channel 的独立卡片队列并立即回应提示；每次画卡片按钮值带新的编号，因为 Channel 按卡片、点击人和按钮值去重，不看表单里选了什么，所以没选就提交时也要重画卡片，下一次提交才不会被当成重复丢掉。`/release` 执行 `pane remote-answers <pane> off`，成功后结束话题；失败时再读一次 `agent list`，Agent 已不关联就按 Agent 消失结束，否则提示稍后重试。
- Bridge 校验允许名单和聊天路由。未绑定的聊天只给允许名单里的人发建绑定卡片，触发卡片的那条消息只在内存里等点击，不写入状态文件；绑定的应用和聊天不接受浏览器传入。
- 消息至多发送一次：消息 ID 在调用 Herdr 之前落盘，重复到达的消息直接忽略；同一话题内的消息按顺序发送，发送失败只记录日志，不重试。回复同样至多转发一次：每条回复的序号在发送前落盘，发送失败只记录日志，不重试。定时任务的每个运行时间至多处理一次（见上面「定时任务的定时器」）。
- skill 的存储：skill 保存在状态目录的 `skills/<名称>/` 下，一个 skill 一个目录，里面是 SKILL.md 和其他文件（脚本、参考资料等）。状态文件的 `skills` 集合只是索引，按名称排序：名称 `name`、描述 `description`（取自 SKILL.md 的 frontmatter）、是否默认加载 `preload`（否则按需读取），以及全部文件的 SHA-256 摘要 `digest`（按路径排序的「路径 → base64 内容」算出，内容变了摘要就变）。正文不放进状态文件：状态文件在几乎每个事件上都整份重写，`/api/state` 也每 4 秒被管理台取一次，正文放进去就会被反复重写、反复传输；只有编辑、读取和放置时才读文件（`skills.ts` 的 `Skills`）。名称按 Agent Skills 的格式：小写字母、数字和单个连字符，最多 64 个字符，也是目录名。SKILL.md 必须以 frontmatter 开头（两行 `---` 之间的 YAML），其中 `name` 和目录名一致，`description` 不为空、最多 1024 个字符。frontmatter 只按 skill 用到的 YAML 读，没有引入 YAML 库：顶层的 `key: value`，值可以是普通文字或者带单、双引号，可以在缩进的下一行继续，也可以是 `|`、`>` 开头的块；嵌套的映射（例如 `metadata:` 下面的内容）不读。文件路径必须在 skill 目录里（不是绝对路径，没有 `..`、`.` 或空的一段），也不能是 `.herdr-bridge-skill`（Bridge 在机器上用这个文件标记自己放的 skill）；内容必须是 base64；全部文件合计最多 1 MiB。不符合时整个写入被拒绝，什么都不改。写入时文件先写到 `skills/` 下的一个临时目录（以 `.` 开头，不会和 skill 重名），再替换原来的目录，然后更新索引；写入是同步的，和写状态文件一样，同一个 skill 的两次写入不会交错。
- 项目、Agent 配置和绑定的管理接口（要求登录或访问密钥，请求体必须是 JSON 对象）：`POST /api/projects/save`（`{id?, name, description, repos[], skills[], workMode}`，没有 `id` 时新建，回答 `{id}`；接管的目录不能经接口设置，只有改成带仓库或每个话题独立时才会放掉）、`/api/projects/remove`（`{id}`）、`/api/agent-configs/save`（`{id?, name?, machineId, kind, model?, permissionMode?, allowedCommands?}`）、`/api/agent-configs/remove`（`{id}`）、`/api/bindings/save`（`{id, defaultProjectId?, defaultAgentConfigId?, requireMention?, enabled?}`，只改给出的字段）和 `/api/bindings/remove`（`{id}`）。`GET /api/state` 带 `projects`（用 `adopted` 布尔值说明是否接管了目录，不给路径）、`agentConfigs` 和不含 `workspaces` 的 `bindings`，没有待绑定聊天的列表。
- skill 的管理接口（要求登录或访问密钥，和其他 `/api/*` 一样）：`GET /api/skills/read?name=<名称>` 返回索引条目加全部文件（`files`：相对路径 → base64）；`POST /api/skills/save`（`{name, text, create}`）把 `text` 写成 SKILL.md，`create` 为真时新建只有这一个文件的 skill，已有同名的拒绝，否则替换已有 skill 的 SKILL.md，其他文件保留；`POST /api/skills/import`（`{name, files}`）按目录整体写入，新建或者替换同名 skill 的全部文件，是否默认加载不变；`POST /api/skills/preload`（`{name, preload}`）设为默认加载或者按需读取；`POST /api/skills/remove`（`{name}`）删除。`/api/skills/` 下的请求体上限是 1,463,640 个字符（1 MiB 的 base64 加 64 KiB 给 JSON 的其余部分），其他请求仍是 100,000 个字符。请求体按 UTF-8 解码，分几次到达、在一个字符中间断开的内容照原文读出。新建、导入、修改、设为默认加载或者按需读取和删除各记一条日志（类别 `skill`）。只有管理员能写入：skill 会被放进之后每个话题的 Agent，网页、文件、群消息里的文字可能诱导 Agent 改写它，影响会扩散到所有话题。
- 状态目录保存机器、应用、项目、Agent 配置、绑定、最近一次新建绑定用的 Agent 配置、话题、定时任务（见上面「定时任务的存储」，包括任务文字）、skill（`skills/` 下的文件和状态文件里的索引，见上面「skill 的存储」）、连接日志和机器人头像。话题只保存首条消息的前 24 个字符作为标题、最近 50 个消息 ID 用于去重、已转发回复的最新序号，尚未取消的表情（消息 ID、表情 ID 和发送时的 `state_change_seq`）、等待中请求的卡片（请求 ID、卡片消息 ID 和卡片标题，例如「权限确认 · Bash」），已提示过的阻塞的 `state_change_seq`，接管来的话题的 `adopted`（卡片消息 ID、接管的 Agent 类型和会话 ID），进行中的 COT（`cot`：COT ID、COT 消息 ID、它回复的消息 ID、prompt 时的 `state_change_seq`、已显示到的工具调用序号、是否显示为等待确认；旧记录没有这个字段，按没有进行中的 COT 处理），写过附件的话题的附件目录（`attachmentDir`，绝对路径，删除后去掉；接管来的 Agent 结束时 Bridge 已经问不到它的工作目录，所以记下来），定时任务开的话题的 `scheduled`（定时任务 ID `id`、运行序号 `n`，有人在话题里发过消息后还有最近一条的时间 `messageAt`），等待确认的定时任务卡片 `proposal`（这次提交的 ID、`kind` 为 `add` 或 `update`、修改时的定时任务 ID `scheduleId` 和修改前的时间、时区与任务文字 `before`、卡片上的 `fields`（模式、`into` 的话题、表达式、时区和任务文字）、卡片消息 ID 和过期时间；确认、取消或过期后删除），以及话题开始时的根消息 `task`（文字和附件的描述，换设置时重新开始用），不保存其他消息内容、图片和文件的内容、回复内容、请求内容和工具调用标题；日志不记录回复内容和请求内容。消息 ID、表情记录、卡片记录、COT 记录和等待确认的定时任务卡片不返回浏览器。
- 客户端连接：客户端（`client.ts`，`bin/bridge-client.ts` 运行它）用 Node.js 自带的 WebSocket 连接 `/api/client`，token 放在 `Authorization: Bearer <token>` 里；控制面用 `ws` 库接受连接（`clients.ts`），升级请求同样要求 Host 在允许范围内。连接上传 JSON 文本帧（`link.ts`），两个方向都可以同时有多个请求：请求是 `{id, method, params}`，回答带同一个 `id` 和 `result` 或者 `error: {message, code}`，两边各自给自己的请求编号，带 `method` 的帧是对方的请求，不带的是对自己请求的回答。不在对方方法集合里的请求得到 `unknown_method` 错误，客户端没有「执行任意命令」这种方法；每个请求有超时，连接断开时进行中的请求立即失败。
  - 握手：连上后客户端发 `hello`，带上协议版本和主机名。控制面先按 token 重新找一次机器（升级之后 token 可能刚被重新生成），再比较协议版本：相同时登记这条连接，回答机器的 ID、名称和心跳间隔（15 秒）；不同时以关闭码断开，在机器上记下原因，原因变化时记一条日志。10 秒内没有 `hello` 的连接被断开。
  - 拒绝和断开都用 WebSocket 的关闭码和一句原因，而不是 HTTP 错误码，因为客户端看不到升级失败的原因：4001 token 无效、token 已重新生成或者机器已移除，4002 版本不一致，4003 Host 不允许，4004 被同一台机器的新连接替换，4005 没有及时握手。
  - 存活：控制面每个心跳间隔向每个客户端发一次 `ping` 请求，下一个间隔内没有回答就断开；客户端连续三个心跳间隔没有收到任何消息，就放弃这条连接重新连接。重连在断开或连接失败后 1 秒开始，每次加倍，最长 30 秒，握手成功后从 1 秒重新算；被拒绝时也照样重试。
  - 同一台机器的第二个连接握手成功后替换前一个，前一个以 4004 断开，它的客户端退出、不再重连。新的优先，是为了让重启的客户端立即接替还没有超时的旧连接；旧的退出，是为了让配置了同一个 token 的两个客户端不会反复互相顶替。
  - 客户端到 Bridge 的请求：握手之后客户端可以调用 Bridge 的 `schedules`（转发 `bridge-schedule` 的请求，见上面「bridge-schedule 的请求」）和 `skills`（转发 `bridge-skill` 的读请求，`{op, body}`，Bridge 只回答 `list`、`search` 和 `read`，见上面「Skill」）。Bridge 按这条连接在登记里找到机器，交给处理函数的是状态里这台机器当前的记录，不读请求里写的机器；握手之前的请求得到「客户端还没有完成握手」，机器已被移除时得到「机器连接不存在」。加上它以后协议版本是 2：只连接、不提供 socket 的版本 1 客户端会被拒绝，管理台显示「客户端被拒绝」和原因，而不是显示在线、这台机器上的 `bridge-schedule` 却用不了。
  - Bridge 到客户端的请求：Bridge 在机器上的操作（见上面「机器上的操作」）都是对那台机器客户端的请求（`Clients.call`）。每个请求带上这次操作的超时：默认 12 秒，`agent start` 70 秒，写附件 60 秒，准备和删除话题的工作目录 10 分钟，准备 Agent 的启动 60 秒。客户端运行的命令在自己的进程组里，到时客户端向整个进程组发 SIGKILL，连同它启动的子进程（例如 `git fetch` 的远程助手）一起结束，回答超时；Bridge 比这个超时多等 5 秒，留给客户端的超时回答，客户端一直不回答时 Bridge 自己按超时处理。机器没有在线的客户端时请求立即失败（错误码 `client_offline`，「机器 <名称> 离线：它的 Bridge 客户端没有连上」），不等超时；请求进行中连接断开时请求立即失败，命令在客户端那边照样受超时限制。机器的轮询只对启用、客户端在线的机器进行，客户端连上时立即轮询一次。加上这些方法以后协议版本是 3：版本 2 的客户端没有这些方法，会被拒绝。`placeSkills` 改为逐个传平台上的 skill、存放目录按 skill 分开、移走不再默认加载的，并加上 `skills` 和 `stockSkill` 以后，协议版本是 4：版本 3 的客户端只认一整包 skill 和一个摘要，也不转发 `bridge-skill` 的请求。项目和 Agent 配置的机器侧（`inspectDirectory`、`prepareWorkspace`、`removeWorkspace`、`prepareLaunch`、`describeRepos`，`nameBranch` 改名为 `askCheapModel`，去掉 `mkdir`、`git`、`exists`）加上以后，协议版本是 5：版本 4 的客户端没有这些方法，也不认新的请求，会被拒绝，所以控制面和所有机器的客户端要一起部署（先升级哪一边都可以，版本一致后客户端自己重连，见上面「机器上的客户端」）。控制面自己调用模型服务（见上面「模型服务」）以后，协议版本是 6：去掉 `askCheapModel`，`describeRepos` 不再运行模型、改为返回各仓库的 README（`{readmes:[{name,text}]}`），版本 5 的客户端回答的是一句描述，所以被拒绝。
  - token 是 32 字节随机数的 base64url，状态文件里的机器只保存它的 SHA-256 摘要 `tokenHash`，`/api/state` 不返回摘要，只返回 `hasToken`。重新生成 token 替换摘要，并以 4001 断开正在连接的客户端；移除机器同样断开它的客户端。
- 管理接口要求登录，校验 Host/Origin；应用 Secret 不回传浏览器。关闭或重启 Bridge 不会停止 Herdr 与其中的 Agent。

当前支持文本、富文本（包括其中的图片、附件和视频）、图片和文件消息，其他类型回复「暂不支持这类消息」。Bridge 在飞书里发的消息都是卡片：自己的状态（未绑定聊天的绑定提示、启动失败、会话已结束、Agent 等待确认或等待终端操作、接管的说明和结束）是不带标题的纯文本卡片，绑定提示里的链接可以点击；Agent 每轮的最终回复是不带标题的 markdown 卡片；定时任务的运行卡片和自动暂停的说明也是不带标题的纯文本卡片；另有带标题的审批、提问和接管卡片、定时任务带「确认」「取消」按钮的确认卡片，以及话题的第一张卡片（带「换项目」「换 Agent 配置」两个下拉框）；从飞书开始的一轮以 COT 显示状态和工具步骤，其他处理中的消息以表情标记；不转发 Agent 的中间文字、思考内容和工具输出。解除绑定会删除它的话题记录，并关闭其中已就绪话题的 pane 的外部回答设置，但不会关闭 Herdr 中的 tab 或 pane；Bridge 只关闭定时任务较早运行的话题里 Agent 的 pane（见上面「定时任务」）。其他话题的自动关闭、把 Agent 产出的图片或文件发回飞书、流式输出和独立手机客户端尚未实现。

审批与提问的限制：Codex 的 `request_user_input`、MCP 表单、Claude 的计划确认（ExitPlanMode），以及 Antigravity 的全部命令审批和 `ask_question`，只提示到 Herdr 处理，不能在飞书回答；不用模拟按键回答任何交互；不能在话题里用普通消息回答提问；Codex 没有「总是允许」。Bridge 不识别「终端先回答了」：Claude 在终端先回答后，卡片保持可点，直到本轮结束才失效，期间点击不会生效（Claude 丢弃迟到的答案），但卡片会显示点击结果。Herdr 不持久化请求，重启或 live handoff 后等待中的请求全部失效，hook 退回终端。Bridge 仍以 5 秒一次的轮询发现请求，不订阅 Herdr 事件。Windows 上的 hook 不上报请求。
