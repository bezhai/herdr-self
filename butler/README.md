# Butler 收集器

工作管家的第一阶段：在运行 open-lark 的机器上常驻运行，从 open-lark 的只读 Agent 接口（`/agent/v1`）把和我有关的飞书消息收进管家自己的存储。它只收集和记录，不分类、不汇总、不提醒，也不调用模型；这些是后续阶段的事（方案见 `.local/prd/butler-overview.md`，本阶段的 spec 见 `.local/prd/butler-message-collection.md`）。

## 收集什么

一条消息满足下面任意一条就收进来，可以同时属于几类：

| 类别 | 含义 |
| --- | --- |
| `mention` | 别人 @我。只 @所有人 的不算；记录里另有 `mentionsAll` 标出消息是否 @所有人 |
| `dm` | 私聊里的全部消息，包括我自己发的和机器人发的 |
| `reply` | 别人回复我的消息：被回复的消息是我发的（`replyTo.senderId` 是我，或者被回复的消息在管家存储里且是我发的） |
| `thread` | 我参与过的话题（我发起，或在里面回复过）里，从我第一次参与起的消息，包括我自己的 |
| `watched` | 关注名单里的群从加入名单起的全部消息 |

收集从收集器第一次启动的时刻开始，更早的消息不收。不在关注名单里、也和我无关的群消息不进存储，留在 open-lark 里。

每条记录有：消息 id、聊天 id、聊天名称和类型（`direct`、`group`、`topic`）、发送者 id、名称和类型（`user`、`bot`、`agent`）、发送时间、话题信息（`threadRole` 为 `none`、`root` 或 `reply`，以及话题根消息 id 和被回复的消息 id）、纯文本和 open-lark 给出的结构化内容（`parts`）、类别、是否我发的、是否已撤回、是否被编辑过、内容是否不可读，以及在 open-lark 网页里打开这条消息的链接。链接的格式和 open-lark 自己的一样：`<网页地址>/messenger/<聊天 id>?message=<消息 id>&position=<位置>`，话题里的消息再带 `&thread=<根消息 id>`，回复定位到根消息的位置。

同一条消息只存一份，按消息 id 更新。编辑和撤回更新这一份记录：撤回后记录跟随 open-lark 的显示，open-lark 保留了原文就保留，否则内容为空，`isRecalled` 为真；撤回和编辑的标记一旦为真就不再变回去，比编辑或撤回更早读到的旧内容也不会覆盖新内容。类别只会增加：一条消息因为当时在关注名单里被收进来，之后这个群移出名单，它仍然是 `watched`。

open-lark 自己的端到端加密消息和密聊消息读不到原文，记录里 `unreadable` 为真，文本是 open-lark 给出的占位文字。

## 为什么要对账

open-lark 的推送（`/agent/v1/events` WebSocket）只推送当下发生的事：没有游标，不能重放，open-lark 重启时连接断开，期间的事件就没了；open-lark 启动时的积压事件在 Agent 端口开始监听之前就发出了。更重要的是，open-lark 补洞、补尾、回填历史、后台同步话题回复时，消息只写进它的数据库，不发事件（后台同步话题回复时只把根消息重新推送一次）。所以只听推送一定会漏。

收集器因此把推送只当作「尽快发现新消息」的手段：推送里的消息立即入库，而完整性靠对账保证。对账读的是 open-lark 已经存下的数据，不管这些数据是推送来的还是事后补的。

### 对账怎样进行

对账一轮一轮地串行进行，触发时机是：启动时；推送连接建立或重连之后（先连上再对账，这样两者之间不会有空隙）；open-lark 的同步状态回到 `live`（并且是 `frontier` 模式）时；之后每分钟一次。每一轮做这些事：

1. **找出有变化的聊天。** 按 open-lark 的排序（置顶在前，其余按最近活跃从新到旧）分页读私聊和群的会话列表，读到最近活跃早于「水位」的会话就停。每个会话的「最后一条消息、最近活跃时间、更新时间」组成一个签名，和上次读完这个聊天时记下的签名不同，就把这个聊天标记为待读。标记存在数据库里，这一轮读不完的下一轮接着读。
2. **按位置读这些聊天，以及每一轮都读关注的群。** 每个聊天记一个位置游标，从游标往后分页读 `GET /conversations/:feedId/messages?afterPosition=…`，每页 100 条。从没读过的聊天，从最新的消息往回读到收集开始的时刻为止。读到的每条消息都交给同一套规则判断类别，不相关的直接丢掉。不只是私聊和关注群：所有有变化的群都按位置读，因为「回复我的消息」可能出现在任何群里，而飞书没有可以按时间补查「回复我的」的接口（open-lark 自己的上下文收集也只能查它的本地账本）。open-lark 正常时这些读取都由它的本地数据库回答，不会访问飞书。
3. **读我参与的话题的变化。** 分页读话题列表 `GET /threads/feed`（我发起、回复过或关注的话题，按最近活跃排序），读到早于水位就停；回复数和上次看到的不同的话题，用 `GET /messages/:id/thread` 取回复。这一步也是收集器得知「我在它停机期间参与了某个话题」的途径。
4. **取回复数变多了的话题。** 不管是推送、按位置读到的还是话题列表里看到的根消息，只要它属于私聊、关注群或我参与的话题，并且回复数比上次多，就取一次这个话题的回复。open-lark 后台同步话题回复时只重发根消息，就是靠这一条补上的。取回复失败时：open-lark 回答 403 或 404（我已经退出这个聊天，根消息没了）就记一条错误，不再取；其他失败只由之后的对账轮次重试，每轮最多一次，失败 10 次后记一条错误放弃。放弃或读不到的话题按已经通报过的回复数记下，同样的通报不会再让它重来；之后根消息通报了更多回复，才算新的工作，重新去取。
5. **@我补扫。** 用 `POST /search/mention-history`（飞书的 @我 搜索）扫描从上次扫到的时刻往前 10 分钟到现在的时间窗口，补上会话列表没有变化、因而第 1 步发现不了的 @我。搜到的消息用 `GET /messages/:id` 取完整内容；open-lark 还没存下的，改读它所在位置附近的那一页（这会让 open-lark 去飞书取），还取不到就记进待补取的列表，之后每轮重试，最多 20 次。飞书搜索失败时 open-lark 返回空结果并标出失败，这种情况记为错误，扫描窗口不前进。这一步和话题列表一样会访问飞书，所以平时每 10 分钟一次，只在启动、重连和同步恢复时立即做。

几个细节：

- **水位。** 第 1 步和第 3 步的「水位」是上一轮完整读完列表的开始时刻再往前留 15 分钟余量，而且只有当这一轮从开始到结束 open-lark 都处于 `live` + `frontier` 时才前进。open-lark 轮询（`polling`）、重连或补数据期间，聊天会带着比当前更早的活跃时间出现；水位停在最后一次健康的时刻，同步恢复后的那一轮就从那里列起，不会漏掉这期间的聊天。
- **重叠和重复。** 每次从游标往前 3 个位置开始读，相邻两页也重叠 3 个位置，open-lark 自己的页还会多给 5 个位置。普通群里的话题回复没有正的位置（位置 ≤ 0），open-lark 按时间把它们混在页里：只包括这一页第一条到最后一条之间（最后一页则是第一条之后）的回复。重叠保证每一页的第一条不晚于上次读到的最后一条，所以没有新的普通消息、只有新话题回复时也能读到。重复读到的消息按 id 更新，没有副作用。话题群里的回复本身有位置，按位置读到。
- **缺口。** open-lark 说某一页有它没能从飞书补上的缺口（`syncState: gap`）时，游标不前进，下一轮重试；连续 3 次仍有缺口就跳过并记一条错误。
- **限流。** 发往 open-lark 的请求一次一个，相邻两个之间隔 100 毫秒；每轮最多读 200 个聊天、30 个话题，剩下的留到下一轮。
- **推送带来的工作。** 推送里的消息让一个话题需要取回复（第一次有了需要取的回复，或者通报的回复数比以前通报过的都多，包括正在取的时候又多出来的），或者带来一个还没有名称的新聊天，收集器会在 1 秒后顺带处理，和对账轮次串行。只处理这些消息新带来的工作：之前就在等的话题（比如取回复失败、等着重试的）不会因为又来了推送就再取一次，否则每条推送都会重试一遍，而每次重试都可能让 open-lark 以我的身份访问飞书。
- **推送里的细节。** 没带消息内容的推送用 `GET /messages/:id` 补全；`sync:complete` 这样的哨兵表示 open-lark 刚在后台补完一个聊天，这个聊天在下一轮按位置读；同一条消息重复推送只更新一次记录；我自己发送时的本地占位消息不入库，等服务端的消息替换它。

### 只读

收集器只用 open-lark 的只读 token，所有请求都经过同一个检查：只允许 GET，以及唯一一个读用途的 POST `/search/mention-history`；任何路径里有 `pins` 的请求都会被拒绝，因为 `GET /conversations/:feedId/pins` 会清除飞书里置顶消息的未读标记。它从不发消息，也读不到 open-lark 的全权限 token 和数据库凭据：配置里只放只读 token，收集器不读 open-lark 的 `app.env`。代价是 token 轮换时要改两处。即使配置里误放了全权限 token，收集器发出的仍然只有上面这些读请求。

open-lark 的 Agent 接口标为旧接口，没有稳定性承诺。收集器启动时用 `GET /agent/v1` 的路由目录检查它要用的路由都在，不全就记一条错误，每分钟重新检查，直到齐了才开始收集。

## 配置和数据

配置文件默认是 `~/.config/butler/butler.env`（`--config` 或环境变量 `BUTLER_CONFIG` 可以换），权限必须是 600，否则收集器和命令行都拒绝运行：

```bash
mkdir -p ~/.config/butler
install -m 600 /dev/null ~/.config/butler/butler.env
# 只取出只读 token，不要把 open-lark 的 app.env 整个复制过来
grep '^OPEN_LARK_AGENT_READ_TOKEN=' ~/.config/open-lark/app.env | sed 's/^OPEN_LARK_AGENT_READ_TOKEN=/BUTLER_OPEN_LARK_TOKEN=/' >> ~/.config/butler/butler.env
```

| 键 | 默认值 | 用途 |
| --- | --- | --- |
| `BUTLER_OPEN_LARK_TOKEN` | 无，必填 | open-lark 的只读 token（open-lark 的 `OPEN_LARK_AGENT_READ_TOKEN`） |
| `BUTLER_OPEN_LARK_URL` | `http://127.0.0.1:8081` | open-lark Agent 接口的地址 |
| `BUTLER_LINK_BASE` | `http://127.0.0.1:3333` | open-lark 网页的地址，用来生成消息链接（open-lark 的 `OPEN_LARK_PUBLIC_URL`） |
| `BUTLER_DATA_DIR` | `~/.local/share/butler` | 数据目录 |

数据是数据目录里的一个 SQLite 文件 `butler.db`（WAL 模式，旁边还有 `butler.db-wal` 和 `butler.db-shm`），目录权限 700，文件权限 600。里面有消息和它们的类别、每个聊天的名称和读取位置、关注名单、跟踪的话题、待补取的 @我、收集器状态和最近 100 条错误。本阶段不做清理，存储会持续增长；`butler status` 显示文件大小，也可以用 `du -sh ~/.local/share/butler` 查看。

## 运行

需要 Node.js 24（用到内置的 `node:sqlite` 和 `WebSocket`），没有 npm 依赖，不需要 `npm install`。

开发时在仓库里直接运行：

```bash
cd butler
node cli.mjs run        # 或 npm start；也可以直接 ./cli.mjs run
```

常驻运行时用复制出去的一份代码（见下面「安装为用户服务」），切换分支或修改仓库不会影响正在运行的服务。`node:sqlite` 仍标为实验特性，命令行会滤掉它的提示。

## 命令行

```bash
./cli.mjs status [--json]
./cli.mjs list [--category mention|dm|reply|thread|watched] [--since 2h] [--until 2026-10-22T18:00] [--limit 50] [--json]
./cli.mjs groups [--search 文字] [--json]
./cli.mjs watch list
./cli.mjs watch add <群名或 id>...
./cli.mjs watch remove <群名或 id>...
```

命令行可以从仓库里运行，也可以用部署的那一份（`~/apps/herdr-butler/cli.mjs`）；两者读同一个配置文件，用同一个存储。

- `status`：收集器是否在运行（看心跳）、推送是否连接和最近一次收到推送的时间、最近一次对账的完成和成功时间、open-lark 的同步状态、@我补扫和话题列表扫到哪里、各类消息的数量、待补取的 @我、关注群数量、存储位置和大小，以及最近的错误。
- `list`：按类别和时间列出消息，新的在前，每条带链接；`--since` 和 `--until` 接受 ISO 时间或 `30m`、`2h`、`7d` 这样的相对时间。
- `groups`：从 open-lark 读出我所在的全部群，显示名称、人数、最近活跃时间，★ 标出关注的群。
- `watch add`：按完整名称、id 或名称中唯一的一段文字加入关注名单，名称对应多个群时列出它们并拒绝；从加入的时刻起收集这个群的全部消息，之前的消息不补。`watch remove` 移出名单，之后的新消息不再因为关注而收集，已收的保留。名单初始为空，改动直接写进存储，正在运行的收集器处理下一条消息时就按新名单判断，不需要重启。

## 安装为用户服务

在运行 open-lark 的机器上作为 systemd 用户服务运行。服务运行的是复制到 `~/apps/herdr-butler` 的一份代码，不是仓库的工作目录，所以切换分支、修改或测试仓库里的代码都不会改变正在运行的服务。配置（`~/.config/butler/`）和数据（`~/.local/share/butler/`）都不在这个目录里，重新复制不会碰到它们。

1. 在仓库根目录复制代码（不带测试）：

   ```bash
   mkdir -p ~/apps/herdr-butler
   rsync -a --delete --exclude test/ butler/ ~/apps/herdr-butler/
   ```

2. 按上面「配置和数据」写好 `~/.config/butler/butler.env`（权限 600）。
3. 把下面的单元文件保存为 `~/.config/systemd/user/butler.service`（Node 路径和 open-lark 服务用的一致，按需调整），然后执行 `systemctl --user daemon-reload && systemctl --user enable --now butler`。

```ini
[Unit]
Description=Butler collector: Feishu messages that concern me, from open-lark
After=open-lark.service

[Service]
Type=simple
WorkingDirectory=%h/apps/herdr-butler
ExecStart=%h/.local/share/fnm/node-versions/v24.13.0/installation/bin/node --disable-warning=ExperimentalWarning cli.mjs run
Restart=on-failure
RestartSec=10
UMask=0077

[Install]
WantedBy=default.target
```

更新：在仓库根目录重新执行第 1 步的 `rsync`，再 `systemctl --user restart butler`。

日志看 `journalctl --user -u butler`：里面有推送的连接和断开，以及每一条错误（同样记在存储里，`status` 能看到）。

收集器停止时会等正在进行的一轮对账结束，最多 5 秒。每次写入都是一个事务，游标只在它之前的消息存好之后才前进，所以被打断的那一轮下次会重做，不会丢也不会重。

## open-lark 重启时

收集器的重启或部署不影响 open-lark。open-lark 重启时推送连接断开，收集器按 1 秒起、最长 30 秒的间隔重连；open-lark 不可达的期间，每轮对账只记一条连接错误。连上之后立即对账一轮（包括话题列表和 @我补扫），补上重启期间丢失的推送和 open-lark 启动时补进来的消息。如果 open-lark 起来之后先处于轮询或重连状态，水位停在重启前最后一次健康的时刻，等同步回到 `live` 再对账一轮。

## 验证

```bash
cd butler
npm test
```

测试用一个假的 open-lark（`test/fake-open-lark.mjs`，HTTP 加 WebSocket）。它按 open-lark 真实的接口形状和怪癖实现：只读 token 的权限、按 open-lark 的规则规划消息窗口（多给 5 个位置）、普通群的话题回复位置 ≤ 0 并按时间混入、话题群的回复有位置、推送可能缺少消息内容、可能重复、有 `sync:complete` 哨兵、话题回复数变化时重发根消息，以及可以只写库不推送。覆盖：

- 推送里的新消息按类别入库；@所有人 不算 @我；不相关的群消息和我在不关注的群里发的普通消息不入库；记录的各个字段和链接。
- 同一消息重复推送只存一份；编辑和撤回更新原记录，更早读到的旧内容不会覆盖它。
- 推送缺少内容时按 id 补全。
- 收集器停机期间的消息（推送丢失和只写库的都有，含私聊、关注群和其中的话题回复、别的群里的 @我和回复我的、超过一页的私聊、停机期间新出现的聊天）在启动后补齐，无关消息不入库；运行期间 open-lark 只写库不推送的消息在下一轮补齐；没有新普通消息时的话题回复也能读到。
- open-lark 重启：推送重连，重启期间的消息补齐。
- 话题回复数变化时补取回复（open-lark 后台同步只重发根消息），正在取回复时又通报的回复也会取到；停机期间我参与的话题群话题里的新回复通过话题列表补齐。
- 取回复失败：404 或 500 的话题在一连串推送下只取一次；403 或 404 的话题记一条错误后不再等待重取；500 的话题只在之后的对账轮次重试，到次数上限记一条错误放弃，之后通报了更多回复再重新去取。
- @我在不关注、会话列表也没变化的群里能被补扫到，所在聊天在同一轮里补上名称；飞书搜索失败时记错误且扫描窗口不前进；open-lark 还没存下的 @我按位置读到，或留到以后重试。
- 关注名单的增删立即生效，新加入的群从加入时开始收集。
- open-lark 不处于 `live` 时水位不前进，同步回到 `live` 时触发对账并补上这期间的消息；open-lark 报告缺口时下一轮重试。
- 只读约束：一整套场景下来，收集器发出的请求里除 `POST /search/mention-history` 外全是 GET，没有任何 `pins` 请求；客户端拒绝其他写方法和 pins 路径。
- 启动时缺少所需路由就记错误、不收集，路由齐了再开始；推送连接一直没有应答时放弃这次连接并重试。
- 状态反映推送的连接和最近时间、对账的最近完成和成功时间、open-lark 同步状态和最近的错误；命令行的 `status`、`list`、`groups`、`watch` 和配置文件权限检查。

测试不连接真实的 open-lark。和真实 open-lark、真实飞书消息的对照（链接能否打开、停机几分钟后的补齐）放在部署后的实测里做。

## 已知限制

- 推送缺失时，话题回复的补齐依赖三条途径：按位置读聊天时按时间混入的回复、根消息回复数的变化、话题列表。关注的普通群里某个我没参与的话题，如果它的回复是 open-lark 在收集器停机期间才后台同步进来的（回复时间早于收集器上次读到的位置），而那次重发根消息的推送又丢了，就补不上。
- 回复我的消息靠 `replyTo` 判断，open-lark 没有存下被回复的消息、管家存储里也没有时，判断不出来。
- 参与话题的判断只往回看话题最近的 500 条回复；在更长的话题里，我很早以前的回复找不到。
- 收集器跟随 open-lark 当前登录的账号，不检查账号是否变化。
