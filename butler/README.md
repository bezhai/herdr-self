# Butler 收集器、加工端和管家机器人

工作管家的这几部分都在运行 open-lark 的机器上常驻运行：

- **收集器**（第一阶段）从 open-lark 的只读 Agent 接口（`/agent/v1`）把飞书消息收进管家自己的存储：和我有关的都收，其余的除了忽略级别的聊天也都存下（见下面「聊天级别」）。它只收集和记录，不调用模型。spec 见 `.local/prd/butler-message-collection.md`。
- **加工端**（第二阶段）把收到的消息交给模型，整理成事项：谁、要我做什么、期限、紧急程度，加上原消息的链接；后续消息归到原事项上，事项结束时记下理由。哪些事归我，按模型从我自己发的消息归纳的「关于TA」和我记下的说明判断。它还在另外的模型通道上让模型给活跃的聊天分级，并在每天早上把前一天每日和即时级别的聊天读一遍，拆成话题存下。见下面「加工端」，spec 见 `.local/prd/butler-processing.md`，分级的 spec 见 `.local/prd/butler-attention.md`，每日读取的 spec 见 `.local/prd/butler-daily-reading.md`。
- **管家机器人**（第二阶段）是管家自己的飞书应用，在加工端的进程里运行：定时把待办汇总成一张卡片发到我和它的私聊里，事项有变化时更新最新的那张，也发分级的卡片。见下面「管家机器人」，spec 同上。
- **命令行**是管家的工具：查看状态、消息、事项、「关于TA」和说明，修改级别、事项、说明和忽略名单。和管家说话在 herdr bridge 里绑定了管家 agent 的飞书群里，那个 agent 用的就是命令行（见「和管家说话」和「命令行」）。

总体方案见 `.local/prd/butler-overview.md`。

## 收集什么

收集器把读到的消息都存下（推送来的，和对账时按位置读到的、取话题回复读到的），只有级别是「忽略」的聊天里和我无关的消息不存。每条消息带着类别，说明为什么收下它，可以同时属于几类：

| 类别 | 含义 |
| --- | --- |
| `mention` | 别人 @我。只 @所有人 的不算；记录里另有 `mentionsAll` 标出消息是否 @所有人 |
| `dm` | 私聊里人发的消息，包括我自己发的。机器人和 agent 在私聊里发的不算：它们按这个私聊的级别收，私聊还没有级别时是即时（见下面「聊天级别」）。发送者类型不明的算人发的，免得人发来的私聊因此只被存下 |
| `reply` | 别人回复我的消息：被回复的消息是我发的（`replyTo.senderId` 是我，或者被回复的消息在管家存储里且是我发的） |
| `thread` | 我参与过的话题（我发起，或在里面回复过）里，从我第一次参与起的消息，包括我自己的 |
| `instant` | 即时级别的聊天从成为即时的时刻起的消息；还没有级别的私聊算即时，从开始收集时算起。私聊里人发的只记 `dm`，所以私聊里的 `instant` 都是机器人和 agent 发的 |
| `flagged` | 每日级别的聊天里，每日读取时模型标出、可能要我去做什么的消息（见「每日读取」）。收集器从不给这个类别：读取标出一条只存下的消息时，用它代替 `stored` |
| `own` | 我自己发的消息，在收集器读到的任何聊天里：推送来的、按位置读到的普通群（不管什么级别）、取回复时读到的话题回复。同时属于别的类别时也带上它，所以私聊里我发的是 `dm` 和 `own` |
| `stored` | 不属于上面任何一类、只因为所在的聊天没有被忽略才存下的消息。它不和别的类别同时出现：后来有了别的类别（比如之后才知道它回复的是我），就换成那个类别；有了别的类别以后再读到它，也不会再加上 `stored` |

`stored` 以外的类别都表示这条消息和我直接相关（`mention`、`dm`、`reply`、`thread`、`own`），来自即时级别的聊天（`instant`），或者是每日读取标出的（`flagged`）：加工端只把这些交给模型（见「加工端」）。`stored` 的消息只作为上下文出现，以后回头找时也能找到。

收集从收集器第一次启动的时刻开始，更早的消息不收。和我直接相关的消息不看级别，在忽略的聊天里也收；忽略的聊天里其余的消息不进存储，留在 open-lark 里。我自己发的消息在哪个聊天里都收：加工端靠它们看出我已经回应过什么（见「加工端」），回复它们的消息也因此在任何群里都能认出是回复我的。话题群不按位置读（见下面「话题群」），我在话题群里发的消息都在我参与的话题里，照样经推送和取话题回复收到，记为 `thread` 和 `own`。从旧版本升级时，存储里我以前发的消息补上 `own`。从有关注名单的旧版本升级时，关注的群变成我定的即时级别，从关注的时刻算起；它们的消息的 `watched` 换成 `instant`；以前机器人和 agent 在私聊里发的消息的 `dm` 换成 `instant`（这些私聊还没有级别，按即时）；关注名单的表删掉。

每条记录有：消息 id、聊天 id、聊天名称和类型（`direct`、`group`、`topic`）、发送者 id、名称和类型（`user`、`bot`、`agent`）、发送时间、话题信息（`threadRole` 为 `none`、`root` 或 `reply`，以及话题根消息 id 和被回复的消息 id）、纯文本和 open-lark 给出的结构化内容（`parts`）、类别、是否我发的、是否已撤回、是否被编辑过、内容是否不可读、表情回复（见下面「表情回复」），以及在 open-lark 网页里打开这条消息的链接。链接的格式和 open-lark 自己的一样：`<网页地址>/messenger/<聊天 id>?message=<消息 id>&position=<位置>`，话题里的消息再带 `&thread=<根消息 id>`，回复定位到根消息的位置。

同一条消息只存一份，按消息 id 更新。编辑和撤回更新这一份记录：撤回后记录跟随 open-lark 的显示，open-lark 保留了原文就保留，否则内容为空，`isRecalled` 为真；撤回和编辑的标记一旦为真就不再变回去，比编辑或撤回更早读到的旧内容也不会覆盖新内容。类别只会增加（`stored` 除外，见上）：一条消息因为当时所在的聊天是即时级别而是 `instant`，之后这个聊天不再是即时，它仍然是 `instant`。

open-lark 自己的端到端加密消息和密聊消息读不到原文，记录里 `unreadable` 为真，文本是 open-lark 给出的占位文字。

### 聊天级别

每个聊天可以有一个级别，决定它的消息存不存、交不交给模型：

| 级别 | 做什么 |
| --- | --- |
| `instant` 即时 | 从成为即时的时刻起，全部消息交给加工端的模型（类别 `instant`）；每天也读一遍，拆成话题存下（见「每日读取」）；即时级别的普通群每轮对账都按位置读（见「对账怎样进行」） |
| `daily` 每日 | 存下；每天读一遍前一天的消息，拆成话题存下，挑出和我的工作有关或者我感兴趣的；可能要我去做什么的消息标出来，交给加工端的模型（类别 `flagged`，见「每日读取」） |
| `store` 只存不看 | 存下，不交给模型，只作为上下文，以后回头找时能找到 |
| `ignore` 忽略 | 不存，只收和我直接相关的消息 |

还没有级别的私聊按即时，从开始收集时算起；还没有级别的群（包括话题群）按只存不看。这样在模型给聊天分级之前，机器人和 agent 在私聊里发的消息和以前一样交给模型，群里和我无关的消息只存下。和我直接相关的消息（@我、人发来的私聊、回复我、我参与的话题、我自己发的）不看级别，照旧收、照旧交给模型，所以聊天的级别定错了，最要紧的消息也不会漏。机器人和 agent 的私聊不算和我直接相关，它们的消息按这个私聊的级别：私聊被定为只存不看以后，它们的消息只存下，不交给模型。人发来的私聊总是 `dm`，私聊的级别对它们不起作用。

级别可以由我定（`level set`，我在和管家说话的群里说，agent 替我执行；或者在每周的分级变化卡片上选，见「和管家说话」和「分级的卡片」），也由模型按「关于TA」和我的说明给每个活跃的聊天定（见「给聊天分级」）。我定过级别的聊天模型不改；我取消自己定的级别（`level clear`）以后，回到模型的判断，模型还没有判断过时回到没有级别（私聊按即时，群按只存不看）。以前的关注名单并进了级别：关注一个群，就是我把它定为即时。

存储里每个有级别的聊天记着：级别、理由（模型的话或者我的话，可以没有）、谁定的（我或者模型）、从什么时候开始（级别不变时不变，即时级别的聊天从这个时刻起的消息是 `instant`），以及模型最后一次给的级别、理由和那次分级的时间。我定了级别以后，模型的那一份也留着：取消我的级别时用它，以后也用它和我定的对比，看我改了模型的哪些判断。级别的改动直接写进存储，正在运行的收集器处理下一条消息时就按新的级别判断，不需要重启。

每次级别的改动另记一行（`level_changes` 表，只增不删，按时间建了索引）：哪个聊天、什么时候、谁改的（我或者模型；取消我定的级别也算我改的）、原来和现在的级别（各带着是谁定的，没有级别时为空），和改完以后这个聊天的理由。级别和定它的人都没变的不记：模型重新分级给出同样的级别、模型的判断记在我定的级别旁边、我把已经是我定的级别再定一次，都不算改动。我纠正的次数从这里数：我定了一个级别，而且聊天的级别因此变了，算一次纠正；把模型给的级别定成我定的同一个级别（确认）、取消我定的级别，都不算。每周的分级变化卡片（见「分级的卡片」）和 `level history`（见「命令行」）读的都是它；`level set` 和 `level clear` 打印每个聊天原来和现在的级别，撤销靠这个（见「命令行」）。

### 表情回复

我常常只用一个表情（Get、OK、DONE、点赞）回应一条消息，所以收集器也记表情回复。每条记录带着它当前的表情回复：每种表情一项，有表情的 key、人数、其中有没有我（`isMine`）和回复的人的名字；open-lark 另外给出的每个人的身份信息和英文名不存。open-lark 给出的消息（推送来的、按位置读到的、取话题回复读到的、按 id 读到的）都带着表情回复，收集器每次记录消息时就用它更新；没带表情回复列表的消息不改动已存的。

表情的变化不会让 open-lark 推送 `message.upserted`，它只推送一个 `reaction.updated`，里面只有消息 id，没有内容，也没有聊天 id；加表情和取消都是这一个事件。收集器只处理管家存储里有的消息：同一条消息在 2 秒内的一串事件（open-lark 每听到一次变化就发一次）只读一次，用 `GET /messages/:messageId/reactions` 取它当前的表情回复，更新记录。这个请求只读 open-lark 自己的数据库；`GET /messages/:id` 也读数据库，但它先向飞书确认我还能看这个聊天（同一个聊天一分钟内一次），所以不用它。请求同样经过只读检查，和其他请求一样一次一个。

每次写入一条消息的表情回复（来自事件，或者来自平常读到的消息）时，其中 `isMine` 为真的表情，如果这条消息的这种表情还没有记过，就记一条「我的表情回复」：哪条消息、哪种表情、管家看到它的时间。每条消息的每种表情只记一次：取消只改这条消息当前的表情回复，取消后再加上也不算新的。「我的表情回复」是加工端的输入（见「加工端」）。

## 为什么要对账

open-lark 的推送（`/agent/v1/events` WebSocket）只推送当下发生的事：没有游标，不能重放，open-lark 重启时连接断开，期间的事件就没了；open-lark 启动时的积压事件在 Agent 端口开始监听之前就发出了。更重要的是，open-lark 补洞、补尾、回填历史、后台同步话题回复时，消息只写进它的数据库，不发事件（后台同步话题回复时只把根消息重新推送一次）。所以只听推送一定会漏。

收集器因此把推送只当作「尽快发现新消息」的手段：推送里的消息立即入库，而完整性靠对账保证。对账读的是 open-lark 已经存下的数据，不管这些数据是推送来的还是事后补的。

### 对账怎样进行

对账一轮一轮地串行进行，触发时机是：启动时；推送连接建立或重连之后（先连上再对账，这样两者之间不会有空隙）；open-lark 的同步状态回到 `live`（并且是 `frontier` 模式）时；之后每分钟一次。每一轮做这些事：

1. **找出有变化的聊天。** 按 open-lark 的排序（置顶在前，其余按最近活跃从新到旧）分页读私聊和群的会话列表，读到最近活跃早于「水位」的会话就停。每个会话的「最后一条消息、最近活跃时间、更新时间」组成一个签名，和上次读完这个聊天时记下的签名不同，就把这个聊天标记为待读（话题群除外，见下面「话题群」）。标记存在数据库里，这一轮读不完的下一轮接着读。
2. **按位置读这些聊天，以及每一轮都读即时级别的普通群。** 每个聊天记一个位置游标，从游标往后分页读 `GET /conversations/:feedId/messages?afterPosition=…`，每页 100 条。从没读过的聊天，从最新的消息往回读到收集开始的时刻为止。读到的每条消息都交给同一套规则判断类别，和推送来的一样，除了忽略的聊天里和我无关的，都存下；这不需要多读什么，这些聊天本来就要读。不只是私聊和即时级别的群：所有有变化的普通群都按位置读，因为「回复我的消息」可能出现在任何群里（我在这些群里发的消息也由此收到），而飞书没有可以按时间补查「回复我的」的接口（open-lark 自己的上下文收集也只能查它的本地账本）。open-lark 的数据库里已经有这些位置的消息时，这一页由它的本地数据库回答；缺少时，它会在这次请求里先去飞书取（实测一页约 4 次飞书调用、1.7 秒）。所以每个聊天每轮最多读 5 页，每轮最多读 50 个聊天，读不完的下一轮从游标接着读。
   - **游标和「读完」。** 游标只认正的位置。open-lark 给出的尾页没有正的 `maxPosition` 时不算读到了：不记游标，聊天保持待读。往后读到 open-lark 说没有更新的消息时，还要确认读到了会话列表显示的那条最后一条消息：它在这次读到的消息里，或者它的位置不超过游标。不在读到的消息里时，它的位置先从管家自己的存储里取（推送来的消息已经存下了，而消息的位置不会变），存储里没有才用 `GET /messages/:id` 查。这个请求读的是 open-lark 的数据库，但它先向飞书确认我还能看这个聊天（同一个聊天一分钟内只确认一次）。它的位置超过游标时，还有一种情况算读完：从游标的下一个位置到它为止，每一个位置上的消息都已经在管家的存储里，这时游标移到它的位置。用 `GET /messages/:id` 查到的那条先照常交给规则判断和记录（open-lark 生成它和生成每一页里的消息用的是同一段代码，记录它和从页里读到它没有区别），它自己就代表它那个位置，只要求它之前的位置都已存下；所以只差一个位置时，查一次就算读完，不管这条消息和我有没有关系。主序列的位置是连续的整数，每个位置一条消息，所以这时主序列里没有漏读的。例外是只有我能看到的临时消息（`isEphemeral`）：open-lark 把它放在它前一条消息的位置上，和那条共用一个位置，所以存下的临时消息不算占了这个位置；查到的最后一条是临时消息，或者是已经删除的消息（每一页都不包括它），也不用来判断。范围长于一个位置时，要这段范围里的每条消息都推送过来或者读到过才凑得齐：管家存下这些消息，忽略的聊天里和我无关的除外（收集开始之前的不存，跨到那时的范围就凑不齐）。没读到就保持游标和待读，之后的轮次重试，连续 5 次都没读到就记一条错误，等这个聊天下次有变化再读。原因是 open-lark 每一页的范围都以它记下的这个聊天的「最后位置」为上限，而这个值可能落后，甚至是 0（见下面「话题群」）：这时它对尾页只回一条位置为 0 的旧消息、不给 `maxPosition`，往后读则回空页并说没有更新的消息，看起来就像读完了。实测还见过这个值连续几轮停在最新一条消息的前一个位置：一个和机器人的私聊里，最新的那条早已推送过来、存进了管家的存储；一个群里，最新的那条和我无关，那时管家还不存这样的消息。旧版本留下的游标 0 当作从没读过，从尾部重新读。
3. **读我参与的话题的变化。** 分页读话题列表 `GET /threads/feed`（我发起、回复过或关注的话题，按最近活跃排序），读到早于水位就停；回复数和上次看到的不同的话题，用 `GET /messages/:id/thread` 取回复。这一步也是收集器得知「我在它停机期间参与了某个话题」的途径。
4. **取回复数变多了的话题。** 不管是推送、按位置读到的还是话题列表里看到的根消息，只要它属于私聊、即时级别的聊天或我参与的话题，并且回复数比上次多，就取一次这个话题的回复。open-lark 后台同步话题回复时只重发根消息，就是靠这一条补上的。取回复失败时：open-lark 回答 403 或 404（我已经退出这个聊天，根消息没了）就记一条错误，不再取；其他失败只由之后的对账轮次重试，每轮最多一次，失败 10 次后记一条错误放弃。放弃或读不到的话题按已经通报过的回复数记下，同样的通报不会再让它重来；之后根消息通报了更多回复，才算新的工作，重新去取。
5. **@我补扫。** 用 `POST /search/mention-history`（飞书的 @我 搜索）扫描从上次扫到的时刻往前 10 分钟到现在的时间窗口，补上会话列表没有变化、因而第 1 步发现不了的 @我。搜到的消息用 `GET /messages/:id` 取完整内容；open-lark 还没存下的，改读它所在位置附近的那一页（这会让 open-lark 去飞书取），还取不到就记进待补取的列表，之后每轮重试，最多 20 次。飞书搜索失败时 open-lark 返回空结果并标出失败，这种情况记为错误，扫描窗口不前进。这一步和话题列表一样会访问飞书，所以平时每 10 分钟一次，只在启动、重连和同步恢复时立即做。

几个细节：

- **水位。** 第 1 步和第 3 步的「水位」是上一轮完整读完列表的开始时刻再往前留 15 分钟余量，而且只有当这一轮从开始到结束 open-lark 都处于 `live` + `frontier` 时才前进。open-lark 轮询（`polling`）、重连或补数据期间，聊天会带着比当前更早的活跃时间出现；水位停在最后一次健康的时刻，同步恢复后的那一轮就从那里列起，不会漏掉这期间的聊天。
- **重叠和重复。** 每次从游标往前 3 个位置开始读，相邻两页也重叠 3 个位置，open-lark 自己的页还会多给 5 个位置。普通群里的话题回复没有正的位置（位置 ≤ 0），open-lark 按时间把它们混在页里：只包括这一页第一条到最后一条之间（最后一页则是第一条之后）的回复。重叠保证每一页的第一条不晚于上次读到的最后一条，所以没有新的普通消息、只有新话题回复时也能读到。重复读到的消息按 id 更新，没有副作用。
- **缺口。** open-lark 说某一页有它没能从飞书补上的缺口（`syncState: gap`）时，游标不前进，之后的轮次重试；连续 5 次仍有缺口就跳过它并记一条错误。
- **限流。** 发往 open-lark 的请求一次一个，相邻两个之间隔 100 毫秒；每轮最多读 50 个聊天（每个最多 5 页）、30 个话题，剩下的留到下一轮。每个聊天限 5 页，是为了让一个积压很多、而 open-lark 又要去飞书补的聊天每轮最多占十来秒，不会像实测那样一个聊天占住一轮好几分钟；一天的积压（几千条）也只需要几轮读完。
- **推送带来的工作。** 推送里的消息让一个话题需要取回复（第一次有了需要取的回复，或者通报的回复数比以前通报过的都多，包括正在取的时候又多出来的），或者带来一个还没有名称的新聊天，收集器会在 1 秒后顺带处理，和对账轮次串行。只处理这些消息新带来的工作：之前就在等的话题（比如取回复失败、等着重试的）不会因为又来了推送就再取一次，否则每条推送都会重试一遍，而每次重试都可能让 open-lark 以我的身份访问飞书。
- **推送里的细节。** 没带消息内容的推送用 `GET /messages/:id` 补全；`reaction.updated` 按上面「表情回复」处理；`sync:complete` 这样的哨兵表示 open-lark 刚在后台补完一个聊天，这个聊天在下一轮按位置读；同一条消息重复推送只更新一次记录；我自己发送时的本地占位消息不入库，等服务端的消息替换它。

### 话题群

话题群（`chatMode: topic`）不按位置读，即时级别的也不读。原因在 open-lark：它每 5 分钟（以及群设置推送时）从飞书重读一遍会话卡片来刷新状态，并把卡片里的 `last_message_position` 写成这个聊天的「最后位置」，取不到时写 0（代码里是字符串 `"0"`，不会被当成「没有」而保留旧值）。话题群的卡片看来没有这个字段：实测在一次刷新之后话题群都变成了下面的样子，普通聊天没有。普通聊天在存下新消息时会把这个值往前推，话题群却被特意跳过，只能等以后某次推送带来的聊天信息再改回来。在这之间，话题群的每一页都只有位置 0 的那条旧消息或者是空页。实测时一次刷新之后，几个话题群同时变成这样，过一会儿又有个别恢复；旧版本据此把三个话题群的游标记成了 0，其中一个从 0 往后读了 100 多页，每页都要 open-lark 去飞书补，一轮用了两分半钟，最后还在空页处停住，漏读了最新的两条。

话题群里和我有关的消息不靠按位置读也能拿到：话题群里的每条消息要么是一个话题，要么在某个话题里（实测两个话题群的 210 条消息里，174 条是话题回复，35 条是话题本身；还有 1 条不是话题回复类型、却带着被回复的消息，open-lark 把它算在那个话题的回复里，取话题回复时会一起取到；这样的消息回复我时记为 `reply`，但不会记为 `thread`）。所以别人回复我，一定发生在我发起或回复过的话题里，由话题列表（上面第 3 步）发现；@我 由 @我补扫发现；推送来的消息也照常入库。代价是即时级别的话题群：我没参与的话题里的消息只能靠推送收到，收集器停机或断线期间的补不上。`level set instant` 把话题群定为即时时会提示这一点。

### 只读

收集器只用 open-lark 的只读 token，所有请求都经过同一个检查：只允许 GET，以及唯一一个读用途的 POST `/search/mention-history`；任何路径里有 `pins` 的请求都会被拒绝，因为 `GET /conversations/:feedId/pins` 会清除飞书里置顶消息的未读标记。它从不发消息，也读不到 open-lark 的全权限 token 和数据库凭据：配置里只放只读 token，收集器不读 open-lark 的 `app.env`。代价是 token 轮换时要改两处。即使配置里误放了全权限 token，收集器发出的仍然只有上面这些读请求。

open-lark 的 Agent 接口标为旧接口，没有稳定性承诺。收集器启动时用 `GET /agent/v1` 的路由目录检查它要用的路由都在，不全就记一条错误，每分钟重新检查，直到齐了才开始收集。

## 加工端

加工端是另一个常驻进程，和收集器共用 `butler.db`。它只读收集器的表，只写自己的表：忽略名单、我的说明、哪些消息和哪些我的表情回复处理过、事项和它们的来源消息、每次模型运行的记录；例外是模型给聊天分级，和我在每周的分级变化卡片上选级别，这两样改的是聊天级别（见「给聊天分级」和「分级的卡片」）；以及每日读取标出的消息，它们的类别从 `stored` 换成 `flagged`（见「每日读取」）。每 10 分钟，它把等着交给模型的消息和我的表情回复（见下面「我的表情回复」）按时间从早到晚分批交给模型，一次一批，每批最多 40 条，直到处理完；我在未结束事项所在的聊天里说了话或加了表情时，不等这 10 分钟（见下面「我回应了就马上处理」）。每天，以及我的说明有变化时，它在处理完新消息之后让模型重写「关于TA」（见下面「关于TA 和说明」）。每 3 小时，以及「关于TA」或说明有变化时，它再把全部未结束的事项交给模型整理一遍（见下面「整理」）。这些一次一个地进行；给聊天分级和每天早上的每日读取各有自己的定时器，不等它们，也不让它们等（见下面「给聊天分级」和「每日读取」）。

### 哪些消息交给模型

只有类别不是 `stored` 的消息交给模型：和我直接相关的消息，即时级别的聊天从成为即时以后的消息，包括还没有级别的私聊里机器人和 agent 发的（见「收集什么」和「聊天级别」），以及每日读取从每日级别的聊天里标出的消息（`flagged`，见「每日读取」）。`stored` 的消息永远不算等着处理，`status` 的待加工数里也没有它们；它们只作为上下文出现，比如同一聊天里在新消息之前的那几条。存储里大部分是这样的消息，所以找等着的消息时只读类别不是 `stored` 的那部分的索引，不读其余的。

### 交给模型什么

每批新消息和我新加的表情，加上帮助理解它们的上下文：同一聊天里在它们之前的 8 条消息（包括只存的消息）、话题的根消息和被回复的消息、表情所在的消息、这些聊天里每个未结束事项最近的 3 条来源消息，以及这个事项开始以后我在它所在的聊天里最近发的 5 条消息和加了表情的消息（到这一批最新的一条为止；这样我的回应即使早已被挤出那 8 条，模型也看得到），全部未结束的事项（编号、标题、谁、要我做什么、期限、紧急程度），以及「关于TA」、我的说明和我最近标记为「不归我」的事项（见「关于TA 和说明」）。只有这一批的聊天里的事项带上这些消息，别的事项只有它们的事实，提示不会随事项的数量变大。每条消息带着收集器记下的事实：发送者和类型（人、机器人、agent），是不是我发的，类别（`mention`、`dm`、`reply`、`thread`、`instant`、`own`、`stored`，说明里写明 `stored` 是和我没有直接关系、只作为上下文的消息），是否 @所有人，@ 了谁（`mentions`，从 `parts` 里的 @ 取名字，@ 我的写成「TA」，@所有人 只由前一项表示；我的 id 取自我发过的消息），我加的表情（`myReactions`，表情的 key），别人加的表情（`reactions`，每种一项，写成「表情×人数」，带最多 3 个名字），在话题里的位置，是否撤回或编辑过，内容是否不可读。表情都是这条消息当前的样子。消息和事项以这一次的编号交给模型（消息是 `m1`、`m2`……，事项是它的编号），消息 id 和链接都不经过模型。一条消息最多给 1500 个字，再长的截断。

### 模型决定什么，代码检查什么

什么算事项，哪些消息属于同一件事（包括把新消息归到已有事项上），紧急程度（`high`、`normal`、`low`），期限，已有事项结束没有、为什么结束，都由模型判断。代码里没有关键词、发送者或群的规则，收集器的类别和发送者类型只作为事实交给模型权衡。

事项的标准写在给模型的说明里：事项是需要我本人去做、回复、决定或跟进的事；只需要我知道的信息（包括状态变化、日程和会议的通知）、成功或完成的通知、没有要做的事的提醒、闲聊（哪怕是在问我）和活动推广都不算。机器人、告警和系统发来的通知默认不算，除非内容明确要我本人去做一件我还没做的事；内容太少、看不出要我做什么的（比如只有标题的卡片）不算。一条消息 @ 了好几个人，或者是即时级别的聊天里的讨论，只有明确要我本人做什么时才算。消息发给了我、@了我或者私聊我，本身不说明这件事归我：模型要按「关于TA」、我的说明和我标记过「不归我」的事项判断是不是该我去做，说明优先于「关于TA」。紧急程度 `high` 是今天就要处理或者影响明显，`normal` 是要处理但不急，`low` 是要做、但可以晚些。批次和整理用同一个标准。

管家只跟踪我还没回应的事。我已经回应过的，不管是回复了消息（哪怕只是答应下来、还没做完），还是加了一个表示收到、知道、同意或完成的表情，我都已经知道了，会自己跟进：模型不为它新建事项，已有的事项关掉，理由写「TA已回应」并说明我怎么回应的。哪个表情算回应由模型判断，说明里举的例子是 Get、OK、DONE、THUMBSUP 算，JOYFUL、ClownFace 这类通常只是表达情绪，不算；代码里没有表情的名单。

我自己发的消息和我加的表情只作为上下文：它们不能单独构成事项，但可以说明我已经回应或处理了某件事。一批里只有我自己的消息和我的表情回复、又没有未结束的事项时，不调用模型，直接记为处理过。

### 我的表情回复

收集器第一次看到我在一条消息上加了某种表情时记一条「我的表情回复」（见上面「表情回复」），加工端把它们和消息一起，按管家看到它的时间排进同一个从早到晚的顺序里分批处理，每条只处理一次：

- 表情所在的消息已经处理过：这个表情是这一批里的一项新内容，排在它所在的聊天里，写成 `{"new":true,"mine":true,"reaction":"Get","on":"m3"}`，`on` 是表情所在的那条消息，它作为上下文一起交给模型；我后来又取消了这个表情时带上 `cancelled`。表情没有自己的编号，模型不能用它构成事项。
- 表情所在的消息还没处理：这条消息交给模型时，它的事实里就有我的表情（`myReactions`），表情不再单独交一次，和消息一起记为处理过。收集器写入表情时同时更新这条消息记录的更新时间，加工端据此只把组提示时读到的记录里已经有的表情算作随消息处理过；模型运行期间才出现的表情，等这条消息处理完以后作为新内容单独交给模型。
- 表情所在的消息只是存下的（`stored`）：它永远不会被处理，表情也就不交给模型；它作为上下文出现时（比如它在一个事项所在的聊天里、是我在那里的回应），我的表情在它的事实里。
- 没有未结束的事项时，我的表情不可能结束什么，和我自己的消息一样直接记为处理过；忽略名单上的发送方的消息上的表情不交给模型；表情所在的消息交不出去（被跳过的消息，或者为了放进提示被截掉了）时，这个表情记为处理过，不再交。

模型只输出一个 JSON 对象：`new` 是新事项（标题、谁、要我做什么、期限、紧急程度、来源消息的编号），`updates` 是对已有事项的修改（新归入的消息、改动的字段、关闭及理由）。加工端只采纳引用这一批编号的部分。下面这些不采纳，各记一条错误：引用了不存在的消息或事项，新事项没有引用任何一条别人发的新消息（只引用了旧消息或我自己的消息），关闭事项但没有写理由。模型写的文字里的网址换成「[链接]」，事项的链接由加工端用它最早的来源消息生成，和收集器的消息链接相同。采纳的部分和这一批消息的「已处理」标记在同一个事务里写入。

### 我回应了就马上处理

我在群里回一句、或者加个表情，事项就该结束了，等下一个 10 分钟太慢。所以加工端除了每 10 分钟一轮，还每 15 秒查一次存储（一条 SQL 查询，只读我发的消息和我的表情回复，不读聊天里别的消息：在一个 52 万条消息、其中 4.3 万条交给模型的存储上约 11 毫秒，以前的写法要 63 毫秒）：在未结束事项所在的聊天里、从最早的未结束事项开始以后，有没有等着处理的我的东西：我发的、还没处理的消息，带着我的表情、还没处理、要交给模型的消息，或者等着交给模型的我的表情回复（忽略名单上的发送方的消息上的不算）。只存的消息即使带着我的表情也不算：它永远不会被处理，算上它的话这个检查会一直成立。有，而且没有一轮正在进行，就马上开始一轮。这一轮就是平常的一轮：所有等着的消息（包括别人的）按同样的批次和上下文处理，到了时间也写「关于TA」和整理。只有别人的消息，或者我在没有未结束事项的聊天里说的话，不触发，等下一个 10 分钟。一轮正在进行时不另开一轮，它处理完手上这一批会接着处理新来的。上一轮哪里失败了（某次模型运行、「关于TA」或整理），快速检查就停下，直到 10 分钟的一轮完整成功一次：模型出问题时重试的频率和以前一样，不会每 15 秒问它一次。模型一次运行要十几到二十秒，所以我回应以后，事项一般在半分钟左右结束。

### 整理

批次里的模型只在事项所在的聊天来了新消息时才判断它结束没有，没人再提的事项会一直开着。所以加工端定期整理：一轮的批次（和要写的「关于TA」）处理完以后，如果上次整理已经过了 3 小时（`BUTLER_REVIEW_EVERY`），或者还没有整理过，或者「关于TA」或我的说明和上次整理时用的不一样了，就把全部未结束的事项交给模型。部署后的第一轮就会整理，加工端停了超过这个间隔再启动时也一样；「关于TA」第一次写出来、重写了，或者我加了、删了一条说明，紧接着也整理一遍，现有的事项马上按它重新判断。这一轮的批次失败停下时不整理，模型这时用不了，等下一轮。

每个事项交给模型的是：编号、标题、谁、要我做什么、期限、紧急程度、开始的时间、最近一条消息的时间、所在的聊天，以及它最近的 3 条来源消息；它开始以后我在它所在的聊天里最近发的 5 条消息和加了表情的消息，这样我在热闹的群里的回应即使被挤出了最新的消息，模型也看得到；再加上每个所在聊天最新的 8 条消息，包括我自己发的；还有「关于TA」、我的说明和我标记为「不归我」的事项。消息的编号、事实和截断都和批次一样，忽略名单上的发送方同样不出现。

模型判断哪些事项不用我再管：我已经回应过（按上面的标准，回复或者表示收到、同意、完成的表情，只是答应下来也算，批次里判断结束时也一样）、已经办完、过时、被后来的事项或消息取代、不归我管（包括按「关于TA」、我的说明和我标记过「不归我」的事项不该我做的），或者按上面的标准本来就不算事项。事项的标题和要我做什么是之前的批次写的，可能把通知或闲聊写成了要做的事，所以说明要求模型以消息本身为准。它关掉这些事项并写明理由，也可以修改留下的事项的紧急程度、标题、要我做什么和期限。整理不新建事项，回复里的新事项不采纳；其余部分按批次里修改事项的同一套规则检查（引用不存在的事项、没有理由的关闭都不采纳，各记一条错误）。整理关掉的事项和批次里关掉的一样记为模型关掉，出现在下一份汇总里。判断全由模型做，代码里没有按时间、发送者或关键词关事项的规则。

一个提示放不下全部事项时（超过 80 KB），分几部分整理：同一个聊天的事项排在一起，从前往后取放得下的事项（放不下就减半），每部分是一次模型运行，结果单独写入。某一部分失败时记一条错误，前面几部分的结果保留，这次整理不算完成，下一轮再整理，不在同一轮里重试；整理失败不影响批次。加工端停止时不再开始新的一部分，这次整理也不算完成。上次完成的整理（时间、整理了多少事项、关掉多少个，以及用的是哪一版「关于TA」和哪几条说明）和之后的失败记在存储里，`status` 显示它们。

### 关于TA 和说明

模型只看得到「有人 @我」「机器人私聊发给我」这样的事实，分不出一件发给我的事是不是我的事，也不知道哪些聊天我关心。所以加工端让模型归纳一段简短的「关于TA」，分两部分：工作（我的角色、所在的团队、在做的项目和系统、常一起做事的人、哪些事归我、哪些通常不归我）和兴趣（工作以外我关心的话题），都是一项一行，工作最多约 400 字，兴趣最多约 200 字。存下的是一段文字，两部分分别以「【工作】」「【兴趣】」开头，看不出兴趣时只有工作；批次、整理和分级读到的都是这一段文字，不分开读。

交给模型的有这些：

- 我最近发的消息（连同所在聊天的名称和类型），每条带着它回复的那条消息，没有回复的带着同一聊天里它前面的那条消息，忽略名单上的发送方不出现。消息多到一个提示放不下（80 KB）时，只给放得下的最新的那些（最多看最近 1000 条）。
- 我在各个聊天里的参与情况：最近 30 天我发过消息、被 @ 过或者加过表情的聊天，我发得多的在前，然后是最近一周有消息、我设了免打扰的聊天，一共最多 60 个。每个给出名称、类型、人数、是否免打扰、我在这里发的消息数、被 @ 的次数、加的表情数和它现在的级别（我定的还是模型定的，或者还没有分级）。这些数字和分级用的出自同一处（见「给聊天分级」）；每天多少条消息和机器人的占比是聊天本身的情况，不说明我做什么，所以不给。
- 我的说明，和我标记为「不归我」的事项（见下面）。
- 纠正题：我亲自定过级别的聊天，每个带着我定的级别、模型之前给它的级别（有的话）和我说的理由（有的话）。
- 最近一次重做纠正题时做错的题（见「给聊天分级」里的「纠正题」）：我定的级别、模型的回答和它当时的理由。那次以后我又改了级别或者取消了的题不再给。
- 上一版「关于TA」，用来对比这一版新加了什么。

纠正题和做错的题说明我看重什么、不看什么。提示要求模型把它们推广成一类聊天、通知或话题的说法，写进「哪些事归TA」「哪些通常不归TA」或兴趣，让分级以后遇到同类的聊天也能分对，而不是逐个列出聊天和级别（那样重做纠正题时就成了照抄答案）。推广出来的话只写进「关于TA」，从不写进说明：说明只记我的原话，按钮上的一次纠正没有说原因，推广是模型的推断，不能冒充我说过的话。推广错了，我再用说明纠正。

模型同时列出这一版比上一版新归纳出的内容，最多 5 条，每条一句话；只是换了说法的不算，没有新内容时是空的。写完以后，加工端把这一版的文字、新内容和写的时间交给机器人（`onProfile`），新内容不为空时机器人私聊发给我（见「管家机器人」）；新内容也记在存储里。

模型写的文字和别的模型文字一样，网址换成「[链接]」，长度有上限。「关于TA」和它写的时间、根据多少条消息、用了哪几条说明、新归纳的内容记在存储里（`meta` 里的 `profile`），`butler profile` 显示它。

什么时候写：还没有时第一轮就写（部署后的第一轮，在批次之后、整理之前，所以紧接着的整理就按它判断）；之后每天一次（`BUTLER_PROFILE_EVERY`）；我的说明和写它时用的不一样了，下一轮就重写。这一轮的批次失败停下时不写。写失败时记一条错误，下一轮再试，同一轮里不重试；它不挡消息的处理，整理照常进行，用的是之前那一版（或者没有）；失败时不通知机器人。每次写也是一次模型运行，记在 `model_runs` 里（`kind` 是 `profile`）。我发的消息、说明、标记为不归我的事项和我定过级别的聊天都没有时不调用模型；只有参与情况（比如有人 @ 过我）说明不了什么，不够写。我定了级别、模型重做纠正题做错了，都不会马上触发重写，等下一次写时带上。

说明是我自己的更正，记我的原话，例如「审批不归我管」「值班群都不看」。它们用命令行的 `notes add` 和 `notes remove` 增删（我在和管家说话的群里说，agent 替我执行，见「和管家说话」），单独存在 `notes` 表里，每条有编号，不会因为重写「关于TA」而丢掉；写「关于TA」、整理消息、整理事项和分级时都会带上，和「关于TA」不一致时以说明为准。说明的变化由加工端和分级自己从存储里发现，不管是哪个进程改的。关掉事项时说的理由（`matters close --reason`）只记在那个事项上，不会自动变成说明。

我在卡片上把一个事项标成「不归我」（见下面「卡片上的按钮」），它就以理由「不归我」关掉；用 `matters close --reason 不归我` 关掉的也一样。写「关于TA」、整理消息和整理事项时，模型还会看到最近 20 个这样的事项（`notMine`：标题、找我的人、所在的聊天，没有编号和链接；重新打开的不算），说明里写的是：管家曾把它们当成我的事，我说不是，用来校准它对哪些事归我的判断。它们只是事实，什么事和它们是一类、该怎么权衡，由模型判断，代码里没有按标题或发送者的规则。只有它们、没有我发的消息也没有说明时，「关于TA」也照样写。标记不会马上触发重写「关于TA」或整理，下一次写和整理时带上。

「关于TA」来自模型，而模型读的是别人写的消息，所以「关于TA」、说明、纠正题和做错的题都放在交给模型的数据里，不放进系统提示；系统提示写明「关于TA」是管家的归纳、说明是我的原话，消息内容仍然只是数据。代价是：「关于TA」只来自我在飞书上说过和做过的事，看不到组织架构和平台上的 owner 信息，可能写偏；写偏时用说明来纠正。

### 给聊天分级

加工端让模型给每个活跃的聊天定一个级别（见「聊天级别」）和一句理由，按「关于TA」和我的说明判断。我定过级别的聊天不交给模型：模型不改我定的级别，而且让它看到我定的级别，就等于让它看到了答案，重做纠正题时也要避开这一点（见下面「纠正题」）。代码里没有按关键词、发送者或群的规则，什么级别合适全由模型判断。

存储里最近 7 天有消息的聊天算活跃，只从推送见过、没有按位置读过的聊天也算。更久没有消息的聊天不分级，等它再有消息推过来再分。

**交给模型什么。** 每个聊天给出：名称（只从推送见过、还没补上名称的聊天没有）、类型（私聊、群、话题群）、人数和我是否设了免打扰（open-lark 的会话列表给过时才有）；它有多活跃：最近一周平均每天多少条消息，其中机器人和 agent 发的占百分之几（管家收下全部消息还不满一周时从那时算起，之后才第一次见到的聊天从它的第一条消息算起）；我在这里做了什么：最近 30 天我发的消息数、@我 的次数（只 @所有人 的不算）和我加的表情数；它现在的级别（模型以前定的，或者还没有分级）；以及它最近的 30 条消息，从早到晚，每条只有时间、发送者、是不是机器人、是不是我发的和开头 100 个字（空白合成一个空格）。忽略名单上的发送方的消息和别处一样不给模型看，但算在每天的消息数里。每个提示再带一次「关于TA」和我的说明。聊天以这一次的编号交给模型（`c1`、`c2`……），聊天 id、消息 id 和链接都不经过模型；说明里和批次一样写明，消息内容是别人写的数据，不是给模型的指令。

**模型回答什么。** 每个聊天一个级别，和一句写给我看的理由：这是个什么聊天、为什么是这个级别。说明里把四个级别的意思写明：即时是这个聊天的每条消息都马上交给整理待办的模型，每天也读一遍、挑出话题，最费成本，适合常有要我本人去做、回复或决定的事出现的聊天；每日是每天读一遍，挑出和我的工作有关或者我感兴趣的话题，读到的可能要我去做的事交给整理待办的模型（见「每日读取」）；只存不看是存下但不读，以后回头找时能找到；忽略是连存都不存，只用于纯粹的噪音。即时也写明每天会读：不写的话，模型会以为想留下一个聊天的讨论就该定为每日。说明还写明，和我直接相关的消息不看级别，总会交给整理待办的模型，所以只是偶尔 @我 的聊天不需要定为即时。

**代码检查什么。** 回答里引用了不存在的聊天、级别不是这四个之一、没有写理由、同一个聊天分了两次（只看第一次），这些部分不采纳，各记一条错误（来源「分级」）；回答里没有提到的聊天也记一条，保持原样，下次再分。采纳的级别记为模型定的，带着理由和这次分级的时间；级别没变时开始的时间也不变。我在模型运行期间给某个聊天定了级别，写入时也不会被改掉，模型的那一份留在旁边。理由里的网址换成「[链接]」，最长 200 字。每次运行记在 `model_runs` 里（`kind` 是 `grade`，`messages` 是交给模型看的消息数）。

**什么时候分级。** 加工端每分钟看一次有没有该分级的聊天：

- 收集器开始存下全部消息不满 2 天时，什么都不分。分级要用每个聊天最近的一段消息作样本，样本只来自开始全收以后存下的消息，不去 open-lark 读历史。开始全收的时刻从存储里算，是管家第一次见到一条只存不看（`stored`）的消息的时间；不按这条消息发出的时间算，因为第一次按位置读的聊天会往回读到开始收集的时刻，这样存下的消息发出得早得多（实测开始全收几分钟后，最早的一条只存的消息发于两天前）。
- 满 2 天以后，还没有级别的活跃聊天在下一次就分；之后才出现的聊天，等它最早的一条消息满 1 天再分，好有一天的样本。
- 每个聊天在模型上次给它分级一周以后再分一次。这是按聊天各自算的，不是每周统一跑一遍：一次分级中途失败时，已经分好的聊天不用重来。
- 我的说明变了（加了或删了一条），在这之前分级的聊天重新分。说明要保持不变满 1 小时才开始，连着改几条只重分一次。变化由正在运行的加工端发现，它停着时改的说明，等它启动看到以后再算这 1 小时。「关于TA」每天重写，重写本身不触发分级，每周的分级用的是最新的那一版。
- 模型定为即时的聊天，最近一小时里交给批次的消息（不算忽略名单上的发送方的）达到 30 条，而模型上次给它分级已经超过一小时，就马上重新分级。我定为即时的不算。
- 我用 `level grade` 要求重分（见「命令行」）。

一次分级把这时该分的聊天按活跃程度从高到低排好，一个提示放下尽可能多的聊天（和批次一样以 80 KB 为限），但最多 25 个，每个提示是一次模型运行。限个数是因为模型要给每个聊天写一句理由：消息少的聊天占地方小，只按大小放，一个提示能放下近百个（实测有一个放了 91 个），回答就会很长，既可能超过 herdr 留下的 64 KiB 被截断，理由也会写得潦草。一个聊天单独都放不下时，只给它较新的那一半消息，直到放得下。

**另一条模型通道。** 分级和重做纠正题在加工端的进程里有自己的定时器，和批次、整理、「关于TA」各自直接调用模型，从不等它们，它们也不等它。两边各自一次一个：批次、整理和「关于TA」在一轮里依次进行，一轮没结束时不开始下一轮；一次分级或重做纠正题没结束时也不开始下一次。每日读取也有自己的定时器（见「每日读取」），所以模型机器上最多同时运行三个 claude，各在自己的 herdr 工作区里（见「模型在哪里」）。全量分级要连着跑十几次模型，和批次排在一起待办会被堵住；只给批次更高的优先级也不够，正在跑的分级不能打断。

**失败时。** 一次运行失败（连不上、超时、没有回复、回复不是要求的 JSON），这次分级就停下，记一条错误，已经分好的聊天保留。失败以后，之后的提示放的聊天减半（最少一个），成功一次后恢复。只有一种失败不让这次分级停下：一个聊天单独一个提示，模型回答了，但回答用不了；这个聊天留到下次，这次接着分后面的。如果紧接着的那次运行也失败，就算模型的问题，停下。这样一个总让模型答不好的聊天，最后只连累它自己。一次分级只要有聊天没分成（运行失败，或者回答里没有、没采纳），下一次自动分级至少等 10 分钟，模型出问题时不会每分钟问它一次。加工端停止时等正在运行的那一次（和批次一起最多等 20 秒），不再开始下一次；被打断的那次不记，没分成的聊天下次再分。

上次分级的时间、几个聊天、分成了几个和没分完时的错误记在存储里（`meta` 里的 `grading`，同一个键里还有加工端上次看到的说明和发现它们变化的时间），`status` 显示它们、模型定了级别的聊天数，和下一次什么时候分。

**告诉机器人。** 每次分级只要分成了至少一个聊天，加工端就把结果交给机器人（`onPass`）：这次分级的时间，它是怎么开始的（`by`：加工端到了时间自己开始的是 `schedule`，我要求的是 `request`，即 `level grade`；它在命令行自己的进程里运行，那里没有机器人），分成和没分成的聊天数，以及模型给的级别变了的聊天（名称、原来的级别、现在的级别和理由；第一次分级的聊天没有原来的级别）。级别和上次一样的不在里面。机器人据此决定什么时候发分级的卡片（见「管家机器人」）。机器人出错只记一条错误，不影响分级。

**纠正题。** 我亲自定过级别的每个聊天都是一道带答案的题，从关注名单迁移来的 4 个群也在里面；题库就是存储里我定的级别，不单独存。重做纠正题时，模型拿到的提示和分级完全一样：同一个系统提示，同样的聊天事实和最近的消息，同一份「关于TA」和说明，只是这些聊天都显示为还没有分级，我定的级别、我的理由和模型以前给的级别都不给，模型看不到答案。它的回答不改任何级别，只逐个和我定的级别比：一样算做对；不一样、回答里没有这个聊天、给的级别不认识，或者这个聊天单独一个提示也答不出来，都算做错。每次重做记下时间、题数、做对的题数和每道题我定的级别、模型的回答和理由（`exams` 和 `exam_answers` 两张表，最新的在前），模型运行记在 `model_runs` 里（`kind` 是 `exam`）。最近一次做错、之后我没再改过级别的题，交给下一次写「关于TA」（见「关于TA 和说明」）。

重做纠正题和分级用同一个定时器，一次一个，加工端每分钟看一次，这时没有要分级的聊天才做；分级失败以后等待重试的那段时间里也可以做，不会被一个总也分不成的聊天挡住。什么时候重做：

- 「关于TA」重写了，或者我的说明变了以后；而且只有「关于TA」的文字、说明或者题库（哪些聊天、我定的什么级别）和上次重做时不一样才做。重写出来的文字一样、别的也没变，不用重做。我新定了级别、「关于TA」还没重写时也不做：等下一次写的「关于TA」从这次纠正里学过以后再做，这样做对的比例衡量的始终是「关于TA」。
- 说明变了以后，等加工端按新的说明重写完「关于TA」再做，免得用旧的「关于TA」配新的说明做一次、紧接着又做一次。
- 两次之间至少隔 1 小时，失败的那次也算。
- 还没有写过「关于TA」、没有我定的级别，或者开始全收不满 2 天时不做。部署以后，有「关于TA」和我定的级别就先做一次，作为起点。

一次运行失败，这次重做就停下，不记结果，记一条错误（来源「分级」），1 小时后再试。上次重做时的「关于TA」（写的时间和文字）、说明、题库和时间，以及失败的时间和错误，记在 `meta` 里的 `exam`。

**要跑多少次模型。** 开始全收几十分钟后，在实际的存储上量过：最近 7 天有消息的聊天 152 个（私聊 89、群 46、话题群 17），除去我定的 4 个，要分级的 148 个；只按大小放时一次全量分级是 4 次模型运行，前三个提示约 77–80 KB，各放了 23、28 和 91 个聊天，最后一个 7 KB；每个提示最多 25 个聊天以后是 6 次。那时群里只存过和我有关的消息，大多数聊天不到 30 条；到了 30 条上限的聊天每个在提示里约 4.2 KB（九成在 5.9 KB 以下），一个提示放得下 18 个左右。全收两天以后，活跃的聊天按 spec 的估计约 345 个，大部分群会到 30 条上限，全量分级约 14 到 19 次模型运行（25 个的上限本身要 14 次）。组提示在加工端的进程里同步进行，148 个聊天一共约 0.8 秒，分在每次运行之前。

### 每日读取

每天早上 6 点，加工端把前一天（本地时间 00:00 到 24:00）每个每日和即时级别的聊天的消息交给模型读一遍。模型按「关于TA」和我的说明，把每个聊天的消息拆成话题，每个话题写一个标题、要点或结论、属于我的工作（`work`）、兴趣（`interest`）还是都不是（`other`）、挑没挑和一句理由，并指出它由哪些消息组成。挑出的和没挑的话题都存下：挑出的是以后我问起时的上下文，没挑的用来检查有没有漏挑。读的结果不推送，也不发卡片：整理出来的东西是上下文，需要时再取，推送只会多一份要看的东西。spec 见 `.local/prd/butler-daily-reading.md`。

**读哪些聊天。** 前一天有消息、而且在那一天结束时级别是每日或即时的聊天。还没有级别的私聊按即时算，所以也读；还没有级别的群按只存不看，不读。级别在当天变过的聊天按那一天结束时的级别：那是当天最后的判断，而且一个聊天要么整天读、要么不读，不会只读半天、把一个话题切开。那一刻的级别从级别的改动记录（`level_changes`）推出来：那一刻之后的第一次改动之前是什么级别，之后没有改动就是现在的级别。所以停机以后补读前几天，用的也是那几天的级别。忽略名单上的发送方的消息不读；我自己发的消息照样读，它们是讨论的一部分。

**交给模型什么。** 消息的样子和批次一样（编号、时间、发送者和类型、类别、@ 了谁、表情、在话题里的位置、是否撤回或编辑、正文，每条最多 1500 字），这一天要读的消息带 `new`。话题里的回复如果根消息在这一天之前，根消息作为上下文一起给，被回复的消息也一样。每个提示还带「关于TA」和我的说明，每个聊天带名称、类型和级别。聊天、消息和话题都以这一次的编号交给模型（`c1`、`m1`、`t1`……），聊天 id、消息 id 和链接都不经过模型；说明里和批次一样写明，消息内容是别人写的数据，不是给模型的指令。

**按大小打包和分段。** 大多数聊天一天只有几条到几十条，一个聊天一次调用太浪费，所以几个小聊天合成一次：从消息最多的聊天开始，往一个提示里放尽可能多的完整的聊天，不超过 80 KB（和批次一样，herdr 的一个参数最多 120 KB），最多 20 个（每个聊天都要回答话题，太多了回答会太长）。一个聊天单独都放不下时，它单独分段读：还没读的消息平均分成放得下的最少几段，每次读一段。平均分而不是每段塞满，是因为后面的段要带上已经拆出的话题，提示会变大；塞满的话最后常剩下一小段，多一次调用。读后面一段时，模型还拿到这一天已经从这个聊天拆出的话题（编号、标题、要点、`area`、挑没挑和理由）和上一段最后的 8 条消息，接着说的讨论就归到已有的话题上，需要时更新它的标题和要点，而不是另开一个。

**标出可能要我做的事。** 每日级别的聊天里，可能要我本人去做、回复或决定什么的消息（不管有没有 @我），模型把编号列在 `flagged` 里。读取不判断它们算不算事项，只把它们的类别从 `stored` 换成 `flagged`，它们就进了批次的待处理，由下一轮批次按同一个标准判断（见「模型决定什么，代码检查什么」）：什么算一件事、归不归我、多急、什么时候结束，只在批次和整理里定义，读取再判断一遍，两处会不一致。已经有别的类别的消息（比如 @我 的）本来就交给批次，不改；即时聊天的消息都交给批次，所以只标每日聊天里的。代价是每日聊天里的事最多晚一天才进待办，和「每日」的意思一致。标出的消息在早上的批次里处理，因此新出的事项多到工作时间外发汇总的数目（见「汇总」）时，上班前会发一份；放在早上读，就是为了不在半夜为它发汇总。

**代码检查什么。** 新话题要有标题，至少引用一条这次要读的消息；它属于第一条消息所在的聊天，别的聊天的消息不采纳。接着已有话题的只能引用那个话题所在聊天里这次要读的消息。`area` 不认识的按 `other`，`picked` 不是 true 或 false 的按没挑；`flagged` 只采纳每日聊天里这次要读的消息。引用上下文里的消息、不存在的消息或话题，这些部分都不采纳，各记一条错误（来源「读取」）。文字里的网址换成「[链接]」，标题最多 80 字、要点 400 字、理由 200 字。怎么拆、挑不挑、标哪些全由模型判断，代码里没有关键词或发送者的规则。

**存下什么。** `topics` 表每个话题一行：哪一天、哪个聊天、标题、要点、`area`、挑没挑、理由、哪次模型运行写的；`topic_messages` 记它由哪些消息组成，话题的链接是它最早一条消息的链接。话题的编号不变：以后的纠正指向它，重做纠正题时用它的标题和要点重新问挑不挑。`readings` 表每个读过的聊天每天一行：读的时候的级别、读了多少条、读到哪一条（分段读的进度）、标出了几条、回答用不了几次和最后的错误、读完或放弃的时间。每次模型调用记在 `model_runs` 里，`kind` 是 `read`，`messages` 是这次要读的消息数。

**什么时候读，停机以后补读。** 加工端每分钟看一次有没有要读的日子。前一天在早上 6 点以后读：晚到的消息（对账补读的、后来取到的话题回复）有时间进来，标出的消息也在早上而不是半夜进批次。在 11-06 的数据上试过（到中午的 1798 条消息、28 个聊天）：7 次调用，80 KB 的提示每次 7 到 10 分钟，小的半分钟到 3 分钟，一共 45 分钟；一整天估计十几次、一到两个小时，上班前早已读完。从开始收下全部消息以后的第一个完整的一天读起，开始的那天不完整，不读。停机以后，没读的日子从早到晚补读，但最多补最近 3 天：3 天能覆盖一个周末的停机，更早的日子要看时由 agent 直接读原始消息，补读太多会让模型连着跑上百次。不补的日子记在存储里，`status` 显示。一天读到一半停机或失败，已经读完的聊天和分段不重读，下次从停下的地方接着读。

**失败时。** 一次调用没有得到回答（连不上、超时、没有回复），这次读取就停下，记一条错误，30 分钟后从停下的地方再读。回答用不了（不是要求的 JSON，或者超过 64 KiB 被截断）时：这次有几个聊天，就马上减半再试；只有一个聊天，就给这个聊天记一次，这次先跳过它、接着读别的，下次读它时每段的大小减半；同一个聊天在这一天记满 3 次就放弃，已经存下的话题保留。一天里每个聊天都读完或放弃了，这一天才算读完，然后才读下一天。加工端停止时等正在运行的那次调用（和批次、分级一起最多等 20 秒），之后不再开始新的调用，读到的保留，不算失败。

**另一条模型通道。** 读取和分级一样，在加工端的进程里有自己的定时器，一次一个，不等批次、整理、「关于TA」和分级，它们也不等它，所以模型机器上最多同时运行三个 claude。上次读完的一天和它的结果（时间、几个聊天、挑出和没挑的话题数、标出的消息数、放弃了的聊天）、没读完时的错误和时间，以及停机后没补读的日子，记在 `meta` 里的 `reading`，`status` 显示它们和下一次读哪一天、什么时候读。

**查话题、读原始消息和纠正。** 话题由和管家说话的 agent 经命令行取用（见「和管家说话」和「命令行」）：`topics` 按聊天、日子、文字和挑没挑查话题，回答「这几天 X 群有什么值得看的」「这周有没有人讨论过 Y」；当天的消息要到第二天早上才有话题，只存不看的聊天从来不读，这些用 `messages` 读一个聊天的原始消息。我说某个话题该挑、不该挑，或者某个聊天某一天有该挑的事却没有拆成话题时，agent 用 `corrections` 按我的原话记一条纠正。纠正存在 `topic_corrections` 表里，每条一行：`kind`（`pick` 该挑、`unpick` 不该挑、`missed` 漏挑）、指向的话题（漏挑的没有话题可指，是空的）、哪一天、哪个聊天、我的原话和记下的时间。话题上的纠正也存它的日子和聊天，这样按聊天或日子找纠正时不用经过话题，漏挑的也一样能找到。话题自己的 `picked` 一直是模型的判断，不随纠正改：重做纠正题时把话题的标题、要点和聊天交给模型，藏起答案再问挑不挑，答案就是最新的那条纠正。纠正和说明一样只增删、不修改，删掉的编号不再给别的纠正：同一个话题可以有几条纠正，最新的一条算数，删掉它就回到上一条，没有了就回到模型的判断；编号也就能说明一次读取或一次重做用了哪些纠正。现在纠正只记下、能查，进入下一次读取的提示、「关于TA」的输入和纠正题是下一步的事。

### 忽略名单

按发送方 id 记录。名单上的发送方的消息不交给模型，也不出现在上下文里。它们被跳过时就记为已处理，所以之后把发送方移出名单，不会把它在名单上期间发的消息补交给模型。

### 模型在哪里

模型是另一台机器（cpu1）上的 claude，经 herdr 调用，claude 访问的网关 token 不离开那台机器。`BUTLER_MODEL_MACHINE` 是 herdr 保存的机器（`herdr machine list`），它指向那台机器上专给管家用的 herdr session，不是我自己用的默认 session。每一批（整理的每一部分也一样）这样运行：

1. `herdr --machine <机器> workspace create --cwd <BUTLER_MODEL_CWD> --label butler-model --no-focus`；
2. 在它的第一个 pane 里 `herdr --machine <机器> agent start <名字> --kind claude -- --tools "" --strict-mcp-config --disable-slash-commands [--model <模型> --settings '{"availableModels":["<模型>"]}'] [--effort <强度>] --system-prompt <说明>`：没有内置工具，没有 MCP 服务器，没有技能和斜杠命令，模型只能回答；
3. `agent prompt <名字> <数据> --wait`，等这一轮结束；
4. `agent replies <名字>` 取它最后的回复（由 claude 的 Stop hook 报给 herdr，可能比状态变化晚一点到，所以最多再等 15 秒）；
5. 不管成功与否，`workspace close` 关掉这个工作区，claude 随之退出。

说明和数据交给 herdr 之前，去掉其中所有不可见的格式字符（Unicode 的 Cf 类），只留下零宽连接符 U+200D（它把多个 emoji 连成一个，claude 能正常接受）。claude 的输入框收到带这类字符的提示时不会提交，这一轮不开始，herdr 报 agent_prompt_stalled；实际遇到的是一个飞书昵称里的双向文本控制符 U+202E、U+202D，它出现在消息表情回复的 userNames 里，带着这个昵称的每一批都这样失败。所以模型看到的名字和文字里没有这些字符。

配置了 `BUTLER_MODEL_NAME` 时才带 `--model` 和 `--settings`（JSON 是一个参数），没有配置时都不带，用 claude 默认的模型。只带 `--model` 不够：cpu1 的 `~/.claude/settings.json` 用 `availableModels` 只允许另一个模型，claude 会提示这个模型被组织的设置限制，然后照样请求允许的那个。`--settings` 再加一份设置，里面的 `availableModels` 只列这个模型，这样就够了：claude 2.1.318 在 cpu1 上实测，会话记录里的请求用的都是这个模型。

配置了 `BUTLER_MODEL_EFFORT` 时才带 `--effort <强度>`，没有配置时不带，用 claude 默认的推理强度（high）。它只能是 claude 的 `--effort` 接受的 low、medium、high、xhigh 或 max，别的值让配置加载失败。以前这里固定带 `--effort low`：那时 cpu1 网关后面是 deepseek，默认的 high 下它要推理几千个 token，40 条消息的一批会超过回复的时限，而 low 给出同样的事项、token 少一半；那个网关对 deepseek 不接受 medium。现在模型换成了 ark/seed-evolving，用它默认的推理强度，所以不再固定。

加工端启动时关掉以前被打断、没来得及关的 `butler-model` 工作区。同一个存储同时只能有一个加工端，第二个会拒绝启动，所以批次和整理不会重叠。分级和每日读取的运行用同一个标签，也是这样开工作区、用完关掉；它们在启动时的清理之后才开始，不会被清理关掉。

### 失败时

连不上那台机器、claude 没有起来、超时（15 分钟）、没有回复、回复不是要求的 JSON，这一批都保持未处理，记一条错误，这一轮停下，下一轮再试；连续失败时每次把批次减半（最少 1 条），成功一次后恢复到 40 条。整个模型出问题时消息不会被丢掉，那台机器断开期间的消息在恢复后补加工。一轮里有失败时，在下一轮成功之前，我的回应也不再马上触发处理（见「我回应了就马上处理」）。

只有一种失败会让加工端跳过消息：一条消息单独成批，模型给了回答，但回答用不了（不是要求的 JSON，或者超过 64 KiB 被 herdr 截断）。网关或 API 出错时不会是这样：claude 这时运行 StopFailure hook 而不是 Stop，herdr 收不到任何回复（claude 2.1.309 里的说明：「Fires instead of Stop when an API error … ended the turn」）。这时这条消息先放到一边，这一轮接着处理它后面的消息（单独成批的是我的一条表情回复时不放到一边，按模型的问题处理：它只是几个字段，不会让模型答不出来）；如果紧接着的那次运行成功了，说明模型本身正常，这次失败记在这条消息上。如果那次也失败了，就算模型的问题，什么都不记，这一轮停下。被记过的消息以后总是单独成批，也不再作为别的消息的上下文；一轮里只试它一次，所以几次尝试至少隔一轮。记满 3 次就把它记为已处理并跳过，同时记一条错误，写明消息 id、所在聊天、发送者、时间、开头的文字和最后一次的原因；`status` 显示跳过了多少条。它挡住后面的消息，最多到它第一次被记上为止（减半到单独成批要几轮）。之后哪次它单独成批成功了，记录就清掉。每次运行的开始和结束时间、是批次还是整理（`kind`）、问的哪个模型（`model`，就是 `BUTLER_MODEL_NAME`，没有配置时为空）、新消息和我的表情回复的数量、交给它的未结束事项数、提示大小、是否成功、错误和模型的原始回复都记在 `model_runs` 表里，方便事后看模型为什么这样判断。

### 第一次设置

在加工端所在的机器上保存模型机器，并让 herdr 在那台机器上开一个单独的 session：

```bash
herdr machine add --label cpu1-butler --remote-session butler <cpu1 的 SSH 地址>
ssh <cpu1 的 SSH 地址> 'mkdir -p -m 700 ~/.local/share/butler-model'
```

`machine add` 需要两边的 herdr 版本兼容；它要求批准安装、更新或替换远端 herdr 时，先停下来确认。`BUTLER_MODEL_CWD` 写这个目录在模型机器上的绝对路径：herdr 对不存在的目录和 `~` 开头的路径都会悄悄换成主目录。这个目录在已信任的主目录下面，claude 启动时不会停在信任对话框上。

## 管家机器人

机器人是管家自己的飞书应用，不复用 Bridge 的机器人。它的长连接（飞书 SDK `@larksuite/channel` 的 WebSocket，断开后由 SDK 重连）由加工端的进程持有，没有第三个进程。没有配置机器人时，加工端照常加工，只是不发卡片。

### 创建应用

`./cli.mjs bot create [--name 名称]` 走飞书官方的一键创建流程（SDK 的 `registerApp`，Bridge 用的也是它）：命令行打印一个飞书域名下的链接，用飞书扫码或在浏览器里打开，在飞书自己的页面上确认应用和权限。确认后，应用的 App ID、App Secret 和创建者的 open_id 写进配置文件（`BUTLER_BOT_APP_ID`、`BUTLER_BOT_APP_SECRET`、`BUTLER_BOT_OWNER`、`BUTLER_BOT_DOMAIN`），文件始终是 600 权限；其他行保持不变。然后重启加工端，机器人上线。已经配置了机器人时，这个命令拒绝运行，不会覆盖。

只申请机器人用到的权限：以机器人身份发消息（`im:message:send_as_bot`）、接收私聊消息（`im:message.p2p_msg:readonly`）、读取机器人自己的基本信息（`application:bot.basic_info:read`），消息事件 `im.message.receive_v1`，以及卡片回传交互回调 `card.action.trigger`（卡片上的按钮，见「卡片上的按钮」）。不用飞书的默认权限模板，没有用户身份的权限。更新已经发出的卡片（`PATCH /open-apis/im/v1/messages/:message_id`）用的也是 `im:message:send_as_bot`，飞书文档写明这个接口开启「以应用的身份发消息」即可调用；点击后在回调的回答里换卡片不需要别的权限。创建流程只允许新建应用，不能选一个已有的应用，免得误用 Bridge 的应用。

事件和回调经机器人的长连接送来。一键流程只能申请权限、事件和回调这几项，订阅方式（长连接还是发到开发者服务器）不在其中（SDK 的说明写明事件订阅方式和回调地址属于敏感配置，不能经这个流程设置）。Bridge 用同一个流程建应用、申请同一个回调，也是在长连接上接收点击；管家的新应用应当一样，但还没有实测。

### 给已有的应用加上卡片回调

按钮出现以前建的应用（现在用的 `cli_aa51fc2e26389c17`）没有 `card.action.trigger` 回调，点按钮时飞书提示应用没有配置卡片回调（错误码 200340），什么都不会送到管家。加上它有两种办法，都要应用的所有者（我）在飞书里确认。

一是 `./cli.mjs bot update`。它走同一个官方流程，但带上配置里的 App ID（SDK `registerApp` 的 `appId`，`createOnly` 为 false；`createOnly` 为 true 时飞书的页面会忽略 `appId`、照样新建一个应用）：命令行打印一个飞书域名下的链接，打开后飞书的确认页列出这个应用要新增的权限、事件和回调（和新建应用申请的一样，现在多出来的只有 `card.action.trigger`），确认后生效。飞书返回的不是配置里的应用时，命令报错，配置文件不动；返回的 App Secret 和配置里的不一样时，把新的写进配置文件。没有配置机器人时它拒绝运行，它不会去动别的应用。这个流程按 SDK（`@larksuiteoapi/node-sdk` 1.76.0 的 README 和源码）和飞书文档「一键创建应用（Java）」里「更新已有应用」的说明写成，还没有实际跑过：确认后返回的 App Secret 是不是原来那个、回调是不是自动用长连接，都要跑一次才知道。之后重启加工端，在卡片上点一下「完成」试试。

二是在开发者后台手动加，`bot update` 之后点按钮仍然提示没有配置回调时也这样做（步骤按飞书文档「使用长连接接收回调」和「添加回调」）：

1. 打开 [飞书开发者后台](https://open.feishu.cn/app)，进入这个应用。
2. 左侧 **开发配置 > 事件与回调**，选 **回调配置** 页签。
3. 编辑 **订阅方式**，选 **使用长连接接收回调**，点 **保存**。保存时飞书要求这个应用的长连接在线，所以加工端（机器人）要正在运行、已经连上（`./cli.mjs status` 里机器人一行是「已连接」）。
4. 在页面下方 **已订阅的回调** 点 **添加回调**，选 **卡片回传交互**（`card.action.trigger`，不是「消息卡片回传交互（旧）」，旧的不支持长连接），**确认添加**。
5. 左侧 **应用发布 > 版本管理与发布**，**创建版本**，填好版本号和更新说明，**保存**，**申请线上发布**。要企业管理员审核时等审核通过；发布以后回调的配置才生效。

回调和事件走同一条长连接。加上以后点按钮仍然没有反应时，重启加工端，让长连接重新连一次。

### 只听我的

机器人的主人是创建应用的人（创建流程返回的 open_id）。SDK 只收这个 open_id 发来的私聊；机器人自己再检查一遍：只有主人在私聊里发的消息才回复（回复是一句固定的话，见「和管家说话」），别人的消息、群里的消息一律不理，也不回复。应用没有接收群消息的权限。卡片上的按钮也只认主人：卡片被转发给别人时，别人点了只会看到一个错误提示「只有管家的主人能操作这张卡片」，什么都不改。

### 汇总

汇总是发到我和机器人的私聊里的一张卡片「管家待办」（飞书卡片 JSON 2.0），样子是这样：

```
管家待办 · 更新于 14:20          2 件紧急
────────────────────────────────────────
● 陈帆让你填开发进展文档     [完成] [⋯]
  陈帆 · 开发进展群 · 期限 11-06

● 金垠廷要 GEO 曝光数据      [完成] [⋯]
  金垠廷 · GEO 小分队 · 今天 10:20
────────────────────────────────────────
▸ 今天结束了 3 件
```

标题下面写着更新的时间（「更新于 14:20」，不是发出的那天时带上日期）。有紧急的事项时，标题右边是一个红色的标签写着有几件紧急，标题是红色；没有时没有这个标签，标题是蓝色。聊天列表和通知里显示的摘要是件数，比如「2 件紧急 · 共 5 件待办」。

卡片里依次是：

1. **没结束的事项**：紧急的在前，同样紧急的按开始的时间、早的在前，每个事项一行。行首是一个按紧急程度上色的圆点（紧急红色、一般橙色、不急灰色），然后是标题（正文大小的字），下面一行灰色小字写谁、所在聊天，和期限（模型写成 `YYYY-MM-DD` 的期限是今年的就省掉年份，别的照原话写），没有期限时写开始的时间（今天的写「今天 10:20」，别的天带上日期）。点标题和这一行打开原消息。右边是两个按钮：「完成」，和「⋯」，里面是「不归我」和「打开原消息」（见下面「卡片上的按钮」）。卡片上不再有编号和「要我做什么」，事项之间只留空白。最多列 10 个，其余的按紧急程度数一下（「另有 3 件没有列出（2 件一般、1 件不急），到 herdr bridge 里绑定了管家 agent 的飞书群里问管家可以看全部」）。没有事项时只有一句「现在没有要你处理的事。」。
2. **今天结束的事项**：一条分隔线下面，收在一个默认折起来的面板里，面板标题是「今天结束了 3 件」，前面的小三角展开时转向下。今天是卡片生成那天的 0 点以来，不管上一份汇总什么时候发的。展开后每个一行灰字「标题 — 理由」。管家关掉的在前，我自己关掉的在后（理由写「你关掉的」，关掉时说了理由的接在后面，比如「你关掉的：不用管」），各自最近结束的在前，最多列 10 个，其余的只数一下。

模型写的文字（标题、谁、期限、理由）和聊天名称都以纯文本显示，不会被当成 Markdown 或链接；卡片里的 Markdown 只有管家自己写的标题和彩色圆点。链接只有管家用来源消息生成的那一个，放在点击标题的跳转和「打开原消息」里，不出现在文字里。一份汇总只有一张卡片：飞书拒收超过 30 KB 或多于 200 个组件（文本元素也算）的卡片，每个事项一行占 15 个组件，列满 10 个、加上标题、数数的那一行和结束的面板一共 162 个组件；事项写得很长、10 个放不下 28000 字节时少列几个（每个字段都写到最长时能列 9 个），没列出的都算进那一行里。

卡片发出以后跟着事项更新，不用等下一份：加工端的批次或整理新建、修改或关掉了事项，或者我用命令行关掉、重新打开了事项（见下面），或者在卡片上点了「完成」「不归我」，管家就按现在的事项重新生成最新那份汇总的卡片，用飞书的更新消息卡片接口原地替换，「更新于」换成现在的时间。几秒内的多次变化合成一次更新；更新和发送一次一个，不会同时进行；机器人没连上、还没有发过能更新的汇总（升级前发的汇总没有记下消息 id），或者那份汇总已经发出 14 天（飞书只允许更新 14 天内的消息）时不更新；更新失败记一条错误，不重试，下一次变化时再更新。卡片的 `config` 里写明 `update_multi: true`，飞书要求更新前后的卡片都这样声明。发出新的一份汇总以后，上一份的卡片换成一句灰色的「有一份更新的待办在下面，这份不再更新。」，旧卡片上不会留着过时的待办。最新那份汇总的消息 id 和它发出的时间记在存储里（`meta` 里的 `digest`）。

命令行（`matters close`、`matters reopen`）在另一个进程里，碰不到机器人，所以它改了事项以后在存储里留一个记号：`meta` 里 `matters` 的 `changes` 加一（在一个事务里加，两个命令行同时改也不会少算一次；用计数而不用时间，同一毫秒里的两次改动也分得开）。加工端每 15 秒看一次这个数（和「我回应了就马上处理」的快速检查同一个间隔，只读 `meta` 的一行），变了就和批次改了事项一样告诉机器人，按上面的规则更新最新那份汇总，所以命令行改的事项一般在 15 秒多一点之内出现在卡片上。没有改动的命令（事项已经是那个状态）不留记号。加工端启动时把当时的数当作看过的：它停着时命令行改的事项，卡片要等下一次事项变化或下一份汇总才跟上。

什么时候发（时间都是本机时间，都可以配置，见「配置和数据」）：

- **工作时间**（默认周一到周五 10:00–20:00）：从开始时刻起每个间隔（默认 1 小时）一个时间点，到结束时刻为止，包括结束时刻，默认就是 10:00、11:00……20:00。到了时间点，有新事项或有结束的事项就发，都没有就不发，等下一个时间点。管家停机错过的时间点，在下一个时间点之前恢复时补发，再晚就不补了。
- **工作时间外**：新事项攒到 3 个才发，而且离上一份汇总至少 2 小时。只有结束的事项时等到工作时间。

我自己关掉事项（卡片上的按钮或命令行）不算变化，不会单独触发一份汇总（我已经知道了），但下一份汇总会列出它。汇总每分钟检查一次；机器人没连上时不发，连上后在当前时间点内补发；发送失败记一条错误，5 分钟后再试。

### 分级的卡片

机器人还往私聊里发三种和分级有关的卡片，写法和汇总一样（飞书卡片 JSON 2.0；模型写的理由和推断、聊天名称都以纯文本显示；卡片上没有链接）。

**分级列表**「聊天的分级」：有级别的聊天按级别分组，每个级别一个默认折起来的面板，依次是即时、每日、只存不看、忽略，最后是最近 7 天有消息、还没有级别的聊天；面板标题写着个数（「只存不看 200 个」）。展开后每个聊天一行，名称和理由（「GEO 小分队 — 项目讨论，和TA的工作有关」），我定的标着「（你定的）」，还没有级别的写它现在按什么处理（「新群（按只存不看）」），只从推送见过、还没有名称的写「（名称未知的聊天）」。最上面一行灰字说怎么在私聊里改级别、问理由。一个级别的行多到一个面板放不下（约 12 KB）时分成几个面板（「只存不看 270 个（1/3）」），一张卡片放不下时接着发下一张（标题带编号，「聊天的分级（2/4）」）。摘要是各级别的个数。

它只在加工端到了时间自己开始的分级第一次分成了聊天以后发（分级把结果交给机器人的 `onPass`，`by` 是 `schedule`，见「给聊天分级」），把全部的分级发给我过目一次。我要求的分级（`request`）不算，否则在第一次全量分级之前先分了一两个聊天，列表里就只有这几个，全量的那份再也不会发；`level grade` 在命令行自己的进程里分级，本来也不告诉机器人。机器人没连上就等连上再发，发送失败 5 分钟后再试，发出以后记在存储里（`meta` 里 `levelCards` 的 `listAt`），之后不再自动发。要看现在的分级，到 herdr bridge 里绑定了管家 agent 的飞书群里问（agent 用 `level list`）。卡片最上面一行灰字也这样说：「你定的级别模型不改。想改哪个、问哪个为什么是这个级别，到 herdr bridge 里绑定了管家 agent 的飞书群里说。」

**每周的分级变化**「分级变化（10-19 至 10-26）」：在汇总的工作日里每周第一天、工作时间开始的时刻发（默认周一 10:00，跟着汇总的配置），内容是从上一个这样的时刻到这一个之间，模型改了级别的聊天和第一次分级的聊天：

```
分级变化（10-19 至 10-26）
这一周模型改了 2 个聊天的级别，第一次分了 1 个；你纠正了 1 次分级；上次重做纠正题（10-25）做对了 8/10（80%）。
点右边的 ⋯ 选一个级别，就改成你定的，模型以后不改它。
开发进展群                                                   [⋯]
  每日 → 即时 · 常有要TA回复的问题
运维通知群                                                   [⋯]
  只存不看 → 忽略 · 你已定为每日 · 只有机器人通知
新来的群                                                     [⋯]
  未分级（按只存不看） → 只存不看 · 和TA的工作无关的闲聊
```

每个聊天一行：名称，下面一行灰色小字写模型把它从什么级别改成什么级别，我之后定了级别时我定的是什么，和模型的理由。一周里模型改了几次的，从第一次之前的级别算到最后一次之后的级别，最后改回原样的不列；第一次分级的原来的级别写「未分级」，已经在分级列表里给我看过的不再列。模型改过的在前，第一次分级的在后，各按改的先后。右边的「⋯」里是四个级别，现在的那个标着「（现在）」，选一个就定为我定的级别（见下面「卡片上的按钮」）。

最上面一行写这一周模型改了几个、第一次分了几个，我纠正了几次（怎么算纠正见「聊天级别」），以及这一周结束以前最近一次重做纠正题的日期和做对的比例（见「给聊天分级」里的「纠正题」；还没有重做过时不写）。一行占 12 个组件，飞书一张卡片最多 200 个，所以一张卡片最多 12 个聊天，写得长、放不下 28000 字节时少列几个，其余的接着发下一张；一周最多列 36 个，多出来的只在最上面说一句：其余的到 herdr bridge 里绑定了管家 agent 的飞书群里问管家。

这一周模型什么都没改时不发。管家停机或机器人没连上错过了这个时刻，在这一周里恢复以后补发；发送失败记一条错误（来源「分级」），5 分钟后再试。上一次处理到的时刻和发出的时间记在 `meta` 里 `levelCards` 的 `weekSlot` 和 `weekAt`。

**新推断**「关于你的新推断」：加工端写完「关于TA」、模型列出了这一版新归纳出的内容时（`onProfile`，见「关于TA 和说明」），把它们一条一行发给我，最后一行灰字说不对的话到 herdr bridge 里绑定了管家 agent 的飞书群里告诉管家，它会记成说明（`notes add`），以我的话为准。没有新内容时不发。发送失败记一条错误（来源「分级」），不重发：下一次写「关于TA」有新内容时再发。

### 卡片上的按钮

汇总里的事项，每行右边有两个按钮，点击经机器人的长连接送回管家（飞书的卡片回传交互回调 `card.action.trigger`，新建的应用申请了它，以前建的应用要先加上它，见「给已有的应用加上卡片回调」）：

- **完成**：把事项关掉，和命令行的 `matters close` 一样记为我关掉的，理由是「完成」。
- **⋯ → 不归我**：把事项关掉，记为我关掉的，理由是「不归我」；之后模型整理消息、整理事项和写「关于TA」时会看到它（见「关于TA 和说明」）。
- **⋯ → 打开原消息**：和点标题一样打开原消息，管家不做什么。

飞书要求 3 秒内回答一次点击，管家马上回答：一个提示（「已完成」，或「已标记为不归你，之后判断时会参考」），和按现在的事项重新生成的这张卡片，飞书用它原地换掉被点的卡片，点过的事项立刻从卡片上消失、出现在「今天结束了」里。被点的是最新那份汇总时，换上的就是现在的汇总；是更早的汇总时，换上「有一份更新的待办在下面」；是别的卡片时只回答提示，卡片不换。随后最新那份汇总按上面的规则跟着更新。事项已经结束了（比如模型刚关掉它）或者不存在时，什么都不改，提示「这件事已经结束了」或「没有这件事了」，卡片同样换成现在的样子。想撤销时用 `matters reopen` 重新打开（在和管家说话的群里说）。

按钮带回来的只有动作、事项编号、是哪张卡片和卡片生成的时间。飞书的 SDK 把同一个人在同一条消息上的同一个点击（按钮带回来的内容也相同）在 12 小时内只交给管家一次，所以每次重新生成的卡片的按钮都带着新的时间：用 `matters reopen` 重新打开一个点过「完成」的事项以后，卡片上再点它的「完成」仍然有效。点击和私聊消息各排各的队，点击不会等在消息后面。

每周的分级变化卡片上，每个聊天右边的「⋯」里是四个级别（即时、每日、只存不看、忽略），现在的级别标着「（现在）」。选一个，就把这个聊天定为我定的这个级别，和 `level set` 一样：模型以后不改它，改动记进级别的改动里（见「聊天级别」）。管家马上回答一个提示，写出原来和现在的级别（「开发进展群：即时 → 只存不看（你定的）」），和重新生成的这张卡片：还是这张卡片上的那些聊天，选过的那一行写上「你已定为只存不看」，「⋯」里标出现在的级别；最上面的数字还是那一周的。选的正是我已经定的级别时什么都不改，只提示一句。「⋯」带回来的是动作、聊天、卡片的那一周（和那时分级列表发出的时间）、这张卡片上的聊天和卡片生成的时间，所以重新生成的总是这张卡片上的那些聊天；聊天不在这张卡片上、级别不认识的都不理。和汇总的按钮一样只认主人：卡片被转发给别人时，别人选了只看到错误提示，级别不变。

### 和管家说话

和管家说话不在机器人的私聊里，而在 herdr bridge 里绑定了管家 agent 的飞书群里：bridge（本仓库的 `bridge/`，部署在 cpu1）把这个群绑到 cpu1 上的一个 herdr Claude agent，agent 经一个包装脚本用 ssh 在 cpu2 上运行管家的命令行（见「命令行」），用它查看和修改事项（`matters`、`matters close`、`matters reopen`）、说明（`notes`）、级别（`level`）、忽略名单（`ignore`），查每日读取的话题（`topics`）、读一个聊天的原始消息（`messages`）、记下和删掉我对挑没挑的纠正（`corrections`），读「关于TA」（`profile`）和状态。命令行的读命令都能输出 JSON，写命令都打印改了什么（原来 → 现在），agent 据此回答我。包装脚本和 agent 的配置不在管家里。

机器人的私聊只用来发卡片。我在私聊里发的每条消息，不管是文字、图片还是别的，都只得到一句固定的回复（回复在这条消息下面），不调用模型：

> 这个私聊只用来发管家的卡片，要和管家说话，请到 herdr bridge 里绑定了管家 agent 的飞书群里说。

回复发送失败时记一条错误（来源「机器人」），不重试。卡片上说的「问管家」「告诉管家」指的也是这个群。从有私聊对话的旧版本升级时，存储里的 `conversation` 表删掉。

## 配置和数据

配置文件默认是 `~/.config/butler/butler.env`（`--config` 或环境变量 `BUTLER_CONFIG` 可以换），权限必须是 600，否则收集器和命令行都拒绝运行：

```bash
mkdir -p ~/.config/butler
install -m 600 /dev/null ~/.config/butler/butler.env
# 只取出只读 token，不要把 open-lark 的 app.env 整个复制过来
grep '^OPEN_LARK_AGENT_READ_TOKEN=' ~/.config/open-lark/app.env | sed 's/^OPEN_LARK_AGENT_READ_TOKEN=/BUTLER_OPEN_LARK_TOKEN=/' >> ~/.config/butler/butler.env
```

| 键 | 默认值 | 用途 |
| --- | --- | --- |
| `BUTLER_OPEN_LARK_TOKEN` | 无，必填 | open-lark 的只读 token（open-lark 的 `OPEN_LARK_AGENT_READ_TOKEN`） |
| `BUTLER_OPEN_LARK_URL` | `http://127.0.0.1:8081` | open-lark Agent 接口的地址 |
| `BUTLER_LINK_BASE` | `http://127.0.0.1:3333` | open-lark 网页的地址，用来生成消息链接（open-lark 的 `OPEN_LARK_PUBLIC_URL`） |
| `BUTLER_DATA_DIR` | `~/.local/share/butler` | 数据目录 |
| `BUTLER_MODEL_MACHINE` | 无，加工端必填 | herdr 保存的模型机器的名称（见上面「第一次设置」） |

| `BUTLER_PROFILE_EVERY` | `24h` | 重写「关于TA」的间隔，如 `12h`；说明有变化时不等这个间隔（见上面「关于TA 和说明」） |

数据是数据目录里的一个 SQLite 文件 `butler.db`（WAL 模式，旁边还有 `butler.db-wal` 和 `butler.db-shm`），目录权限 700，文件权限 600。里面有消息和它们的类别、表情回复和我的表情回复、每个聊天的名称、读取位置和级别、跟踪的话题、待补取的 @我、收集器状态和最近 100 条错误，加工端的忽略名单、我的说明、处理记录、事项、模型运行记录、整理状态（上次完成的整理和之后的失败）、「关于TA」（最新的一版和之后的失败）和分级状态（上次分级，和上次看到的说明），以及机器人的连接状态、汇总状态（上次发出的时间和时间点）和命令行改事项的记号（`meta` 里的 `matters`，见「汇总」）。除了忽略的聊天，收集器存下全部推送来的消息，按以前的量估算每天约多 40 MB（大头是机器人卡片的原始结构）。本阶段不做清理，存储会持续增长；`butler status` 显示文件大小，也可以用 `du -sh ~/.local/share/butler` 查看。

## 运行

需要 Node.js 24（用到内置的 `node:sqlite` 和 `WebSocket`）。唯一的 npm 依赖是飞书官方的 Channel SDK `@larksuite/channel`（机器人用，版本和 Bridge 相同），第一次运行前在 `butler/` 里安装：`npm ci --registry=https://registry.npmjs.org`。

开发时在仓库里直接运行：

```bash
cd butler
node cli.mjs run        # 或 npm start；也可以直接 ./cli.mjs run
```

常驻运行时用复制出去的一份代码（见下面「安装为用户服务」），切换分支或修改仓库不会影响正在运行的服务。`node:sqlite` 仍标为实验特性，命令行会滤掉它的提示。

命令行可以从仓库里运行，也可以用部署的那一份（`~/apps/herdr-butler/cli.mjs`）；两者读同一个配置文件，用同一个存储。`--help`（`-h`）或不带命令时打印上面的用法和每个命令的说明。

命令行也是和管家说话的 agent 的工具（见「和管家说话」），所以输出分两种，规则对每个命令都一样：

- 读的命令（`status`、`list`、`messages`、`topics`、`corrections [list]`、`groups`、`level [list]`、`level history`、`matters [list]`、`notes [list]`、`profile`、`ignore [list]`）打印给人看的文字；加 `--json` 时输出存储里的记录（JSON），形状见下表。
- 写的命令（`level set`、`level clear`、`level grade`、`matters close`、`matters reopen`、`notes add`、`notes remove`、`corrections pick`、`corrections unpick`、`corrections missed`、`corrections remove`、`ignore add`、`ignore remove`）打印改了什么，每项一行，写成「原来 → 现在」；加 `--json` 时输出同样的内容：每个改动的 `before` 和 `after`，没有的一边是 `null`。要改的已经是那个样子时（关掉已经结束的事项、加一条已经有的说明、再定一次我定的同一个级别、再记一条同样的纠正）什么都不改，照样输出，`before` 和 `after` 相同，退出码是 0。找不到要改的（编号不存在、名称没有对应或对应多个）、参数不对时什么都不改，原因写在标准错误里，退出码是 1。
- 我的话（`--reason` 的理由、`notes add` 的说明、`corrections` 的原话）里的空白合成一个空格，不能是空的，最长 200 字：它们要放进每个交给模型的提示，截断了就不是我的原话，所以更长的拒绝，不截断。`--reason` 只用于 `level set` 和 `matters close`，带在别的命令上会报错，免得理由不声不响地丢掉。
- 事项、说明、话题和纠正的编号写 `12` 或 `#12`。
- 时间（`--since`、`--until`）写 ISO 时间或 `30m`、`2h`、`7d` 这样的相对时间（多久以前）；只写日期（`2026-11-06`）时是那天本地的 0 点，而不是 `Date.parse` 理解的 UTC 0 点。日期（`--day` 和 `corrections missed` 的日期）写 `2026-11-06` 这样的本地日期。

| 命令 | `--json` 输出 |
| --- | --- |
| `status` | 一个对象，和文字的各行对应：`collector`、`events`、`reconcile`、`sync`、`counts`、`levels`、`processing`、`review`、`profile`、`grading`、`reading`、`bot`、`digest`、`errors`、`file`、`sizeBytes` 等 |
| `list` | 消息记录的数组，新的在前：`id`、`chatId`、`chatName`、`senderId`、`senderName`、`senderType`、`createdAt`、`text`、`categories`、`isMine`、`reactions`、`link` 等 |
| `messages` | 消息记录的数组，旧的在前，形状同 `list` |
| `topics` | 话题的数组，顺序同文字：`id`、`day`、`chatId`、`chatName`、`title`、`summary`、`area`（`work`、`interest` 或 `other`）、`picked`（模型挑没挑）、`reason`、`messageIds`（旧的在前）、`link`（第一条消息的链接）、`at`、`updatedAt`，有纠正时还有 `correction`：最新的一条纠正，同 `corrections` 的一项，但没有 `topic` |
| `corrections [list]` | 纠正的数组，旧的在前：`id`、`kind`（`pick`、`unpick` 或 `missed`）、`topicId`（漏挑的没有）、`day`、`chatId`、`chatName`、`words`（我的原话）、`at`，`topic` 是它指向的话题（同 `topics` 的一项），漏挑的是 `null` |
| `groups` | 群的数组：`feedId`、`name`、`chatMode`、`memberCount`、`isMuted`、`lastActiveAt` 等，`level` 是它的级别记录（同 `level list`），没有级别时是 `null` |
| `level [list]` | 有级别的聊天的数组，顺序同文字：`feedId`、`name`、`chatMode`、`memberCount`、`level`、`by`（`owner` 我定的，`model` 模型定的）、`reason`、`since`、`modelLevel`、`modelReason`、`modelAt` |
| `level history` | 改动的数组，新的在前：`id`、`feedId`、`name`、`chatMode`、`at`、`by`、`before` 和 `after`（`{level, by}`，没有级别时是 `null`）、`reason`（改完以后的理由）、`correction`（是不是一次纠正，见「聊天级别」） |
| `matters [list]` | 事项的数组，顺序同文字：`id`、`title`、`who`、`ask`、`due`、`urgency`、`status`（`open` 或 `closed`）、`reason`、`closedBy`（`model` 或 `owner`）、`closedAt`、`since`、`lastAt`、`openedAt`、`updatedAt`、`messageIds`、`chatIds`、`chats`、`link` |
| `notes [list]` | 说明的数组，旧的在前：`id`、`text`、`at` |
| `profile` | `{profile, notes}`：`profile` 是存储里的「关于TA」（`text`、`at`、`notes`、`messages`、`added`，之后写失败了还有 `failedAt`、`error`），还没有时是 `null`；`notes` 同 `notes --json` |
| `ignore [list]` | 忽略名单的数组：`senderId`、`name`、`since` |
| `level set` | 数组，每个聊天一项：`feedId`、`name`、`chatMode`、`before`、`after`（级别记录，同 `level list` 的一项，但没有名称等聊天的信息；没有级别时是 `null`）；定为即时的是话题群时还有 `warning` |
| `level clear` | 同 `level set`，没有 `warning`；取消以后没有模型的级别时 `after` 是 `null` |
| `level grade` | `{chats, runs, graded, left, error}`：交给模型的聊天数、模型运行次数、分成的聊天（每个 `feedId`、`name`、`before`、`after`，级别记录）、没分成的聊天（每个 `feedId`、`name`）和最后的错误（没有时不出现）；有没分成的聊天时退出码是 1 |
| `matters close`、`matters reopen` | `{before, after}`：改动前后的事项，同 `matters --json` 的一项 |
| `notes add`、`notes remove` | `{before, after}`：说明（`{id, text, at}`）或 `null` |
| `corrections pick`、`corrections unpick` | `{before, after}`：改动前后的话题，同 `topics` 的一项，`correction` 是它最新的纠正 |
| `corrections missed` | `{before, after}`：`before` 是 `null`，`after` 是记下的纠正，同 `corrections` 的一项（同样的已经记过时两边都是它）；那个聊天那一天没有读过时还有 `warning` |
| `corrections remove` | `{before, after}`：删掉的纠正（同 `corrections` 的一项）和 `null` |
| `ignore add`、`ignore remove` | 数组，每个发送方一项：`senderId`、`name`、`before`、`after`（忽略名单上的一项，同 `ignore --json`，不在名单上时是 `null`） |

- `status`：收集器是否在运行（看心跳）、推送是否连接和最近一次收到推送的时间、最近一次对账的完成和成功时间、open-lark 的同步状态、@我补扫和话题列表扫到哪里、各类消息的数量、待补取的 @我、各级别的聊天数（其中我定的有几个；没有级别的私聊按即时、群按只存不看）、存储位置和大小，以及最近的错误。
- `list`：按类别和时间列出消息，新的在前，每条带链接，正文只显示一行（最多 200 字）；`--since` 和 `--until` 的写法见上面。
- `messages <聊天名或 id>`：一个聊天的原始消息，旧的在前，正文完整，每条带时间、发送者、撤回编辑这类标记和链接；第一行写这段时间里一共几条。`--day` 是一整天，`--since`、`--until` 是一段时间，都不写时不限时间；`--search` 只列正文里有这段文字的（不分大小写）；多于 `--limit` 条（默认 100）时列最近的那些，第一行说明。忽略名单上的发送方的消息也列出：忽略名单管的是交给加工端模型的消息，agent 读聊天是为了回答我。聊天的找法和 `level grade` 一样，只在存储里找。读一个聊天不放进 `list`：`list` 是按类别看最近收到了什么，新的在前、正文一行，读一段对话要旧的在前、正文完整，放进一个命令的话，顺序和截断都得跟着参数变。
- `topics [<聊天名或 id>]`：每日读取拆出的话题（见「每日读取」），新的日子在前，同一天里按拆出的顺序，默认最多 50 个，更多时最后一行写一共几个。每个话题一段：编号、日子、聊天、标题、模型挑没挑、属于工作还是兴趣，然后是要点、理由和消息数，有纠正时是我最新的一条纠正，最后是第一条消息的链接。可以只看一个聊天；`--day` 是一天，`--since`、`--until` 选这段时间碰到的日子（`--since 7d` 从 7 天前那一天起，`--until 2026-11-06` 到 11-05 为止）；`--search` 找标题、要点和组成它的消息里的文字（不分大小写）；`--picked` 只列挑出的、`--not-picked` 只列没挑的，纠正过的话题按我最新的纠正算。
- `corrections`（或 `corrections list`）：我对每日读取挑没挑的纠正，旧的在前：编号、哪个话题（标题、聊天、日子、模型挑没挑）或者漏挑的聊天和日子、我说该挑、不该挑还是漏挑、我的原话和记下的时间。
- `corrections pick <话题编号> <我的原话>`、`corrections unpick <话题编号> <我的原话>`：这个话题该挑、不该挑，按我的原话记一条纠正（几个参数用空格连起来）。打印「话题 #12 标题（聊天 日子）：模型挑出 → 我说不该挑（纠正 #3）：原话」，有过纠正时左边是上一条纠正。和最新的一条纠正说的一样、原话也一样，或者没有纠正而模型本来就是这样挑的，什么都不改。话题的 `picked` 不变，纠正另外记（见「每日读取」）。
- `corrections missed <聊天名或 id> <日期> <我的原话>`：这个聊天这一天有该挑的事，却没有拆成话题，没有话题可指。先用 `topics` 看那一天没挑的话题里有没有它，有的话用 `corrections pick`。日期是今天或以后时拒绝（那天还没有读）；那个聊天那一天没有读过（级别不是每日或即时，或者还没读到）时照样记下，提示一句怎样让它以后每天被读。同一个聊天、同一天、同样的原话记过时不再记。
- `corrections remove <编号>`：删掉一条纠正（我说错了，或者 agent 记错了），编号不会再给别的纠正；话题回到上一条纠正，没有了就回到模型的判断，打印它现在的样子。
- `groups`：从 open-lark 读出我所在的全部群，显示级别（我定的写「我定的」，没有级别的写「未分级（按只存不看）」）、名称、人数、最近活跃时间；`--json` 里每个群带着它的级别记录，没有级别时是 null。
- `level`（或 `level list`）：有级别的聊天，按级别排列，每个带着谁定的、从什么时候开始、理由，我定的还带着模型的判断（如果有）。
- `level set <级别> <聊天名或 id>... [--reason 文字]`：由我定聊天的级别（`instant`、`daily`、`store`、`ignore`，见上面「聊天级别」），模型以后不改它。聊天按完整名称、id 或名称中唯一的一段文字找，私聊（比如和某个机器人的私聊，定为只存不看就不再把它发的消息交给模型）也可以，名称对应多个聊天时列出它们并拒绝；存储里找不到时先从 open-lark 读一遍我所在的群。每个聊天打印原来的级别和现在的级别，没有级别时写它按什么级别处理（「未分级（按即时）」），有理由时接着写理由。`--reason` 是我的理由，作为这个级别的理由记下（`level list`、`level history` 和写「关于TA」时的纠正题里都看得到），定了几个聊天就给几个聊天；不带时理由为空。已经是我定的这个级别、又没有新的理由时什么都不改，原来的理由留着；只换理由时级别和开始的时间不变，也不算一次级别的改动。定为即时的时刻起这个聊天的消息交给模型，之前的不补；定为即时的是话题群时照样定，但会提示：话题群只能收到推送来的消息（见上面「话题群」）。改动直接写进存储，正在运行的收集器处理下一条消息时就按新的级别判断，不需要重启。
- `level clear <聊天名或 id>...`：取消我定的级别，回到模型的判断，模型还没有判断过时私聊按即时、群按只存不看；只能取消我定的。已经存下的消息不受影响。
- `level history [--since 时间]`：级别的改动（见「聊天级别」），新的在前，默认最近 7 天：时间、聊天、原来和现在的级别（我定的写「我定的」）、我改的还是模型改的、理由。最后一行数一下：一共几次改动，我改了几次、其中纠正几次，模型改了几次。`--since` 的写法和 `list` 的一样。
- `level grade [<聊天名或 id>...]`：让模型现在给这些聊天分级，不写聊天时是最近 7 天有消息、级别不是我定的全部聊天（见「给聊天分级」）。不等样本，也不管它们到没到时间。它在命令行的进程里经 herdr 直接问模型，不经过加工端，所以要配置好模型机器；加工端自己的分级正好在跑时，模型机器上会多一个 claude。聊天按名称或 id 在存储里找，规则和 `level set` 一样，但不从 open-lark 读：存储里没有消息的聊天也没有可分的。我定了级别的聊天拒绝，要先 `level clear`。每个聊天打印原来的级别、现在的级别和模型的理由；有聊天没分成时列出它们和原因，退出码是 1。
- `status` 还显示加工端最近一轮和最近成功的时间、待加工的消息数（包括等着交给模型的我的表情回复）、跳过的消息数（见上面「失败时」）和未结束的事项数；加工端的错误记在同一个错误列表里，来源是「加工」。另一行是整理：上次完成的时间、整理了多少个事项、关掉了多少个，以及下一次在什么时间之后；之后的整理失败了时，显示失败的时间和原因（下一轮再试）。再一行是「关于TA」：写的时间、多少字、根据多少条我发的消息和几条说明，以及下一次在什么时间之后；之后写失败了时，显示失败的时间和原因。还有一行是分级：上次分级的时间、几个聊天、分成了几个（没分完时带上错误），然后是现在有几个聊天等着分级（刚有聊天没分成时写几点以后再分）、开始全收不满 2 天时什么时候开始，或者下一次在什么时间之后，最后是模型定了级别的聊天数；分级的错误来源是「分级」。再一行是每日读取：最近读完的一天、读完的时间、几个聊天、挑出和没挑的话题数、交给批次的消息数和放弃了的聊天；之后没读完时显示哪一天、错误和几点以后再试，否则显示现在要读的日子，或者下一次读哪一天、在什么时间之后；停机以后没补读的日子也列出来；读取的错误来源是「读取」。
- `process`：运行加工端（常驻），常驻时也给聊天分级（见「给聊天分级」），每天早上读一遍前一天的聊天（见「每日读取」）。`--once` 只运行一轮就退出，不分级，不读，和常驻时的一轮一样：把积压处理完，到了时间也写「关于TA」、整理一次（上一次已经超过间隔，或者还没有过，或者「关于TA」或说明变了）；批次、「关于TA」或整理有失败时退出码是 1。
- `profile`：「关于TA」的全文、写的时间和根据，以及我的说明（编号、原话、记下的时间）；`--json` 输出存储里的原样。
- `matters`（或 `matters list`）：未结束的事项，紧急的在前，每个带编号、紧急程度、标题、谁、要我做什么、期限、来源消息数、所在聊天和链接；`--all` 连同已结束的事项和结束理由。
- `matters close <编号> [--reason 文字]`：由我关掉一个未结束的事项，和卡片上的「完成」走同一条路：记为我关掉的（`closedBy` 是 `owner`），理由是我给的，不给时为空（汇总里写「你关掉的」）。理由正好是「不归我」时和卡片上的「不归我」一样，之后模型会把它当作我说过不归我的事（见「关于TA 和说明」）。打印「#12 标题：未结束 → 已结束：你关掉的：理由」；事项已经结束时什么都不改。
- `matters reopen <编号>`：重新打开一个结束了的事项（模型关掉的、我关掉的都可以），结束的理由和时间清掉；没有结束时什么都不改。`matters close` 和 `matters reopen` 改了事项以后，运行中的加工端在 15 秒内让最新那份汇总的卡片跟上（见「汇总」）。
- `notes`（或 `notes list`）：我的说明，编号、原话和记下的时间。`notes add <文字>`：把参数按我的原话记成一条说明（几个参数用空格连起来）；同样的话已经记过时不再记。`notes remove <编号>`：按编号删掉一条，编号不会再给别的说明。说明存在存储里，加工端和分级自己去读：加工端下一轮按新的说明重写「关于TA」，再把未结束的事项整理一遍；说明一小时内不再变时，分级的模型按它重新给聊天分级（见「关于TA 和说明」和「给聊天分级」）。
- `ignore`（或 `ignore list`）：忽略名单，每个发送方带着从什么时候起忽略。`ignore add`：按完整名称、id 或名称中唯一的一段文字把发送方加入忽略名单，只能是发过要交给模型的消息的发送方（我自己除外；消息都只是存下的发送方不在其中），对应多个时列出它们并拒绝；已经在名单上的什么都不改。`ignore remove` 移出名单，之后的新消息照常交给模型。改动直接写进存储，加工端下一批就按新名单处理。
- `bot create`：创建管家机器人的飞书应用，见上面「创建应用」。`bot update`：给已经配置的应用加上新应用有、它还没有的权限和回调，见上面「给已有的应用加上卡片回调」。
- `status` 还显示机器人的连接状态（已连接、正在重连、连接失败和原因；加工端没在运行时显示未运行）、上一份汇总的时间，以及有要发的内容时下一份汇总的时间和其中新事项、结束事项的数量。

## 安装为用户服务

在运行 open-lark 的机器上作为 systemd 用户服务运行。服务运行的是复制到 `~/apps/herdr-butler` 的一份代码，不是仓库的工作目录，所以切换分支、修改或测试仓库里的代码都不会改变正在运行的服务。配置（`~/.config/butler/`）和数据（`~/.local/share/butler/`）都不在这个目录里，重新复制不会碰到它们。

1. 在仓库根目录复制代码（不带测试）：

   ```bash
   mkdir -p ~/apps/herdr-butler
   rsync -a --delete --exclude test/ --exclude node_modules/ butler/ ~/apps/herdr-butler/
   (cd ~/apps/herdr-butler && npm ci --omit=dev --registry=https://registry.npmjs.org)
   ```

2. 按上面「配置和数据」写好 `~/.config/butler/butler.env`（权限 600）。
3. 把下面的单元文件保存为 `~/.config/systemd/user/butler.service`（Node 路径和 open-lark 服务用的一致，按需调整），然后执行 `systemctl --user daemon-reload && systemctl --user enable --now butler`。

```ini
[Unit]
Description=Butler collector: Feishu messages that concern me, from open-lark
After=open-lark.service

[Service]
Type=simple
WorkingDirectory=%h/apps/herdr-butler
ExecStart=%h/.local/share/fnm/node-versions/v24.13.0/installation/bin/node --disable-warning=ExperimentalWarning cli.mjs run
Restart=on-failure
RestartSec=10
UMask=0077

[Install]
WantedBy=default.target
```

加工端是第二个用户服务，单元文件 `~/.config/systemd/user/butler-processor.service`。它通过 herdr 用 SSH 连模型机器，所以服务里要能不经交互地 SSH 过去（不带口令的密钥，或者把 SSH agent 的套接字传给服务），`BUTLER_HERDR` 写 herdr 的完整路径：

```ini
[Unit]
Description=Butler processor: matters from the collected Feishu messages, by a model reached through herdr
After=butler.service

[Service]
Type=simple
WorkingDirectory=%h/apps/herdr-butler
ExecStart=%h/.local/share/fnm/node-versions/v24.13.0/installation/bin/node --disable-warning=ExperimentalWarning cli.mjs process
Restart=on-failure
RestartSec=30
UMask=0077

[Install]
WantedBy=default.target
```

配置了机器人时，加工端的服务同时运行机器人；`bot create` 之后要 `systemctl --user restart butler-processor`。机器人直接连 open.feishu.cn，不经过代理。

第一次启动前，用命令行加好忽略名单（比如 `./cli.mjs ignore add Zebra2.0自动化投放平台`），否则这些发送方积压的消息会交给模型。加工端停止时等正在运行的那一批结束，最多 20 秒；没等到的那一批下次重做，留在模型机器上的工作区在下次启动时关掉。

更新：在仓库根目录重新执行第 1 步，再 `systemctl --user restart butler butler-processor`。

日志看 `journalctl --user -u butler`：里面有推送的连接和断开，以及每一条错误（同样记在存储里，`status` 能看到）。

收集器停止时会等正在进行的一轮对账结束，最多 5 秒。每次写入都是一个事务，游标只在它之前的消息存好之后才前进，所以被打断的那一轮下次会重做，不会丢也不会重。

## open-lark 重启时

收集器的重启或部署不影响 open-lark。open-lark 重启时推送连接断开，收集器按 1 秒起、最长 30 秒的间隔重连；open-lark 不可达的期间，每轮对账只记一条连接错误。连上之后立即对账一轮（包括话题列表和 @我补扫），补上重启期间丢失的推送和 open-lark 启动时补进来的消息。如果 open-lark 起来之后先处于轮询或重连状态，水位停在重启前最后一次健康的时刻，等同步回到 `live` 再对账一轮。

## 验证

```bash
cd butler
npm test
```

测试用一个假的 open-lark（`test/fake-open-lark.mjs`，HTTP 加 WebSocket）。它按 open-lark 真实的接口形状和怪癖实现：只读 token 的权限、按 open-lark 的规则规划消息窗口（多给 5 个位置，以它记下的聊天最后位置为上限，`maxPosition` 只算正的位置）、每个聊天都有一条位置 0 的旧消息、记下的最后位置可以停在 0 或旧值（重现话题群的尾页占位和空页）、普通群的话题回复位置 ≤ 0 并按时间混入、话题群的回复有位置、只有我能看到的临时消息放在前一条消息的位置上、已删除的消息不出现在页里但能按 id 读到、推送可能缺少消息内容、可能重复、有 `sync:complete` 哨兵、话题回复数变化时重发根消息，以及可以只写库不推送。覆盖：

- 推送里的新消息按类别入库；@所有人 不算 @我；和我无关的群消息以 `stored` 入库，忽略的聊天里只有和我有关的入库；机器人在私聊里发的不是 `dm`，按私聊的级别收：还没有级别时是 `instant`、交给模型，模型定为只存不看以后只存、不再交给模型（人发的私聊只记 `dm`）；我在任何聊天里发的消息都以 `own` 入库（推送来的和只写库、按位置读到的都一样），回复它的消息不带被回复者时也按存储里的这条认出是回复我；记录的各个字段和链接。
- 同一消息重复推送只存一份；编辑和撤回更新原记录，更早读到的旧内容不会覆盖它。
- 推送缺少内容时按 id 补全。
- 收集器停机期间的消息（推送丢失和只写库的都有，含私聊、即时级别的群和其中的话题回复、别的群里的 @我和回复我的、忽略的群里的 @我、超过一页的私聊、停机期间新出现的聊天）在启动后补齐，和我无关的以 `stored` 入库，忽略的群里和我无关的不入库；运行期间 open-lark 只写库不推送的消息在下一轮补齐；没有新普通消息时的话题回复也能读到。
- open-lark 重启：推送重连，重启期间的消息补齐。
- 话题回复数变化时补取回复（open-lark 后台同步只重发根消息），正在取回复时又通报的回复也会取到；私聊里的话题回复从开始收集时取起，不管私聊定了什么级别；停机期间我参与的话题群话题里的新回复通过话题列表补齐。
- 取回复失败：404 或 500 的话题在一连串推送下只取一次；403 或 404 的话题记一条错误后不再等待重取；500 的话题只在之后的对账轮次重试，到次数上限记一条错误放弃，之后通报了更多回复再重新去取。
- @我在没有级别、会话列表也没变化的群里能被补扫到（搜索一并找到的只 @所有人 的消息以 `stored` 入库），所在聊天在同一轮里补上名称；飞书搜索失败时记错误且扫描窗口不前进；open-lark 还没存下的 @我按位置读到，或留到以后重试。
- 级别立即生效：定为即时的群从定的时刻起的消息是 `instant`，之前的是 `stored`，它每轮都按位置读，会话列表没有变化时也读；取消以后的消息只存，也不再每轮读。
- open-lark 不处于 `live` 时水位不前进，同步回到 `live` 时触发对账并补上这期间的消息；open-lark 报告缺口时之后的轮次重试，一直有缺口就记一条错误并跳过。

## 已知限制

- 即时级别的话题群不按位置读：我没参与的话题里的消息只能靠推送收到，收集器停机或断线期间的补不上（见「话题群」）。其他级别的聊天也不为补齐它们的消息多读：只存的消息靠推送和本来就要做的按位置读，推送漏掉的补不上。
- 开始全收以后的头 2 天，以及之后新出现的聊天的头一天，模型还没有给它们分级：没有级别的群都按只存不看、私聊都按即时。机器人和 agent 的私聊这期间照旧全部交给模型，不想要的用 `level set store` 定为只存不看。
- 分级的样本只有开始全收以后存下的消息和以前就收的和我有关的消息；以前不活跃、开始全收以后又没说话的聊天，最近 7 天有消息也可能只有很少的样本。消息数从开始全收算起，头一周的「每天多少条」按实际的天数算。
- 一个总让模型给不出可用回答的聊天，几次之后单独一个提示，每次分级都再试一次并记一条错误（加工端每 10 分钟最多一次），不会自己放弃；给它定一个我的级别（`level set`）就不再交给模型。
- 模型坚持把一个刷屏的聊天定为即时时，刷屏期间它每小时被重新分一次。
- 说明的变化由正在运行的加工端发现：加工端停着时改的说明，从它启动、看到变化时算那 1 小时。
- `level grade` 在命令行的进程里运行，和加工端的分级互不知道：两边可能同时给同一个聊天分级，后写的为准，模型机器上也会多一个 claude。
- 找等着交给模型的消息（待加工数、跳过忽略名单也一样）要读一遍所有交给过模型的消息的索引，只存的消息不读。这部分随时间增长：在一个 52 万条消息、其中 4.3 万条交给模型的存储上约 20 毫秒，每轮读几次。
- 推送缺失时，普通群里话题回复的补齐依赖三条途径：按位置读聊天时按时间混入的回复、根消息回复数的变化、话题列表。即时级别的普通群里某个我没参与的话题，如果它的回复是 open-lark 在收集器停机期间才后台同步进来的（回复时间早于收集器上次读到的位置），而那次重发根消息的推送又丢了，就补不上。
- 表情回复只靠推送和之后再读到这条消息时更新：收集器停机或推送断开期间的表情变化，要等这条消息再被读到（按位置读时的重叠、取话题回复）才会记下，否则就没有。管家存储里没有的消息上的表情不记。
- 回复我的消息靠 `replyTo` 判断，open-lark 没有存下被回复的消息、管家存储里也没有时，判断不出来。
- 参与话题的判断只往回看话题最近的 500 条回复；在更长的话题里，我很早以前的回复找不到。
- 收集器跟随 open-lark 当前登录的账号，不检查账号是否变化。
- 加工端交给模型的 claude 是交互式的，它的会话记录（包括交给它的消息）留在模型机器上 `~/.claude/projects/` 里对应 `BUTLER_MODEL_CWD` 的目录：`--no-session-persistence` 只能和 `--print` 一起用。
- 提示是本机 herdr 命令行的一个参数（`herdr agent prompt` 不能从标准输入或文件读），Linux 上一个参数最多 128 KiB；加工端把提示限制在 80 KB，超过就拆小批次。
- 模型对某条消息总是给出空回答时，herdr 那边和 API 出错一样，都是「没有回复」，分不出来。这种消息不会被跳过，会一直留在队首，后面的消息也跟着等；错误记在 `status` 里。要分开这两种情况，需要 herdr 把 claude 的 StopFailure 和空回复分别报出来。
- 已经处理过的消息之后被编辑或撤回，不会再交给模型。
- 「关于TA」只来自我在飞书上说过和做过的事，看不到组织架构和平台上的 owner 信息，可能写偏，要靠说明纠正。说明是和管家说话的 agent 按我的话用 `notes add` 写下的，代码不核对它和我说的话是否一字不差。
- 「关于TA」新归纳了什么由模型自己对比上一版说出来，代码不比较两版文字：模型漏报或者把换了说法当成新内容时，发给我的新推断就会少一条或多一条。
- 纠正题做对的比例只说明「关于TA」加说明能不能让模型还原我定的级别。提示要求模型把纠正推广成一类聊天，不要逐个写出聊天和级别，但代码不检查；模型照抄了聊天名时，比例会偏高。做错的题要等下一次写「关于TA」（最长一天）才用上，我定了级别以后也要等下一次「关于TA」才重做。
- 重做纠正题每次都把全部的题交给模型，我定的级别越多，每次重做的模型运行越多（一个提示最多 25 个聊天）。
- 整理时模型只看到每个事项最近的 3 条来源消息、它开始以后我在它所在聊天里最近的 5 次回应（我的消息和加了表情的消息）和所在聊天最新的 8 条消息。别人的后续在很热闹的群里早已被挤出这 8 条，或者事项的后续（包括我的回应）发生在别的聊天里，比如我在私聊里回了群里问我的事，模型就看不到。
- 每周的分级变化卡片一周最多列 36 个聊天，说明变了以后模型大批改级别时，其余的在卡片上改不了，要到 herdr bridge 里绑定了管家 agent 的飞书群里改。分级列表只在第一次分级以后自动发一次，也不跟着级别更新；要看现在的，到那个群里问（agent 用 `level list`）。
- 命令行改了事项以后，汇总的卡片要等加工端下一次看记号（最多 15 秒）再加上更新前几秒的合并才跟上；加工端停着时改的事项，它启动以后也不补这次更新，要等下一次事项变化或下一份汇总。
- 分级列表在加工端自己开始的分级第一次分成聊天以后发。第一次全量分级中途有运行失败时，列表里只有已经分成的那些；其余的之后分出来，在每周的分级变化里列出。
- 新推断发送失败时不重发，那一次的内容只在 `butler profile --json` 里能看到。
- 汇总卡片只在发出后 14 天内跟着事项更新（飞书的限制）；更新失败时不重试，卡片停在上一次更新的样子，直到事项再有变化。卡片的 JSON 按飞书卡片 JSON 2.0 的文档写，测试只检查结构，飞书是否接受要发出去才知道。
