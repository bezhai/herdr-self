# Butler 收集器和加工端

工作管家的前两部分，都在运行 open-lark 的机器上常驻运行：

- **收集器**（第一阶段）从 open-lark 的只读 Agent 接口（`/agent/v1`）把和我有关的飞书消息收进管家自己的存储。它只收集和记录，不分类，也不调用模型。spec 见 `.local/prd/butler-message-collection.md`。
- **加工端**（第二阶段）把收到的消息交给模型，整理成事项：谁、要我做什么、期限、紧急程度，加上原消息的链接；后续消息归到原事项上，事项结束时记下理由。见下面「加工端」，spec 见 `.local/prd/butler-processing.md`。

汇总和对话由之后的管家机器人负责，不在这里。总体方案见 `.local/prd/butler-overview.md`。

## 收集什么

一条消息满足下面任意一条就收进来，可以同时属于几类：

| 类别 | 含义 |
| --- | --- |
| `mention` | 别人 @我。只 @所有人 的不算；记录里另有 `mentionsAll` 标出消息是否 @所有人 |
| `dm` | 私聊里的全部消息，包括我自己发的和机器人发的 |
| `reply` | 别人回复我的消息：被回复的消息是我发的（`replyTo.senderId` 是我，或者被回复的消息在管家存储里且是我发的） |
| `thread` | 我参与过的话题（我发起，或在里面回复过）里，从我第一次参与起的消息，包括我自己的 |
| `watched` | 关注名单里的群从加入名单起的全部消息 |

收集从收集器第一次启动的时刻开始，更早的消息不收。不在关注名单里、也和我无关的群消息不进存储，留在 open-lark 里。

每条记录有：消息 id、聊天 id、聊天名称和类型（`direct`、`group`、`topic`）、发送者 id、名称和类型（`user`、`bot`、`agent`）、发送时间、话题信息（`threadRole` 为 `none`、`root` 或 `reply`，以及话题根消息 id 和被回复的消息 id）、纯文本和 open-lark 给出的结构化内容（`parts`）、类别、是否我发的、是否已撤回、是否被编辑过、内容是否不可读，以及在 open-lark 网页里打开这条消息的链接。链接的格式和 open-lark 自己的一样：`<网页地址>/messenger/<聊天 id>?message=<消息 id>&position=<位置>`，话题里的消息再带 `&thread=<根消息 id>`，回复定位到根消息的位置。

同一条消息只存一份，按消息 id 更新。编辑和撤回更新这一份记录：撤回后记录跟随 open-lark 的显示，open-lark 保留了原文就保留，否则内容为空，`isRecalled` 为真；撤回和编辑的标记一旦为真就不再变回去，比编辑或撤回更早读到的旧内容也不会覆盖新内容。类别只会增加：一条消息因为当时在关注名单里被收进来，之后这个群移出名单，它仍然是 `watched`。

open-lark 自己的端到端加密消息和密聊消息读不到原文，记录里 `unreadable` 为真，文本是 open-lark 给出的占位文字。

## 为什么要对账

open-lark 的推送（`/agent/v1/events` WebSocket）只推送当下发生的事：没有游标，不能重放，open-lark 重启时连接断开，期间的事件就没了；open-lark 启动时的积压事件在 Agent 端口开始监听之前就发出了。更重要的是，open-lark 补洞、补尾、回填历史、后台同步话题回复时，消息只写进它的数据库，不发事件（后台同步话题回复时只把根消息重新推送一次）。所以只听推送一定会漏。

收集器因此把推送只当作「尽快发现新消息」的手段：推送里的消息立即入库，而完整性靠对账保证。对账读的是 open-lark 已经存下的数据，不管这些数据是推送来的还是事后补的。

### 对账怎样进行

对账一轮一轮地串行进行，触发时机是：启动时；推送连接建立或重连之后（先连上再对账，这样两者之间不会有空隙）；open-lark 的同步状态回到 `live`（并且是 `frontier` 模式）时；之后每分钟一次。每一轮做这些事：

1. **找出有变化的聊天。** 按 open-lark 的排序（置顶在前，其余按最近活跃从新到旧）分页读私聊和群的会话列表，读到最近活跃早于「水位」的会话就停。每个会话的「最后一条消息、最近活跃时间、更新时间」组成一个签名，和上次读完这个聊天时记下的签名不同，就把这个聊天标记为待读（话题群除外，见下面「话题群」）。标记存在数据库里，这一轮读不完的下一轮接着读。
2. **按位置读这些聊天，以及每一轮都读关注的群。** 每个聊天记一个位置游标，从游标往后分页读 `GET /conversations/:feedId/messages?afterPosition=…`，每页 100 条。从没读过的聊天，从最新的消息往回读到收集开始的时刻为止。读到的每条消息都交给同一套规则判断类别，不相关的直接丢掉。不只是私聊和关注群：所有有变化的普通群都按位置读，因为「回复我的消息」可能出现在任何群里，而飞书没有可以按时间补查「回复我的」的接口（open-lark 自己的上下文收集也只能查它的本地账本）。open-lark 的数据库里已经有这些位置的消息时，这一页由它的本地数据库回答；缺少时，它会在这次请求里先去飞书取（实测一页约 4 次飞书调用、1.7 秒）。所以每个聊天每轮最多读 5 页，每轮最多读 50 个聊天，读不完的下一轮从游标接着读。
   - **游标和「读完」。** 游标只认正的位置。open-lark 给出的尾页没有正的 `maxPosition` 时不算读到了：不记游标，聊天保持待读。往后读到 open-lark 说没有更新的消息时，还要确认读到了会话列表显示的那条最后一条消息：它在这次读到的消息里，或者它的位置不超过游标。不在读到的消息里时，它的位置先从管家自己的存储里取（推送来的消息已经存下了，而消息的位置不会变），存储里没有才用 `GET /messages/:id` 查。这个请求读的是 open-lark 的数据库，但它先向飞书确认我还能看这个聊天（同一个聊天一分钟内只确认一次）。它的位置超过游标时，还有一种情况算读完：从游标的下一个位置到它为止，每一个位置上的消息都已经在管家的存储里，这时游标移到它的位置。用 `GET /messages/:id` 查到的那条先照常交给规则判断和记录（open-lark 生成它和生成每一页里的消息用的是同一段代码，记录它和从页里读到它没有区别），它自己就代表它那个位置，只要求它之前的位置都已存下；所以只差一个位置时，查一次就算读完，不管这条消息和我有没有关系。主序列的位置是连续的整数，每个位置一条消息，所以这时主序列里没有漏读的。例外是只有我能看到的临时消息（`isEphemeral`）：open-lark 把它放在它前一条消息的位置上，和那条共用一个位置，所以存下的临时消息不算占了这个位置；查到的最后一条是临时消息，或者是已经删除的消息（每一页都不包括它），也不用来判断。范围长于一个位置时，实际上几乎只在私聊和关注群里能凑齐：管家在那里存下全部消息（收集开始或加入关注之前的不存，跨到那时的范围就凑不齐），其他群只存和我有关的。没读到就保持游标和待读，之后的轮次重试，连续 5 次都没读到就记一条错误，等这个聊天下次有变化再读。原因是 open-lark 每一页的范围都以它记下的这个聊天的「最后位置」为上限，而这个值可能落后，甚至是 0（见下面「话题群」）：这时它对尾页只回一条位置为 0 的旧消息、不给 `maxPosition`，往后读则回空页并说没有更新的消息，看起来就像读完了。实测还见过这个值连续几轮停在最新一条消息的前一个位置：一个和机器人的私聊里，最新的那条早已推送过来、存进了管家的存储；一个不关注的群里，最新的那条和我无关，管家没有存。旧版本留下的游标 0 当作从没读过，从尾部重新读。
3. **读我参与的话题的变化。** 分页读话题列表 `GET /threads/feed`（我发起、回复过或关注的话题，按最近活跃排序），读到早于水位就停；回复数和上次看到的不同的话题，用 `GET /messages/:id/thread` 取回复。这一步也是收集器得知「我在它停机期间参与了某个话题」的途径。
4. **取回复数变多了的话题。** 不管是推送、按位置读到的还是话题列表里看到的根消息，只要它属于私聊、关注群或我参与的话题，并且回复数比上次多，就取一次这个话题的回复。open-lark 后台同步话题回复时只重发根消息，就是靠这一条补上的。取回复失败时：open-lark 回答 403 或 404（我已经退出这个聊天，根消息没了）就记一条错误，不再取；其他失败只由之后的对账轮次重试，每轮最多一次，失败 10 次后记一条错误放弃。放弃或读不到的话题按已经通报过的回复数记下，同样的通报不会再让它重来；之后根消息通报了更多回复，才算新的工作，重新去取。
5. **@我补扫。** 用 `POST /search/mention-history`（飞书的 @我 搜索）扫描从上次扫到的时刻往前 10 分钟到现在的时间窗口，补上会话列表没有变化、因而第 1 步发现不了的 @我。搜到的消息用 `GET /messages/:id` 取完整内容；open-lark 还没存下的，改读它所在位置附近的那一页（这会让 open-lark 去飞书取），还取不到就记进待补取的列表，之后每轮重试，最多 20 次。飞书搜索失败时 open-lark 返回空结果并标出失败，这种情况记为错误，扫描窗口不前进。这一步和话题列表一样会访问飞书，所以平时每 10 分钟一次，只在启动、重连和同步恢复时立即做。

几个细节：

- **水位。** 第 1 步和第 3 步的「水位」是上一轮完整读完列表的开始时刻再往前留 15 分钟余量，而且只有当这一轮从开始到结束 open-lark 都处于 `live` + `frontier` 时才前进。open-lark 轮询（`polling`）、重连或补数据期间，聊天会带着比当前更早的活跃时间出现；水位停在最后一次健康的时刻，同步恢复后的那一轮就从那里列起，不会漏掉这期间的聊天。
- **重叠和重复。** 每次从游标往前 3 个位置开始读，相邻两页也重叠 3 个位置，open-lark 自己的页还会多给 5 个位置。普通群里的话题回复没有正的位置（位置 ≤ 0），open-lark 按时间把它们混在页里：只包括这一页第一条到最后一条之间（最后一页则是第一条之后）的回复。重叠保证每一页的第一条不晚于上次读到的最后一条，所以没有新的普通消息、只有新话题回复时也能读到。重复读到的消息按 id 更新，没有副作用。
- **缺口。** open-lark 说某一页有它没能从飞书补上的缺口（`syncState: gap`）时，游标不前进，之后的轮次重试；连续 5 次仍有缺口就跳过它并记一条错误。
- **限流。** 发往 open-lark 的请求一次一个，相邻两个之间隔 100 毫秒；每轮最多读 50 个聊天（每个最多 5 页）、30 个话题，剩下的留到下一轮。每个聊天限 5 页，是为了让一个积压很多、而 open-lark 又要去飞书补的聊天每轮最多占十来秒，不会像实测那样一个聊天占住一轮好几分钟；一天的积压（几千条）也只需要几轮读完。
- **推送带来的工作。** 推送里的消息让一个话题需要取回复（第一次有了需要取的回复，或者通报的回复数比以前通报过的都多，包括正在取的时候又多出来的），或者带来一个还没有名称的新聊天，收集器会在 1 秒后顺带处理，和对账轮次串行。只处理这些消息新带来的工作：之前就在等的话题（比如取回复失败、等着重试的）不会因为又来了推送就再取一次，否则每条推送都会重试一遍，而每次重试都可能让 open-lark 以我的身份访问飞书。
- **推送里的细节。** 没带消息内容的推送用 `GET /messages/:id` 补全；`sync:complete` 这样的哨兵表示 open-lark 刚在后台补完一个聊天，这个聊天在下一轮按位置读；同一条消息重复推送只更新一次记录；我自己发送时的本地占位消息不入库，等服务端的消息替换它。

### 话题群

话题群（`chatMode: topic`）不按位置读，关注了也不读。原因在 open-lark：它每 5 分钟（以及群设置推送时）从飞书重读一遍会话卡片来刷新状态，并把卡片里的 `last_message_position` 写成这个聊天的「最后位置」，取不到时写 0（代码里是字符串 `"0"`，不会被当成「没有」而保留旧值）。话题群的卡片看来没有这个字段：实测在一次刷新之后话题群都变成了下面的样子，普通聊天没有。普通聊天在存下新消息时会把这个值往前推，话题群却被特意跳过，只能等以后某次推送带来的聊天信息再改回来。在这之间，话题群的每一页都只有位置 0 的那条旧消息或者是空页。实测时一次刷新之后，几个话题群同时变成这样，过一会儿又有个别恢复；旧版本据此把三个话题群的游标记成了 0，其中一个从 0 往后读了 100 多页，每页都要 open-lark 去飞书补，一轮用了两分半钟，最后还在空页处停住，漏读了最新的两条。

话题群里和我有关的消息不靠按位置读也能拿到：话题群里的每条消息要么是一个话题，要么在某个话题里（实测两个话题群的 210 条消息里，174 条是话题回复，35 条是话题本身；还有 1 条不是话题回复类型、却带着被回复的消息，open-lark 把它算在那个话题的回复里，取话题回复时会一起取到；这样的消息回复我时记为 `reply`，但不会记为 `thread`）。所以别人回复我，一定发生在我发起或回复过的话题里，由话题列表（上面第 3 步）发现；@我 由 @我补扫发现；推送来的消息也照常入库。代价是关注的话题群：我没参与的话题里的消息只能靠推送收到，收集器停机或断线期间的补不上。`watch add` 加入话题群时会提示这一点。

### 只读

收集器只用 open-lark 的只读 token，所有请求都经过同一个检查：只允许 GET，以及唯一一个读用途的 POST `/search/mention-history`；任何路径里有 `pins` 的请求都会被拒绝，因为 `GET /conversations/:feedId/pins` 会清除飞书里置顶消息的未读标记。它从不发消息，也读不到 open-lark 的全权限 token 和数据库凭据：配置里只放只读 token，收集器不读 open-lark 的 `app.env`。代价是 token 轮换时要改两处。即使配置里误放了全权限 token，收集器发出的仍然只有上面这些读请求。

open-lark 的 Agent 接口标为旧接口，没有稳定性承诺。收集器启动时用 `GET /agent/v1` 的路由目录检查它要用的路由都在，不全就记一条错误，每分钟重新检查，直到齐了才开始收集。

## 加工端

加工端是另一个常驻进程，和收集器共用 `butler.db`。它只读收集器的表，只写自己的表：忽略名单、哪些消息处理过、事项和它们的来源消息、每次模型运行的记录。每 10 分钟，它把还没处理过的消息按时间从早到晚分批交给模型，一次一批，每批最多 40 条，直到处理完。

### 交给模型什么

每批新消息，加上帮助理解它们的上下文：同一聊天里在它们之前的 8 条消息、话题的根消息和被回复的消息、这些聊天里未结束事项最近的 3 条来源消息，以及全部未结束的事项（编号、标题、谁、要我做什么、期限、紧急程度）。每条消息带着收集器记下的事实：发送者和类型（人、机器人、agent），是不是我发的，类别（`mention`、`dm`、`reply`、`thread`、`watched`），是否 @所有人，在话题里的位置，是否撤回或编辑过，内容是否不可读。消息和事项以这一次的编号交给模型（消息是 `m1`、`m2`……，事项是它的编号），消息 id 和链接都不经过模型。一条消息最多给 1500 个字，再长的截断。

### 模型决定什么，代码检查什么

什么算事项，哪些消息属于同一件事（包括把新消息归到已有事项上），紧急程度（`high`、`normal`、`low`），期限，已有事项结束没有、为什么结束，都由模型判断。代码里没有关键词、发送者或群的规则，收集器的类别和发送者类型只作为事实交给模型权衡。

我自己发的消息只作为上下文：它们不能单独构成事项，但可以说明某个事项已经处理了。一批里只有我自己的消息、又没有未结束的事项时，不调用模型，直接记为处理过。

模型只输出一个 JSON 对象：`new` 是新事项（标题、谁、要我做什么、期限、紧急程度、来源消息的编号），`updates` 是对已有事项的修改（新归入的消息、改动的字段、关闭及理由）。加工端只采纳引用这一批编号的部分。下面这些不采纳，各记一条错误：引用了不存在的消息或事项，新事项没有引用任何一条别人发的新消息（只引用了旧消息或我自己的消息），关闭事项但没有写理由。模型写的文字里的网址换成「[链接]」，事项的链接由加工端用它最早的来源消息生成，和收集器的消息链接相同。采纳的部分和这一批消息的「已处理」标记在同一个事务里写入。

### 忽略名单

按发送方 id 记录。名单上的发送方的消息不交给模型，也不出现在上下文里。它们被跳过时就记为已处理，所以之后把发送方移出名单，不会把它在名单上期间发的消息补交给模型。

### 模型在哪里

模型是另一台机器（cpu1）上的 claude，经 herdr 调用，claude 访问的网关 token 不离开那台机器。`BUTLER_MODEL_MACHINE` 是 herdr 保存的机器（`herdr machine list`），它指向那台机器上专给管家用的 herdr session，不是我自己用的默认 session。每一批这样运行：

1. `herdr --machine <机器> workspace create --cwd <BUTLER_MODEL_CWD> --label butler-model --no-focus`；
2. 在它的第一个 pane 里 `herdr --machine <机器> agent start <名字> --kind claude -- --tools "" --strict-mcp-config --disable-slash-commands --system-prompt <说明>`：没有内置工具，没有 MCP 服务器，没有技能和斜杠命令，模型只能回答；
3. `agent prompt <名字> <数据> --wait`，等这一轮结束；
4. `agent replies <名字>` 取它最后的回复（由 claude 的 Stop hook 报给 herdr，可能比状态变化晚一点到，所以最多再等 15 秒）；
5. 不管成功与否，`workspace close` 关掉这个工作区，claude 随之退出。

加工端启动时关掉以前被打断、没来得及关的 `butler-model` 工作区。同一个存储同时只能有一个加工端，第二个会拒绝启动，所以批次不会重叠。

### 失败时

连不上那台机器、claude 没有起来、超时（15 分钟）、没有回复、回复不是要求的 JSON，这一批都保持未处理，记一条错误，这一轮停下，下一轮再试；连续失败时每次把批次减半（最少 1 条），成功一次后恢复到 40 条。整个模型出问题时消息不会被丢掉，那台机器断开期间的消息在恢复后补加工。

只有一种失败会让加工端跳过消息：一条消息单独成批，模型给了回答，但回答用不了（不是要求的 JSON，或者超过 64 KiB 被 herdr 截断）。网关或 API 出错时不会是这样：claude 这时运行 StopFailure hook 而不是 Stop，herdr 收不到任何回复（claude 2.1.309 里的说明：「Fires instead of Stop when an API error … ended the turn」）。这时这条消息先放到一边，这一轮接着处理它后面的消息；如果紧接着的那次运行成功了，说明模型本身正常，这次失败记在这条消息上。如果那次也失败了，就算模型的问题，什么都不记，这一轮停下。被记过的消息以后总是单独成批，也不再作为别的消息的上下文；一轮里只试它一次，所以几次尝试至少隔一轮。记满 3 次就把它记为已处理并跳过，同时记一条错误，写明消息 id、所在聊天、发送者、时间、开头的文字和最后一次的原因；`status` 显示跳过了多少条。它挡住后面的消息，最多到它第一次被记上为止（减半到单独成批要几轮）。之后哪次它单独成批成功了，记录就清掉。每次运行的开始和结束时间、消息数、提示大小、是否成功、错误和模型的原始回复都记在 `model_runs` 表里，方便事后看模型为什么这样判断。

### 第一次设置

在加工端所在的机器上保存模型机器，并让 herdr 在那台机器上开一个单独的 session：

```bash
herdr machine add --label cpu1-butler --remote-session butler <cpu1 的 SSH 地址>
ssh <cpu1 的 SSH 地址> 'mkdir -p -m 700 ~/.local/share/butler-model'
```

`machine add` 需要两边的 herdr 版本兼容；它要求批准安装、更新或替换远端 herdr 时，先停下来确认。`BUTLER_MODEL_CWD` 写这个目录在模型机器上的绝对路径：herdr 对不存在的目录和 `~` 开头的路径都会悄悄换成主目录。这个目录在已信任的主目录下面，claude 启动时不会停在信任对话框上。

## 配置和数据

配置文件默认是 `~/.config/butler/butler.env`（`--config` 或环境变量 `BUTLER_CONFIG` 可以换），权限必须是 600，否则收集器和命令行都拒绝运行：

```bash
mkdir -p ~/.config/butler
install -m 600 /dev/null ~/.config/butler/butler.env
# 只取出只读 token，不要把 open-lark 的 app.env 整个复制过来
grep '^OPEN_LARK_AGENT_READ_TOKEN=' ~/.config/open-lark/app.env | sed 's/^OPEN_LARK_AGENT_READ_TOKEN=/BUTLER_OPEN_LARK_TOKEN=/' >> ~/.config/butler/butler.env
```

| 键 | 默认值 | 用途 |
| --- | --- | --- |
| `BUTLER_OPEN_LARK_TOKEN` | 无，必填 | open-lark 的只读 token（open-lark 的 `OPEN_LARK_AGENT_READ_TOKEN`） |
| `BUTLER_OPEN_LARK_URL` | `http://127.0.0.1:8081` | open-lark Agent 接口的地址 |
| `BUTLER_LINK_BASE` | `http://127.0.0.1:3333` | open-lark 网页的地址，用来生成消息链接（open-lark 的 `OPEN_LARK_PUBLIC_URL`） |
| `BUTLER_DATA_DIR` | `~/.local/share/butler` | 数据目录 |
| `BUTLER_MODEL_MACHINE` | 无，加工端必填 | herdr 保存的模型机器的名称（见上面「第一次设置」） |
| `BUTLER_MODEL_CWD` | 无（herdr 用远端的主目录） | 模型在那台机器上运行的目录，绝对路径 |
| `BUTLER_HERDR` | `herdr` | 本机 herdr 可执行文件。systemd 用户服务的 PATH 里通常没有 `~/.local/bin`，服务里写完整路径 |

数据是数据目录里的一个 SQLite 文件 `butler.db`（WAL 模式，旁边还有 `butler.db-wal` 和 `butler.db-shm`），目录权限 700，文件权限 600。里面有消息和它们的类别、每个聊天的名称和读取位置、关注名单、跟踪的话题、待补取的 @我、收集器状态和最近 100 条错误，以及加工端的忽略名单、处理记录、事项和模型运行记录。本阶段不做清理，存储会持续增长；`butler status` 显示文件大小，也可以用 `du -sh ~/.local/share/butler` 查看。

## 运行

需要 Node.js 24（用到内置的 `node:sqlite` 和 `WebSocket`），没有 npm 依赖，不需要 `npm install`。

开发时在仓库里直接运行：

```bash
cd butler
node cli.mjs run        # 或 npm start；也可以直接 ./cli.mjs run
```

常驻运行时用复制出去的一份代码（见下面「安装为用户服务」），切换分支或修改仓库不会影响正在运行的服务。`node:sqlite` 仍标为实验特性，命令行会滤掉它的提示。

## 命令行

```bash
./cli.mjs status [--json]
./cli.mjs list [--category mention|dm|reply|thread|watched] [--since 2h] [--until 2026-10-22T18:00] [--limit 50] [--json]
./cli.mjs groups [--search 文字] [--json]
./cli.mjs watch list
./cli.mjs watch add <群名或 id>...
./cli.mjs watch remove <群名或 id>...
./cli.mjs process [--once]
./cli.mjs matters [--all] [--json]
./cli.mjs ignore list
./cli.mjs ignore add <发送方名称或 id>...
./cli.mjs ignore remove <发送方名称或 id>...
```

命令行可以从仓库里运行，也可以用部署的那一份（`~/apps/herdr-butler/cli.mjs`）；两者读同一个配置文件，用同一个存储。

- `status`：收集器是否在运行（看心跳）、推送是否连接和最近一次收到推送的时间、最近一次对账的完成和成功时间、open-lark 的同步状态、@我补扫和话题列表扫到哪里、各类消息的数量、待补取的 @我、关注群数量、存储位置和大小，以及最近的错误。
- `list`：按类别和时间列出消息，新的在前，每条带链接；`--since` 和 `--until` 接受 ISO 时间或 `30m`、`2h`、`7d` 这样的相对时间。
- `groups`：从 open-lark 读出我所在的全部群，显示名称、人数、最近活跃时间，★ 标出关注的群。
- `watch add`：按完整名称、id 或名称中唯一的一段文字加入关注名单，名称对应多个群时列出它们并拒绝；从加入的时刻起收集这个群的全部消息，之前的消息不补。加入的是话题群时照样加入，但会提示：话题群只能收到推送来的消息（见上面「话题群」）。`watch remove` 移出名单，之后的新消息不再因为关注而收集，已收的保留。名单初始为空，改动直接写进存储，正在运行的收集器处理下一条消息时就按新名单判断，不需要重启。
- `status` 还显示加工端最近一轮和最近成功的时间、待加工的消息数、跳过的消息数（见上面「失败时」）和未结束的事项数；加工端的错误记在同一个错误列表里，来源是「加工」。
- `process`：运行加工端（常驻）。`--once` 把积压处理完就退出，有失败时退出码是 1。
- `matters`：未结束的事项，紧急的在前，每个带编号、紧急程度、标题、谁、要我做什么、期限、来源消息数、所在聊天和链接；`--all` 连同已结束的事项和结束理由。
- `ignore add`：按完整名称、id 或名称中唯一的一段文字把发送方加入忽略名单，只能是存储里发过消息的发送方（我自己除外），对应多个时列出它们并拒绝。`ignore remove` 移出名单，之后的新消息照常交给模型。改动直接写进存储，加工端下一批就按新名单处理。

## 安装为用户服务

在运行 open-lark 的机器上作为 systemd 用户服务运行。服务运行的是复制到 `~/apps/herdr-butler` 的一份代码，不是仓库的工作目录，所以切换分支、修改或测试仓库里的代码都不会改变正在运行的服务。配置（`~/.config/butler/`）和数据（`~/.local/share/butler/`）都不在这个目录里，重新复制不会碰到它们。

1. 在仓库根目录复制代码（不带测试）：

   ```bash
   mkdir -p ~/apps/herdr-butler
   rsync -a --delete --exclude test/ butler/ ~/apps/herdr-butler/
   ```

2. 按上面「配置和数据」写好 `~/.config/butler/butler.env`（权限 600）。
3. 把下面的单元文件保存为 `~/.config/systemd/user/butler.service`（Node 路径和 open-lark 服务用的一致，按需调整），然后执行 `systemctl --user daemon-reload && systemctl --user enable --now butler`。

```ini
[Unit]
Description=Butler collector: Feishu messages that concern me, from open-lark
After=open-lark.service

[Service]
Type=simple
WorkingDirectory=%h/apps/herdr-butler
ExecStart=%h/.local/share/fnm/node-versions/v24.13.0/installation/bin/node --disable-warning=ExperimentalWarning cli.mjs run
Restart=on-failure
RestartSec=10
UMask=0077

[Install]
WantedBy=default.target
```

加工端是第二个用户服务，单元文件 `~/.config/systemd/user/butler-processor.service`。它通过 herdr 用 SSH 连模型机器，所以服务里要能不经交互地 SSH 过去（不带口令的密钥，或者把 SSH agent 的套接字传给服务），`BUTLER_HERDR` 写 herdr 的完整路径：

```ini
[Unit]
Description=Butler processor: matters from the collected Feishu messages, by a model reached through herdr
After=butler.service

[Service]
Type=simple
WorkingDirectory=%h/apps/herdr-butler
ExecStart=%h/.local/share/fnm/node-versions/v24.13.0/installation/bin/node --disable-warning=ExperimentalWarning cli.mjs process
Restart=on-failure
RestartSec=30
UMask=0077

[Install]
WantedBy=default.target
```

第一次启动前，用命令行加好忽略名单（比如 `./cli.mjs ignore add Zebra2.0自动化投放平台`），否则这些发送方积压的消息会交给模型。加工端停止时等正在运行的那一批结束，最多 20 秒；没等到的那一批下次重做，留在模型机器上的工作区在下次启动时关掉。

更新：在仓库根目录重新执行第 1 步的 `rsync`，再 `systemctl --user restart butler butler-processor`。

日志看 `journalctl --user -u butler`：里面有推送的连接和断开，以及每一条错误（同样记在存储里，`status` 能看到）。

收集器停止时会等正在进行的一轮对账结束，最多 5 秒。每次写入都是一个事务，游标只在它之前的消息存好之后才前进，所以被打断的那一轮下次会重做，不会丢也不会重。

## open-lark 重启时

收集器的重启或部署不影响 open-lark。open-lark 重启时推送连接断开，收集器按 1 秒起、最长 30 秒的间隔重连；open-lark 不可达的期间，每轮对账只记一条连接错误。连上之后立即对账一轮（包括话题列表和 @我补扫），补上重启期间丢失的推送和 open-lark 启动时补进来的消息。如果 open-lark 起来之后先处于轮询或重连状态，水位停在重启前最后一次健康的时刻，等同步回到 `live` 再对账一轮。

## 验证

```bash
cd butler
npm test
```

测试用一个假的 open-lark（`test/fake-open-lark.mjs`，HTTP 加 WebSocket）。它按 open-lark 真实的接口形状和怪癖实现：只读 token 的权限、按 open-lark 的规则规划消息窗口（多给 5 个位置，以它记下的聊天最后位置为上限，`maxPosition` 只算正的位置）、每个聊天都有一条位置 0 的旧消息、记下的最后位置可以停在 0 或旧值（重现话题群的尾页占位和空页）、普通群的话题回复位置 ≤ 0 并按时间混入、话题群的回复有位置、只有我能看到的临时消息放在前一条消息的位置上、已删除的消息不出现在页里但能按 id 读到、推送可能缺少消息内容、可能重复、有 `sync:complete` 哨兵、话题回复数变化时重发根消息，以及可以只写库不推送。覆盖：

- 推送里的新消息按类别入库；@所有人 不算 @我；不相关的群消息和我在不关注的群里发的普通消息不入库；记录的各个字段和链接。
- 同一消息重复推送只存一份；编辑和撤回更新原记录，更早读到的旧内容不会覆盖它。
- 推送缺少内容时按 id 补全。
- 收集器停机期间的消息（推送丢失和只写库的都有，含私聊、关注群和其中的话题回复、别的群里的 @我和回复我的、超过一页的私聊、停机期间新出现的聊天）在启动后补齐，无关消息不入库；运行期间 open-lark 只写库不推送的消息在下一轮补齐；没有新普通消息时的话题回复也能读到。
- open-lark 重启：推送重连，重启期间的消息补齐。
- 话题回复数变化时补取回复（open-lark 后台同步只重发根消息），正在取回复时又通报的回复也会取到；停机期间我参与的话题群话题里的新回复通过话题列表补齐。
- 取回复失败：404 或 500 的话题在一连串推送下只取一次；403 或 404 的话题记一条错误后不再等待重取；500 的话题只在之后的对账轮次重试，到次数上限记一条错误放弃，之后通报了更多回复再重新去取。
- @我在不关注、会话列表也没变化的群里能被补扫到，所在聊天在同一轮里补上名称；飞书搜索失败时记错误且扫描窗口不前进；open-lark 还没存下的 @我按位置读到，或留到以后重试。
- 关注名单的增删立即生效，新加入的群从加入时开始收集。
- open-lark 不处于 `live` 时水位不前进，同步回到 `live` 时触发对账并补上这期间的消息；open-lark 报告缺口时之后的轮次重试，一直有缺口就记一条错误并跳过。
- 尾页没有正的 `maxPosition` 时不记游标、聊天保持待读；往后读到的空页或「没有更新」比会话列表显示的最后一条消息低两个位置时不算读完（open-lark 记的最后位置为 0 或停在游标处两种情况）；读不到时之后的轮次重试，到次数上限记一条错误，聊天有新变化再读；open-lark 记的最后位置落后时，管家的存储有中间每一个位置就算读完，游标移到最后一条：最后一条已经推送来、存下时不用 `GET /messages/:id` 查它，没存下时查一次，只差一个位置就算读完（私聊里没推送的、不关注的群里和我无关的都一样）；中间缺一个位置（不关注的群里没存的消息、私聊里推送漏掉的消息、差两个位置时不关注的群里和我无关的消息），中间那个位置上只存了一条临时消息，或者最后一条是临时消息、已删除的消息时，仍然不算读完，到次数上限记一条错误；一个聊天每轮最多读 5 页，下一轮接着读；旧版本的存储自动升级，留下的游标 0 从尾部重新读。
- 话题群不按位置读（关注的也一样），其中我参与的话题里会话列表没有变化的回复由话题列表补齐，@我 由补扫补齐，推送来的消息照常入库；`watch add` 加入话题群时提示。
- 只读约束：一整套场景下来，收集器发出的请求里除 `POST /search/mention-history` 外全是 GET，没有任何 `pins` 请求；客户端拒绝其他写方法和 pins 路径。
- 启动时缺少所需路由就记错误、不收集，路由齐了再开始；推送连接一直没有应答时放弃这次连接并重试。
- 状态反映推送的连接和最近时间、对账的最近完成和成功时间、open-lark 同步状态和最近的错误；命令行的 `status`、`list`、`groups`、`watch` 和配置文件权限检查。

加工端的测试用假的模型（按收到的提示给出回复的函数）和假的 herdr（`test/fake-herdr.mjs`，一个单独的进程，按 herdr 0.9.1 的命令和 JSON 形状回答，记下每次调用）。覆盖：

- 新消息由模型整理成事项，加工端记下来源消息、用它们生成链接；这一批的消息都记为处理过，收集器的表不变；没有新消息时不调用模型。
- 后续消息归到模型指出的已有事项上，模型看得到这个事项和它之前的消息；模型说事项结束时关闭它并记下理由；我自己的消息作为上下文交给模型，只由它们构成的新事项不采纳。
- 忽略名单上的发送方的消息不交给模型，也不出现在上下文里；移出名单后，以前跳过的消息不会再交给模型。只有我自己的消息、又没有未结束的事项时不调用模型。
- 模型连不上时消息保持未处理并记错误，之后批次减半，成功一次后恢复；回复不是要求的 JSON 时同样，原始回复留在运行记录里。一条消息单独成批时回答总是用不了、而别的消息正常：它放到一边，后面的消息照常处理，它也不再作为它们的上下文；它每轮试一次，3 次后跳过并记一条写明这条消息的错误。模型整体出问题（连不上、没有回复、对什么都回答用不了的内容、放到一边后紧接着的运行也失败）时一条都不跳过，每轮最多多运行一次。单独成批成功一次的消息清掉记录。批次一次一个、从早到晚；提示超过上限时拆小批次和上下文。同一个存储上的第二个加工端拒绝启动。
- 提示：交给模型的是事实和这一次的编号，没有消息 id 和链接；说明是一行（herdr 不接受参数里的控制字符）；长消息截断。读回复：代码块包着的 JSON 也能读，不是 JSON 或缺少 `new` 和 `updates` 时报错；引用不存在的消息或事项、只引用旧消息或我自己的消息的新事项、没有理由的关闭都不采纳；网址被替换；文字长度有上限。
- herdr 调用层：每一批在自己的工作区里开一个新的、没有工具的 claude，命令都带 `--machine`，提示原样送到；出任何错（claude 起不来、超时、没有回复、回复被截断、停在确认界面）都关掉工作区并说明原因，其中只有回复被截断算模型回答了；回复晚到一点也能取到；机器连不上时直接报出 herdr 的错误；提示超过一个命令行参数的上限时什么都不启动；清理只关 `butler-model` 工作区。
- 命令行的 `ignore`、`process --once`（经假的 herdr）、`matters` 和 `status` 里加工端的一行。

测试不连接真实的 open-lark，也不调用真实的模型。和真实 open-lark、真实飞书消息的对照（链接能否打开、停机几分钟后的补齐）放在部署后的实测里做。

## 已知限制

- 关注的话题群不按位置读：我没参与的话题里的消息只能靠推送收到，收集器停机或断线期间的补不上（见「话题群」）。
- 推送缺失时，普通群里话题回复的补齐依赖三条途径：按位置读聊天时按时间混入的回复、根消息回复数的变化、话题列表。关注的普通群里某个我没参与的话题，如果它的回复是 open-lark 在收集器停机期间才后台同步进来的（回复时间早于收集器上次读到的位置），而那次重发根消息的推送又丢了，就补不上。
- 回复我的消息靠 `replyTo` 判断，open-lark 没有存下被回复的消息、管家存储里也没有时，判断不出来。
- 参与话题的判断只往回看话题最近的 500 条回复；在更长的话题里，我很早以前的回复找不到。
- 收集器跟随 open-lark 当前登录的账号，不检查账号是否变化。
- 加工端交给模型的 claude 是交互式的，它的会话记录（包括交给它的消息）留在模型机器上 `~/.claude/projects/` 里对应 `BUTLER_MODEL_CWD` 的目录：`--no-session-persistence` 只能和 `--print` 一起用。
- 提示是本机 herdr 命令行的一个参数（`herdr agent prompt` 不能从标准输入或文件读），Linux 上一个参数最多 128 KiB；加工端把提示限制在 80 KB，超过就拆小批次。
- 模型对某条消息总是给出空回答时，herdr 那边和 API 出错一样，都是「没有回复」，分不出来。这种消息不会被跳过，会一直留在队首，后面的消息也跟着等；错误记在 `status` 里。要分开这两种情况，需要 herdr 把 claude 的 StopFailure 和空回复分别报出来。
- 已经处理过的消息之后被编辑或撤回，不会再交给模型。
